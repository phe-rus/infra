# Rationale: 0001 instance branding on the settings page

## Context

infra's admin dashboard has a Settings section (`_workspace/settings`) with a working metrics subpage, but an empty landing page: the route and sidebar link exist, the page itself renders a placeholder greeting. Nothing about the instance (its name, logo, or any contact information) is configurable after deploy today; the only related value is `env.VITE_APPNAME`, a build time environment variable used for the session cookie prefix and, incidentally, as the app name shown in every outgoing email (`infra/auth/emails/emails.ts`). Renaming an instance, or giving it a logo, currently means editing an env var and redeploying, for something purely cosmetic.

This is the first admin configurable settings surface this codebase has needed. Every existing better-auth plugin (rate limiting, session policy, OAuth scopes) is configured once at Worker startup in `auth.ts`, not read per request. It's also the first feature that needs a custom, non-better-auth-owned D1 (Cloudflare's SQLite database) table: every table in `schemas/auth.ts` today is generated by better-auth's own CLI. And it's the first upload not tied to a specific user: `@infra/assets`' existing upload endpoints all attribute stored bytes to a `{userId}/` prefix for its personal storage quota, which is the wrong model for an instance wide asset an admin uploads on behalf of the whole deployment, not themselves.

The engineer scoped this build to branding only (name, logo, favicon, support email). Security policy and rate limit tuning were both raised and explicitly deferred, since making `auth.ts`'s static configuration dynamically read is a materially larger, riskier change than adding a cosmetic settings row.

## Options considered

### Option 1: A D1 settings table plus a new instance scoped upload endpoint in @infra/assets

A dedicated `instanceSettings` table (Drizzle, one singleton row) holds the branding fields. A small, additive endpoint in `@infra/assets` lets admins upload logo/favicon to a fixed `instance/` prefix, outside any individual user's storage quota, reusing the plugin's existing file type sniffing and SVG sanitization.

**Pros**:
- Branding data stays typed and queryable like every other piece of state in this codebase.
- Solves the quota problem at its root instead of working around it.
- The new endpoint is genuinely reusable: any future app on this auth server gets the same "instance asset" concept for free.

**Cons**:
- Touches a shared package other workspaces (`accounts`) also depend on, so this build must typecheck and ship cleanly there too, even though `accounts` won't call the new endpoint yet.

### Option 2: A D1 settings table, reusing the existing self service uploadFile endpoint as is

Same table, but skip touching `@infra/assets` entirely. The uploading admin's own user scoped `uploadFile` endpoint handles the logo/favicon, storing them under that admin's personal `{userId}/` prefix.

**Pros**:
- Zero changes to a shared package, smallest possible build.

**Cons**:
- A 2MB logo can consume nearly half of one admin's personal 5MB quota, an unrelated side effect an admin uploading branding on the instance's behalf shouldn't have to think about.
- Deleting that admin's account later would need special handling so it doesn't silently delete the instance's branding along with it.

### Option 3: Key value settings in KV instead of a D1 table

Store each branding field as an individual KV (Cloudflare's key value store) entry, mirroring how rate limiting already uses KV in this app, instead of a typed D1 row.

**Pros**:
- No new migration, no new schema file.

**Cons**:
- KV in this codebase is currently used only for better-auth's own rate limit storage, not application data; a key value store gives up the type safety, constraints, and query ability every other piece of app state here already gets from Drizzle/D1, for no real benefit at this scale (one row, four fields).

## Rationale

Option 1 is the only one that resolves the actual problem (an instance wide asset shouldn't be billed against one admin's personal quota) rather than working around or ignoring it. The cost, touching a shared package, is small and contained: one new endpoint, purely additive, not a change to any existing `@infra/assets` behavior, so `accounts` keeps working exactly as it does today. Option 3's KV approach would be a real inconsistency with how every other piece of app state in this codebase is modeled. Option 2 and Option 3's simplicity isn't worth their respective costs at this scale: a handful of fields, a low frequency admin action, not a hot path where avoiding one small package change would actually matter.
