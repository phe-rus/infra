# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`www` is the public marketing site for Pherus, serving the bare apex `pherus.org`: still no auth, no data fetching, no `domains/`, no `QueryClient` — every page is static, now with real i18n (see **i18n** below) instead of English-only. `accounts` (`account.pherus.org`) and `infra` (`infra.pherus.org`) carry the actual product. See the monorepo root `CLAUDE.md` for the `infra`/`accounts`/`www` split.

All real routes live under a `/_public` layout route (`src/routes/_public/route.tsx`), which wraps every page in shared `<Toolbars />`/`<Footers />` chrome (`components/toolbars/`, `components/footers/`, both top-level dirs — not under `src/`; `toolbars/` was renamed from an earlier `headers/`, keep using the new name). There is no `src/content/`, `src/data/divisions.tsx`, `division-mark.tsx`, `lib/frontmatter/`, or `@tanstack/markdown` dependency — several markdown-driven content approaches were tried and abandoned this project's history; the site stays static, no markdown pipeline. Route components define nothing at module scope except the `Route` export itself — every page's content lives in `www/data/` instead, see **Content data** below. **Never use the word "division"** anywhere in this app (UI copy, variable/field names, comments) — the site's own vocabulary is "resource" (`Resource`, `data/showcase.ts`, `/showcase/$slug`); this was a deliberate terminology sweep, not a style nit.

This app shares `@infra/ui`'s actual design tokens and components (`Button`, `Badge`, `Avatar`, `buttonVariants`, etc.) — it does not carry its own color palette or font stack, and the i18n/design work described below never touched `shared/ui/src/globals.css` or `typeset.css`. `<body>` carries the `typeset` class globally (`shared/ui/src/typeset.css`), which already styles every `h1`–`h6`, `p`, `ul`/`ol`/`li`, `table`/`th`/`td`, `blockquote`, and `pre` under it — a route rendering prose (via `renderDoc()`, see **Content data**) never needs its own `[&_h2]:...`/`[&_p]:...` Tailwind overrides for this, that was tried and reverted as redundant with (and fighting) the shared system. The one opt-out is `data-not-typeset` on an element that isn't real prose (an `<img>`, or a `<pre>` holding verbatim non-code text like a license body) — same escape hatch, not a new one. Icons come from HugeIcons (`@hugeicons/react`'s `HugeiconsIcon` + `@hugeicons/core-free-icons`), not Tabler, which this codebase used previously — every icon usage is `<HugeiconsIcon icon={SomeNameIcon} />`, never a bare `<IconSomeName />`. A link styled as a button uses TanStack Router's own `<Link>` with `buttonVariants({ variant, size })` applied as `className`, not `LinkButton` (that renders a plain `<a>`, losing TanStack Router's client-side navigation). `<Button render={...}>` is fine to use directly if needed: `@infra/ui`'s components are now built on Base UI (`@base-ui/react`), whose `render` prop accepts a bare `ReactElement` (not react-aria-components' render-function shape this codebase used previously). `motion` (the `framer-motion` successor) is used for the Toolbars' mega-menu enter/exit (`AnimatePresence`, with a staggered per-section reveal and `useReducedMotion`-aware distances) and the nav-trigger underline — the only animation lib in the app.

**i18n**: real locales — `en` (base, unprefixed at `/`), `zh` (`/zh/…`), `fr` (`/fr/…`) — built on `@inlang/paraglide-js`'s Vite plugin (`project.inlang/settings.json`, `paraglideVitePlugin` in `vite.config.ts`). Paraglide is the actual copy source now, not just the routing/locale-detection engine — the hand-authored-dictionary approach described in earlier drafts of this doc (`lib/i18n/dictionaries/*.json`, a `getDictionary()` helper) was never built; don't reintroduce it without revisiting this decision. `www/messages/{en,zh,fr}.json` hold real, hand-translated content directly, read at render time via the compiled `m` proxy (`import { m } from "@/paraglide/messages"`). Message ids can carry dots and dashes (`nav.legal.cookie-policy`), which gives real per-section grouping, but only through bracket/string-key access on `m` (`m["nav.legal.cookie-policy"]()`) — there's no dot-chained `m.nav.legal.cookiePolicy()` form. Paraglide only owns short, single-string chrome now: nav labels (`nav.*`), page titles/descriptions, and the handful of connector words in `legal.common.*` (`lastUpdated`, `seeAlso`, `and`). Long-form page bodies (legal pages, license text) do **not** go through Paraglide at all — see **Content data** for why and where they actually live. Every real page is fully translated in all three locales now, nothing left hardcoded English. `outputStructure` in `vite.config.ts` is `"locale-modules"` (one compiled file per locale) — deliberately not `"message-modules"` (one file per message key, tried first): that per-message split caused a real production bug, since browser ad/privacy blockers reflexively block any request whose filename matches cookie-consent patterns (a compiled `nav_legal_cookie_policy.js` in this case), and because the toolbar renders inside the `_public` layout wrapping every page, one blocked message chunk crashed the entire site's chrome, not just the affected page. `urlPatterns` in `vite.config.ts` prefixes only `zh`/`fr`; `en` matches the bare catch-all pattern. `src/router.tsx`'s `rewrite` (`localizeUrl`/`deLocalizeUrl`) does the prefix rewriting transparently — no route files are locale-aware, no `$locale` param route exists or is needed. `src/server.ts` wraps the Cloudflare fetch handler in `paraglideMiddleware`, passing the *original* `request` through to `handler.fetch` (not the middleware's own delocalized one) since TanStack Router already owns the rewrite — see the doc comment in the generated `src/paraglide/server.js` for why passing the wrong one causes a redirect loop. `src/paraglide/` is fully generated (gitignored, regenerated by `vite build`/`vite dev`, never hand-edited) — `emitTsDeclarations: true` is set so it ships real `.d.ts` files. **`@` resolves to the `www` package root, not `src/`** (see `vite.config.ts`'s `resolve.alias` and `tsconfig.json`'s `paths`), so anything importing generated Paraglide output from outside `src/` uses `@/src/paraglide/...`, while files already inside `src/` use a relative `./paraglide/...` or `../paraglide/...`. `components/toolbars/config.ts`'s `getNavItems()` builds the nav tree fresh on every render by calling `m[...]()` directly — no translated/untranslated split, no per-item fallback lookup; it's plain data, always current for whichever locale is active (previously this was memoized with an empty dependency array, which silently froze the nav text at whatever locale was active on first render — fixed by not memoizing it, since the list is trivially cheap to rebuild). `components/toolbars/views/locale-switcher.tsx` is the only UI for switching locale, built on `@infra/ui/components/select`, driving Paraglide's `setLocale()`. There's no footer component yet (see **Footer** below), so footer copy isn't part of this i18n pass. `lib/seo.ts`'s canonical URL runs through `localizeUrl()` so it's correct per-locale. `shared/ui`'s `ComposeViewport` widget gained one small additive `lang?: string` prop (default `"en"`) so `__root.tsx` can pass `getLocale()` through to `<html lang>` — this is shared by `infra`/`accounts` too, but the prop is optional and defaults to the old hardcoded behavior, so it changes nothing for them.

**Content data (`www/data/`)**: every page's content is a zod-validated tree, one file per page (`data/home.ts`, `data/about-us.ts`, `data/showcase.ts`, `data/legal.ts`, `data/licenses.ts`), no `lib/config.ts` anymore. Each file defines its own zod schema, then calls `data/lib/handler.ts`'s `defaultHandlers(schema)(values)` — a thin `schema.parse` wrapper — so `export const home = defaultHandlers(HomeSchema)({...})` is both the schema-checked data *and* the one export a route imports. `data/lib/message-key.ts`'s `messageKey` schema (`z.custom<MessageKey>()`) is how a field holding a Paraglide message id (`titleKey`, `descriptionKey`) still gets real validation. Route-specific `path` fields are typed `z.literal(...)`/`z.enum([...])`, not bare `z.string()` — that's what lets `<Link to={item.path}>` keep type-checking against the router's real route union instead of degrading to a loose string.

Long-form content (legal page bodies, license text, a showcase resource's deep-dive) is a Tiptap `JSONContent` doc, not HTML and not Paraglide keys — the site's own CMS will eventually be Tiptap-based, so this is the format it'll read and write either way. `@tiptap/core` is a devDependency imported `import type` only (fully erased at build time, zero runtime bundle cost); `data/lib/tiptap-doc.tsx`'s `renderDoc(doc)` is the one dependency-free renderer (paragraph, heading, text + bold/italic/code/link marks, bullet/ordered lists, `codeBlock`, `table`/`tableRow`/`tableHeader`/`tableCell`, `blockquote`, `hardBreak`) — add a node type there, not a one-off renderer per page. A `table`'s wrapper uses the shared `typeset-scroll` utility class (from `typeset.css`), not a bespoke `overflow-x-auto`.

Legal and license content is **per-language**, not per-Paraglide-key: `data/legal/*.json` and `data/licenses/*.json` each hold `{ en: TiptapDoc, zh: TiptapDoc, fr: TiptapDoc }` (or a `TiptapDoc` alone for licenses, which are English-only, see below), resolved by `data/lib/locale.ts`'s `activeLocale()` and loaded via `import.meta.glob(..., { eager: true })`. This was a deliberate migration off Paraglide for exactly this content: one Paraglide message key per heading/body line doesn't scale past a couple of sentences, and translating a real document means translating the *document*, not reassembling it from fifty independent keys. Nav labels, page titles, and `legal.common.*` connector words are the one exception that stays on Paraglide (see **i18n**), since those are genuinely short, shared, single-string UI chrome. License bodies specifically are **never translated** — only the surrounding page chrome (disclaimer, description) is — and are stored as a `codeBlock` Tiptap node so the verbatim text round-trips exactly; `data/licenses/strings.json` holds the small set of translated short strings (index intro, page description, the Pherus-license placeholder, the disclaimer).

`data/showcase.ts`'s `resolveResource(slug)` attaches a resource's optional `body` (from `data/showcase/*.json`, English-only, same reasoning as license text — no per-language translation infrastructure exists for this yet) on top of its static fields. **Only write a full detailed body** (technology stack, features, pros/cons, comparisons) **for something actually verifiable against real code in this repo or one you can audit** — Pass earned one because `infra`/`accounts` are real, auditable apps right here. Every other resource (Health, Collective, Research, Software, Transspace, Laniina, Futa, Sora) has no real implementation anywhere accessible, so each gets a short vision paragraph (grounded in copy that already existed elsewhere, e.g. `overview.fields.*`, never invented) plus a bracketed placeholder blockquote saying the project is still being defined — inventing a tech stack or feature list for these is exactly the kind of fabricated-sounding fact this app's legal-content convention already forbids, just applied to product marketing instead of legal text. `data/icons.ts` maps a small set of plain string keys (`"idea"`, `"security"`, ...) to the actual HugeIcons components, so content data stays serializable strings and never embeds a component reference directly.

`www/src/routes/api/` mirrors `infra`'s public CDN read path convention (`server: { handlers: { GET } }` on a `createFileRoute`, see `infra/CLAUDE.md`): one endpoint per license and legal page (`/api/mit-license`, `/api/privacy-policy`, ...), returning the same resolved JSON (`resolveLicense`/`resolveLegalPage`/`resolveCookiePolicy`) the page itself renders, so this content is fetchable outside the app too. `/api/cookie-policy` doesn't exist — it's `/api/site-storage`, and its data asset is `data/legal/site-storage.json`: a real browser ad-blocker rule matching "cookie" in a URL cascaded into breaking the whole app's dev-mode hydration (confirmed by reproducing it), so anything with "cookie" in its own file/route name got renamed; the *page* URL `/legal/cookie-policy` was left alone since top-level navigations aren't ad-blocked, only subresource fetches are.

**Routes**: `/` (`_public/index.tsx`) is the real landing page — hero, a `home.fields` chip grid (six fields of interest, `data/home.ts`), a "what we're building" marquee (`showcase.items` filtered to ones with a `feed`), and a real showcase highlight section: three tabs (Identity/Community/Research, `home.showcaseTabs`) driven by `resourcesByHomeCategory()`, laid out `columns-1 md:columns-2 lg:columns-3` (masonry, matching `/showcase`'s own card shape) inside each tab, never a plain grid — home shows curated *highlights* only, `/showcase` is where the full catalog lives. `/about-us` covers what Pherus does, where it's based (the real address also used on `/legal/legal-notice`), how it works, a "what we're building" marquee, and contact (email + phone). `/showcase` (`showcase/index.tsx`) is the full masonry catalog of every resource with a `descriptionKey`; `/showcase/$slug` is the detail page, rendering a resource's `tags`/`stack`/`catalogs`/`links`/`status` badge and its optional `body` via `renderDoc()`. `/legal` and `/licenses` are each an index (a plain link list with a vertical accent tick beside each row, `w-px bg-primary/40` brightening on hover — never a bordered/`bg-muted` card) plus four detail pages apiece. Every route above has its own `head()` calling `lib/seo.ts`'s `seo()` — see **SEO** below.

**Toolbars** (`components/toolbars/`): `config.ts`'s `getNavItems()` builds a flat `NavItem[]` fresh on every call (`Home`, `Showcase`, `About us`, plus two grouped items, `Legal` and `Licenses`, each carrying an `items: NavLeaf[]` submenu) by calling `m[...]()` directly for every label — see **i18n** for why this isn't memoized. There is no hover-triggered desktop mega-menu and no separate mobile-only nav: `views/nav-drawer.tsx` is the one `NavDrawer` component for every breakpoint, a slide-out panel (`createPortal`'d into `document.body`, width driven by `@infra/ui/lib/use-media-query`'s `useIsMobile`) wrapped in Motion's `AnimatePresence` so its overlay/panel/stagger-list `exit` animations actually play on close (an earlier version gated the whole portal behind `open &&` outside `AnimatePresence`, which silently made every `exit` prop dead code — fixed by moving the `open &&` check inside `AnimatePresence` instead). `views/locale-switcher.tsx` is the language `Select` described in **i18n**. `components/toolbars/index.tsx` is the top-level `Toolbar`: the sticky header bar (logo, `LocaleSwitcher`, a "More" toggle button) plus the `NavDrawer` it opens — it holds the only piece of local state (`open`). None of this is tied to a resources/mega-menu data model — the landing page's own content and the showcase resources list (`data/showcase.ts`) are unrelated, separate data.

**Footer** (`components/footers/`): `config.ts` derives its resource columns straight from `toolbars/config.ts`'s `Resources` `NavGroup` (see above — no separate/duplicated list), wrapped with a static `Company` group (About, Open Knowledge, Investors, Contact, Blog, FAQ) and a static `Legal` group (Privacy Policy, Terms & Conditions) around it. Some `FooterLink`s intentionally have no `to` yet (pages that don't exist), rendered as plain non-clickable text rather than dead links.

**SEO** (`lib/seo.ts`): `seo({ title, description, image, keywords, type, path, publishedTime })` returns `{ meta, links }` for a route's `head()` — builds the page `<title>` (`"{title} · Pherus"`, or bare `"Pherus"` for the home page), description, OG/Twitter tags (image URLs made absolute via `SITE_URL`), and a canonical `<link>` run through `localizeUrl()` so it reflects the current locale prefix. Also exports `organizationJsonLd()` for the root route's `Organization` JSON-LD block. `SITE_URL` comes from `import.meta.env.VITE_SITE_URL` (see **Env vars** below), never hardcoded. `public/robots.txt` allowlists real search engines (Googlebot, Bingbot, DuckDuckBot, Slurp, YandexBot, Baiduspider) plus named AI crawlers (ClaudeBot and friends, Google-Extended, GPTBot/ChatGPT-User/OAI-SearchBot, Grok) individually with `Allow: /`, then blocks everything else via a trailing `User-agent: *` / `Disallow: /`. `public/sitemap.xml` is a static hand-maintained list of real routes (still English-URL only; not yet updated with `/zh/`/`/fr/` variants) — update it when a route is added or removed.

**Env vars**: `VITE_SITE_URL` is this app's own public base URL, used by `lib/seo.ts` for canonical/OG/Twitter/JSON-LD URLs and by `sitemap.xml`'s implied origin — `.env.local` (gitignored) points it at the local dev server (`http://100.115.92.26:3002` in this ChromeOS Crostini setup, or `http://localhost:3002`), `.env.production` (also gitignored, committed pattern only via `.env.example`) hardcodes the real `https://pherus.org`; no app starts already running in production, so local dev always needs `.env.local`. `VITE_ACCOUNTS_URL` is `accounts`'s base URL for the "sign in" link. `X_LOCAL_OBSERVABILITY` is the same Cloudflare Vite plugin dev-only span capture documented in `infra/CLAUDE.md`'s "Known issues" section.

Package manager: **bun** (`bun.lock` is the lockfile, gitignored, autogenerated by `bun install`, never committed).

## Commands

```bash
bun install       # install dependencies
bun run dev       # start dev server on port 3002
bun run build     # production build (also (re)compiles src/paraglide)
bun run typecheck # tsc --noEmit
bun run deploy    # wrangler deploy
```

## Architecture

Same 4-file TanStack Start convention as `infra`/`accounts` (`src/start.ts`, `src/server.ts`, `src/router.tsx`, `src/routes/__root.tsx`), stripped of everything session/query-client related since this app has no state to bootstrap — `src/server.ts` and `src/router.tsx` additionally carry the Paraglide middleware/rewrite wiring described in **i18n**. Everything else lives under the `/_public` layout route described above, not directly in `src/routes/`.

Don't add `better-auth`, `@tanstack/react-query`, or a `domains/` folder here — if a feature needs any of those, it belongs in `accounts`, not `www`. This still holds even with i18n in place: there's no async data fetching in this app, so there's nothing for a `QueryClient` to manage.
