# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`www` is the public marketing site for Pherus, serving the bare apex `pherus.org`: still no auth, no data fetching, no `domains/`, no `QueryClient` — every page is static, now with real i18n (see **i18n** below) instead of English-only. `accounts` (`account.pherus.org`) and `infra` (`infra.pherus.org`) carry the actual product. See the monorepo root `CLAUDE.md` for the `infra`/`accounts`/`www` split.

All real routes live under a `/_public` layout route (`src/routes/_public/route.tsx`), which wraps every page in shared `<Toolbars />`/`<Footers />` chrome (`components/toolbars/`, `components/footers/`, both top-level dirs — not under `src/`; `toolbars/` was renamed from an earlier `headers/`, keep using the new name). There is no `src/content/`, `src/data/divisions.tsx`, `division-mark.tsx`, `lib/frontmatter/`, or `@tanstack/markdown` dependency — several markdown-driven content approaches were tried and abandoned this project's history; the site stays static, plain-TypeScript data, no markdown pipeline. Route components define nothing at module scope except the `Route` export itself. Data that's genuinely one page's own (the landing page's community-links list, the FAQ's Q&A sections) lives inline inside that route's own component function via `useMemo`. Data reused across more than one route — blog posts, resource pages, the resources nav tree — is centralized instead, see **Content data** below. **Never use the word "division"** anywhere in this app (UI copy, variable/field names, comments) — the site's own vocabulary is "resource" (`resources`, `ResourceTag`, `/r/$slug`); this was a deliberate terminology sweep, not a style nit.

This app shares `@infra/ui`'s actual design tokens and components (`Button`, `Badge`, `Avatar`, `buttonVariants`, etc.) — it does not carry its own color palette or font stack, and the i18n/design work described below never touched `shared/ui/src/globals.css` or `typeset.css`. Icons come from HugeIcons (`@hugeicons/react`'s `HugeiconsIcon` + `@hugeicons/core-free-icons`), not Tabler, which this codebase used previously — every icon usage is `<HugeiconsIcon icon={SomeNameIcon} />`, never a bare `<IconSomeName />`. A link styled as a button uses TanStack Router's own `<Link>` with `buttonVariants({ variant, size })` applied as `className`, not `LinkButton` (that renders a plain `<a>`, losing TanStack Router's client-side navigation). `<Button render={...}>` is fine to use directly if needed: `@infra/ui`'s components are now built on Base UI (`@base-ui/react`), whose `render` prop accepts a bare `ReactElement` (not react-aria-components' render-function shape this codebase used previously). `motion` (the `framer-motion` successor) is used for the Toolbars' mega-menu enter/exit (`AnimatePresence`, with a staggered per-section reveal and `useReducedMotion`-aware distances) and the nav-trigger underline — the only animation lib in the app.

**i18n**: real locales — `en` (base, unprefixed at `/`), `zh` (`/zh/…`), `fr` (`/fr/…`) — built on `@inlang/paraglide-js`'s Vite plugin (`project.inlang/settings.json`, `paraglideVitePlugin` in `vite.config.ts`), but **only for the routing/locale-detection engine**, not for message text. Paraglide's own compiled message system (`m.some_key()`) only supports flat, underscore-namespaced keys — it cannot produce real nested objects — so UI copy instead lives in hand-authored nested dictionaries at `lib/i18n/dictionaries/{en,zh,fr}.json` (shape: `nav`, `footer`, `overview`, each nested — e.g. `overview.hero.title`, `nav.mobile.description`), combined and typed by `lib/i18n/index.ts`'s `getDictionary()` (reads the current request/client locale via Paraglide's `getLocale()` and returns the matching dictionary — call it inside a component's render, never at module scope, since ES modules are cached per process and the locale is per-request). The `www/messages/{en,zh,fr}.json` files and the `plugin.inlang.messageFormat` module in `project.inlang` are inert scaffolding required for Paraglide's compiler to run at all (it errors on an empty `modules` array) — they're intentionally left near-empty; don't add real copy there, it won't be used. `urlPatterns` in `vite.config.ts` prefixes only `zh`/`fr`; `en` matches the bare catch-all pattern. `src/router.tsx`'s `rewrite` (`localizeUrl`/`deLocalizeUrl`) does the prefix rewriting transparently — no route files are locale-aware, no `$locale` param route exists or is needed. `src/server.ts` wraps the Cloudflare fetch handler in `paraglideMiddleware`, passing the *original* `request` through to `handler.fetch` (not the middleware's own delocalized one) since TanStack Router already owns the rewrite — see the doc comment in the generated `src/paraglide/server.js` for why passing the wrong one causes a redirect loop. `src/paraglide/` is fully generated (gitignored, regenerated by `vite build`/`vite dev`, never hand-edited) — `emitTsDeclarations: true` is set so it ships real `.d.ts` files. **`@` resolves to the `www` package root, not `src/`** (see `vite.config.ts`'s `resolve.alias` and `tsconfig.json`'s `paths`), so anything importing generated Paraglide output from outside `src/` uses `@/src/paraglide/...`, while files already inside `src/` use a relative `./paraglide/...` or `../paraglide/...`. `components/toolbars/views/locale-switcher.tsx` is the only UI for switching locale, built on `@infra/ui/components/select`, driving Paraglide's `setLocale()`. Static structural data (`toolbars/config.ts`'s `NavItem[]`, `footers/config.ts`'s `FooterGroup[]`) stays in English and untranslated by design — a small pure-function lookup in each config file (`navLabel(item, t)`, `footerLabel(label, t)`) maps the known English label strings to the current dictionary's translated string at render time, falling back to the English label for anything not in the lookup (e.g. the Resources mega-menu's per-resource labels/descriptions, which are out of scope for translation this round — only the toolbar/footer chrome and the landing page copy are translated). `lib/seo.ts`'s canonical URL runs through `localizeUrl()` so it's correct per-locale. `shared/ui`'s `ComposeViewport` widget gained one small additive `lang?: string` prop (default `"en"`) so `__root.tsx` can pass `getLocale()` through to `<html lang>` — this is shared by `infra`/`accounts` too, but the prop is optional and defaults to the old hardcoded behavior, so it changes nothing for them.

**Content data (`lib/config.ts`)**: the one shared data module, so blog/resource content isn't repeated between a list route and its detail route. Exports a `Block` union (`{h2: string} | {p: string} | {ul: string[]}`, a page body is just `Block[]`, rendered by manually mapping over it in JSX — no markdown/MDX renderer anywhere), `posts: Post[]` (real blog posts: `slug`, `title`, `resource`, `date`, `excerpt`, `cover`, `body`), and `resources: Resource[]` (one entry per Pherus resource: `slug`, `label`, `tag: ResourceTag` (`"active" | "in development" | "in planning"`), `tagline`, `body`) — real, specific content per resource (kept intentionally short, banner-length, not a full pitch deck — enough to convey the idea without exposing every detail), not filler; this content is not yet translated (see **i18n** above). `src/routes/_public/blog/index.tsx` and `blog/$slug.tsx`, and `r/$slug.tsx`, all import from here. Content is written close to verbatim from whatever source material was provided for it (e.g. Transspace's page draws on real copy from a sibling project) rather than paraphrased or genericized — when real source content exists, use it as given, don't compress it for "voice consistency."

**Routes**: `/` (`_public/index.tsx`) is the real landing page — hero, a "what we're working on" chip grid built from the Toolbars' Resources nav tree (`components/toolbars/config.ts`, via `useMemo`, not duplicated data), a real testimonial quote attributed to Pherus's own founder, and a community-links grid; all its own copy comes from the `overview` dictionary namespace (see **i18n**), and the hero/section spacing and type scale got an Awwwards-tier pass (viewport-scale hero type, wider vertical rhythm) without touching `shared/ui`. Some pieces are still placeholder: the "Be in the mix with herus" heading has an intentional-but-unresolved typo (kept as-is, untranslated, in every locale — it's a stylized pun, not literal copy), the sign-up CTA and its avatar image are mockup, not wired to anything. `/blog` (`blog/index.tsx`) is a `columns-1 md:columns-2 lg:columns-3` masonry grid of post cards with a cover block, resource badge, date, title, excerpt; `/blog/$slug` renders one post's `body` blocks. `/faq` (`faq/index.tsx`) is real Q&A content in three sections (General/Status/Getting involved) rendered as a `grid grid-cols-1 md:grid-cols-2` of left-accent-bordered cards, inline `useMemo` data (FAQ content isn't reused elsewhere, so it doesn't live in `lib/config.ts`). `/r/$slug` (a generic resource/detail page — the Toolbars' Resources mega-menu links here, e.g. `/r/infra`, `/r/seer`, `/r/transspace`) renders one `resources` entry's `body` blocks under its `tag` badge and `tagline`. Every route above has its own `head()` calling `lib/seo.ts`'s `seo()` — see **SEO** below. `/blog`, `/faq`, and `/r/$slug` are not yet part of the i18n/design pass — only their nav/footer chrome is translated for now.

**Toolbars** (`components/toolbars/`): `config.ts` defines a `NavItem[]` tree — flat `NavLink`s (`Overview`, `FAQ`, `Blog`) alongside one `NavGroup` (`Resources`), whose `items` are five `NavSection`s (`Platforms & Services`, `Products`, `Community & Knowledge`, `Health & Home`, `Frontier`), each holding `NavLeaf`s (`label`, `description`, `to`, `tag: "active" | "in development" | "in planning"`) that render as `views/mega-menu.tsx` on hover. This is the **single source of truth for the resources list**: the landing page's chip grid and the footer's resource columns both derive their data from this file (via `isNavGroup`), rather than each keeping their own copy — adding or renaming a resource only ever happens here. `views/mobile-nav.tsx` covers the same tree with swipe support below `md`; `views/nav-trigger.tsx` is the shared trigger button for both flat links and group headers; `views/locale-switcher.tsx` is the language `Select` described in **i18n**.

**Footer** (`components/footers/`): `config.ts` derives its resource columns straight from `toolbars/config.ts`'s `Resources` `NavGroup` (see above — no separate/duplicated list), wrapped with a static `Company` group (About, Open Knowledge, Investors, Contact, Blog, FAQ) and a static `Legal` group (Privacy Policy, Terms & Conditions) around it. Some `FooterLink`s intentionally have no `to` yet (pages that don't exist), rendered as plain non-clickable text rather than dead links.

**SEO** (`lib/seo.ts`): `seo({ title, description, image, keywords, type, path, publishedTime })` returns `{ meta, links }` for a route's `head()` — builds the page `<title>` (`"{title} · Pherus"`, or bare `"Pherus"` for the home page), description, OG/Twitter tags (image URLs made absolute via `SITE_URL`), and a canonical `<link>` run through `localizeUrl()` so it reflects the current locale prefix. Also exports `organizationJsonLd()` for the root route's `Organization` JSON-LD block. `SITE_URL` comes from `import.meta.env.VITE_SITE_URL` (see **Env vars** below), never hardcoded. `public/robots.txt` allowlists real search engines (Googlebot, Bingbot, DuckDuckBot, Slurp, YandexBot, Baiduspider) plus named AI crawlers (ClaudeBot and friends, Google-Extended, GPTBot/ChatGPT-User/OAI-SearchBot, Grok) individually with `Allow: /`, then blocks everything else via a trailing `User-agent: *` / `Disallow: /`. `public/sitemap.xml` is a static hand-maintained list of real routes (still English-URL only; not yet updated with `/zh/`/`/fr/` variants) — update it when a route is added or removed.

**Env vars**: `VITE_SITE_URL` is this app's own public base URL, used by `lib/seo.ts` for canonical/OG/Twitter/JSON-LD URLs and by `sitemap.xml`'s implied origin — `.env.local` (gitignored) points it at the local dev server (`http://100.115.92.26:3002` in this ChromeOS Crostini setup, or `http://localhost:3002`), `.env.production` (also gitignored, committed pattern only via `.env.example`) hardcodes the real `https://pherus.org`; no app starts already running in production, so local dev always needs `.env.local`. `VITE_ACCOUNTS_URL` is `accounts`'s base URL for the "sign in" link. `X_LOCAL_OBSERVABILITY` is the same Cloudflare Vite plugin dev-only span capture documented in `infra/CLAUDE.md`'s "Known issues" section.

Package manager: **bun** (`bun.lock` is the lockfile, gitignored, autogenerated by `bun install`, never committed).

## Commands

```bash
bun install       # install dependencies
bun run dev       # start dev server on port 3002
bun run build     # production build (also (re)compiles src/paraglide)
bun run typecheck # tsc --noEmit
bun run deploy    # wrangler deploy
```

## Architecture

Same 4-file TanStack Start convention as `infra`/`accounts` (`src/start.ts`, `src/server.ts`, `src/router.tsx`, `src/routes/__root.tsx`), stripped of everything session/query-client related since this app has no state to bootstrap — `src/server.ts` and `src/router.tsx` additionally carry the Paraglide middleware/rewrite wiring described in **i18n**. Everything else lives under the `/_public` layout route described above, not directly in `src/routes/`.

Don't add `better-auth`, `@tanstack/react-query`, or a `domains/` folder here — if a feature needs any of those, it belongs in `accounts`, not `www`. This still holds even with i18n in place: there's no async data fetching in this app, so there's nothing for a `QueryClient` to manage.
