# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

This repo is both a self-hosted authentication backend (better-auth, on Cloudflare Workers + D1 + KV) and its admin dashboard: one TanStack Start (React 19 + SSR) app, one Worker, serving both the dashboard UI and better-auth's HTTP API. See `README.md` for what the project is and why it exists; this file is the technical map.

Package manager: **bun** (`bun.lock` is the lockfile; `.vscode/settings.json` pins `npm.packageManager` to `bun`).

## Commands

```bash
bun install       # install dependencies
bun run dev       # start dev server on port 3000
bun run build     # production build (vite build)
bun run preview   # preview a production build
bun run test      # run the vitest suite once (vitest run)
bun run lint      # eslint
bun run format    # prettier --write across ts/tsx/js/jsx
bun run check     # prettier --check (no writes)
bun run typecheck # tsc --noEmit
```

There are no test files in the repo yet and no `vitest.config.*`, vitest currently runs against Vite's default config. When adding tests, run a single file with `bunx vitest run path/to/file.test.tsx` or a single test name with `bunx vitest run -t "test name"`.

## Architecture

**Routing is file-based and code-generated.** Routes live under `src/routes/`; `src/routeTree.gen.ts` is auto-generated by the `@tanstack/router-plugin` Vite plugin on dev/build, never hand-edit it (it's marked read-only in `.vscode/settings.json`). Three pathless layout routes sit at the top level:
- `_auth` (`src/routes/_auth/route.tsx`): `sign-in` and `setup`, redirects away if a session already exists. `setup` is two phases toggled by one `initialized` boolean in the route file, not a multi-step wizard: `features/auth/run-setup-migrations.tsx` (mandatory before an owner can exist) then `features/auth/create-first-user.tsx` (name/email/password only). `sign-in.tsx` renders `features/auth/login.tsx` the same way, its own route-level job is just the `session-expired` search-param toast, nothing form-related. Nothing else gets collected here: app name, security, email-verification, sign-in methods, and instance access (owner/admin only, `user` never) are all static now, nothing left to configure afterward from a dashboard settings page, that whole category of "editable after setup" no longer exists in this app. An earlier five-step wizard (`components/auth/setup/`) collected all of that upfront; it was deleted, not because the settings don't matter, but because forcing them into a one-time form added friction for zero benefit over just defaulting sensibly and letting an owner change them whenever.
- `_workspace` (`src/routes/_workspace/route.tsx`): everything behind the dashboard shell. `beforeLoad` does two checks in order: is there a session (else redirect to `/sign-in`), then is this session's role allowed to access the instance at all (else redirect to `/unauthorized`), see **Access model** below. Root's own session fetch (`getSession` in `kit/auth/get-session.ts`) is deliberately non-throwing, it runs for every route including `/sign-in`/`/setup`, which exist to handle the no-session case, so this is the layout where "you actually need a session" gets enforced, not root.
- `_protected` (`src/routes/_protected/route.tsx`): just `unauthorized.tsx` today, deliberately outside `_workspace` so it renders without the `Dashboard` shell (someone who lands here isn't authorized to see it).

Current `_workspace` pages: `index` (home), `users` (member management), `storage` (per-user files, see Object storage below). `database`/`logs`/`billing` still exist as sidebar links in `Dashboard` with no route behind them yet. Team & Roles existed too (instance access, then later custom roles as well) and was removed entirely, same treatment as Providers and API keys elsewhere in this doc: access is fixed code now (see Access model below), nothing left to manage on a page. There is no self-service API keys feature, it was built, then removed entirely (plugin, middleware, functions, hooks, route, schema, types) as a deliberate scope decision, not a gap; don't reintroduce it without that decision being revisited.

**A route file's `RouteComponent` *is* the page — there is no separate page-wrapper component.** State, handlers, mutation hooks, a `useMemo(() => [...], [])`-wrapped column array, all of it lives directly in `RouteComponent`; `users.tsx`, `storage.tsx`, and `database.tsx` are all this shape now (each was previously a thin route delegating to a `features/<domain>/index.tsx` "page" component — that layer was removed as pure indirection). `src/features/<domain>/` holds only the individual pieces a page composes (`list-users.tsx`, `create-user.tsx`, `get-user-detail.tsx`, ...), flat, no nested `components/` subfolder, no generic `-section`/`-drawer` suffixes, named after the action or resource it's built around, matching its `kit/hypermedia/<resource>/` counterpart file-for-file wherever one exists. **`features/<domain>/index.ts` (never `.tsx`) is a plain re-export barrel over those pieces**, nothing else — it holds no component of its own, no JSX; a domain that hasn't outgrown a single file yet doesn't get one. `src/features/` is not where `components/ui/` (shadcn primitives), `components/widgets/` (generic reusable pieces), or `components/dashboard/` (the shell) belong, those three stay exactly where they are.

The one real exception is something genuinely reused by more than one call site. `components/widgets/` holds pieces reusable from anywhere (`DataTable`, the `useAppForm` blocks setup, `DialogWidget`), always imported, never inlined. `components/dashboard/` currently holds only the `Dashboard` shell itself. A feature-specific standalone dialog with only one caller, like the user-detail dialog, is not a `components/dashboard/` thing (that folder is for the shell), it lives flat in `features/<domain>/` per the note above; when in doubt for a small page, inline it into the route first, and only reach for `features/` once it's genuinely too large to.

**Shell / entry points**: `src/start.ts` creates the TanStack Start server instance and registers CSRF middleware scoped only to server-function requests. `src/router.tsx` builds the router and wraps it with `QueryProvider`. `src/routes/__root.tsx` renders the actual `<html>` document (theme is hardcoded to `dark` via a static class, not runtime-toggled), does the root `beforeLoad` (session + setup status, see below), and mounts `TanStackDevtools`.

**Query client is a client/server-aware singleton** (`src/lib/queryClient.tsx`): on the client, `getContext()` reuses one module-level `QueryClient` across navigations; on the server it always constructs a fresh one per request (standard SSR-safe pattern, don't change this to a plain module-level singleton, it would leak state across requests). The `QueryProvider` unconditionally mounts `TanStackDevtools` (Router + Query panels). It is not gated behind a dev/prod check, so don't add one without checking whether that's intentional for this project.

**`queryClient.tsx` overrides `focusManager` to always report focused**; `networkMode` and `retryDelay` are both back to react-query's defaults (an earlier version fixed `retryDelay` at 1s and set `networkMode: 'always'`, both were removed, along with the per-call `withTimeout` wrapper every `use*Hooks.ts` mutation/query used to be wrapped in — none of that is the app's problem to solve right now; if the local dev runtime's occasional unresponsiveness becomes disruptive again, that's the first place to look, not something to reintroduce speculatively). The one non-default piece left is queries' `retry`: a predicate that skips retrying on a `401`/`403` status and otherwise retries up to twice (mutations still default to `retry: 0`, untouched by any of this). The `focusManager.setEventListener` override still means `refetchOnWindowFocus` is inert app-wide (the tab is always reported focused, so the underlying visibility event this depends on never fires), no automatic refetch when returning to a tab; acceptable here since every mutation already invalidates its own affected queries explicitly. If you ever need real refetch-on-focus back, that override is the first thing to remove. With `networkMode` back to default, a query retry now *can* genuinely pause while the browser is offline and only resume on the next `online` event, unlike when `networkMode: 'always'` was set; this doesn't affect the local dev experience but is worth knowing if this app ever needs to behave differently offline.

**Errors surface as toasts globally**: the `QueryCache` in `queryClient.tsx` has an `onError` that calls `t.error(...)` (from `@/components/ui/sonner`, backed by `goey-toast`) for every failed query except `AbortError`. Individual query hooks generally don't need their own error handling/toast logic for reads, it happens centrally.

**Every mutation hook builds on `useAppMutation` (`src/kit/shared/use-app-mutation.ts`)** instead of calling `useMutation` directly. It reads the query client via `useQueryClient()` (React context, the same instance every `useSuspenseQuery` in the tree reads from) rather than each hook grabbing its own reference, takes an `invalidates` array of query keys and fires `invalidateQueries` for each one in `onSettled` (not awaited, callers don't need to see the refetch land before `mutateAsync` resolves), and applies the standard success/error toast pair from `successMessage`/`successDescription`/`errorMessage` so a hook only states its own keys and copy. `optimisticUpdate`'s `cancelQueries` call in `onMutate` **is** awaited, matching the documented react-query pattern (narrows the window where an in-flight refetch could land after the optimistic write and clobber it); an earlier version of this hook made it non-awaited chasing a "hang" theory that turned out to be wrong (confirmed by reading `query-core`'s `retryer.ts` directly: `cancelQueries` rejects synchronously, it can't hang `onMutate`). The optimistic rollback in `onError` only restores the pre-mutation snapshot if the cache still holds exactly what this mutation wrote, skipping it if a second mutation on the same key wrote something newer in the meantime, otherwise the rollback would silently erase that concurrent change. See any `kit/<domain>/use-*.ts` file for the shape. The exceptions are sign-in/sign-out/impersonation/complete-setup (`kit/auth/use-sign-in.ts`, `use-logout.ts`, `use-complete-setup.ts`, `kit/hypermedia/users/use-impersonate-user.ts`, `use-stop-impersonating.ts`), which swap out the session identity entirely and need `q.clear()` plus a navigation rather than a targeted invalidate, so they still call `useMutation` directly against the module-level `getContext()` client.

**Data flow: loader `ensureQueryData` + `useSuspenseQuery`, not `Route.useLoaderData()`, for anything a mutation can change.** The loader prefetches into the query cache so SSR/first paint has data; the component then subscribes via `useSuspenseQuery(sameQueryOptions())` so that a mutation's `invalidateQueries` actually triggers a re-render. `Route.useLoaderData()` is a one-time snapshot, fine for values a form seeds itself with once (e.g. a settings form's `defaultValues`) and forgets about, wrong for anything meant to stay live (a table of users, a list of API keys).

**`src/kit/` is the one place all backend-adjacent code lives**: `kit/auth/` (session/sign-in/setup), `kit/hypermedia/<resource>/` (`users/`, `objects/`, `stats/`, more resources nest alongside as they show up), `kit/middleware/` (`AdminMiddleware`/`OwnerMiddleware`), `kit/shared/` (cross-cutting helpers with no one domain), plus three flat root files: `kit/schemas.ts` (every zod schema), `kit/types.ts` (every shared type), `kit/index.ts` (a flat barrel re-exporting all of the above, for the rare case something needs a bit of everything). `src/auth/` (the better-auth config itself) and `src/components/` are deliberately outside `kit/`, this is about the server-function/hooks/schema/type layer, not the auth library setup or the UI.

**Inside a domain folder, `fnc.ts` holds every `createServerFn(...)` for that domain and nothing else** (no `Fn` suffix on the exported name: `createUser`, `banUser`, `getSession`). Everything that *wraps* those functions for the client lives outside `fnc.ts`, split by what kind of React Query hook it produces: a `get-<name>.ts` file holds a `*QueryOptions()` factory plus its `useQuery`/`useSuspenseQuery` hook (`get-users.ts`: `usersQueryOptions` + `useUsers`, both importing `listUsers` from `./fnc`); a `use-<name>.ts` file holds one or more `useMutation`/`useAppMutation` hooks (`use-sessions.ts`, `use-users.ts`). Grouping within `use-*.ts` follows what the actions actually do, not the resource name: `hypermedia/users/use-users.ts` bundles `createUser`/`removeUser`/`updateUser`/`uploadUserImage` because those only touch plain profile/collection data, while `use-sessions.ts` bundles `setUserRole`/`setUserPassword`/`banUser`/`unbanUser`/`impersonateUser`/`stopImpersonating`/`revokeUserSession`/`revokeUserSessions` because every one of those gates or manipulates a session's validity or permissions, not just a stored field. `kit/auth/` follows the same `fnc.ts` + `get-*`/`use-*` shape but without the domain-specific grouping (`get-session.ts`, `get-setup-status.ts`, `use-sign-in.ts`, `use-logout.ts`, `use-complete-setup.ts`, `use-run-setup-migrations.ts`, each is its own concern, nothing to pair up). Every domain folder has an `index.ts` barrel doing `export * from "./fnc"` plus one `export *` per `get-*`/`use-*` file (never named re-exports, since each source file already declares its own export name — a barrel just needs to say which files exist); import from `@/kit/<domain>` (or `@/kit/hypermedia/<resource>`), not the individual file, unless you're inside that same folder, where relative imports between colocated files (typically `import { x } from "./fnc"`) are normal. Inside a handler that needs the request's headers for an `auth.api.*` call, use `getRequestHeaders()` from `@tanstack/react-start/server` (synchronous, no `await`), assigned to its own `const headers = getRequestHeaders()` line, not called inline in the call args. Middleware bodies, by contrast, already receive `request` as a parameter from the framework and should use `request.headers` directly rather than also calling `getRequestHeaders()`. Don't thread `headers` through middleware `context` for handlers to consume; every handler that needs it calls the utility itself. A handler gated by `AdminMiddleware`/`OwnerMiddleware` never re-checks `if (!sessions)`, the middleware already guarantees a session (and the required role tier) before the handler runs; re-checking is dead code. A check that needs the *validated body* (not just the session), like `fnc.ts`'s "admin can only hand out the `user` role" rule on `createUser`, can't live in a `createMiddleware()` at all: TanStack Start always runs `.middleware([...])` before the server function's own `.validator()`, regardless of call order in the source, so a middleware here only ever sees the raw unvalidated body. Those live as plain guard functions in `kit/shared/` instead (`assert-can-assign-role.ts`'s `assertCanAssignRole`), called from inside the handler where `data` is already typed. `kit/shared/` is also where `useAppMutation`/`settleAll` (`use-app-mutation.ts`) and cache-patch helpers reused across a domain's mutation hooks (`patch-user-cache.ts`'s `patchUserInCache`, used by several of `hypermedia/users/`'s hooks) live, since none of those belong to one specific action.

A `fnc.ts`-consuming file's internal order is imports, then anything local and not itself a server function (types, plain consts like `stats/fnc.ts`'s `ACTIVE_WINDOW_MS`, helper functions like `users/fnc.ts`'s `readImageUpload`), then the `createServerFn` exports last — this matches the general "imports, types, consts, functions/constructs last" ordering used everywhere else in this codebase, `fnc.ts` is not a special case. A file that accepts `FormData` as its input (`uploadUserImage` in `users/fnc.ts`) uses a plain function as its `.validator()`, not a zod schema — TanStack Start detects `data instanceof FormData` client-side and sends it as the raw fetch body instead of JSON-serializing it, and hands that same `FormData` instance straight to `.validator()` unparsed server-side (confirmed by reading `server-functions-handler.js`), so the validator does its own `.get()` extraction.

**Every mutating `auth.api.*` call forwards its response headers**, not just Set-Cookie. `src/auth/forward-headers.ts`'s `forwardAuthHeaders(headers)` wraps `setResponseHeaders()` (from `@tanstack/react-start/server`) to propagate the entire header set better-auth returns, not a hand-parsed Set-Cookie subset, since better-auth can set more than one cookie-shaped header on a write. Call the `auth.api.*` method with `returnHeaders: true` and pass its `headers` straight to `forwardAuthHeaders`. Note the response shape changes when `returnHeaders: true` is added: an endpoint that normally returns a real payload gets wrapped as `{ response: T, headers }` (destructure `{ response: { user }, headers: responseHeaders }`), while an endpoint with no meaningful body stays flat as `{ headers }`.

**Every middleware lives in `src/kit/middleware/`, one file per middleware, with its own `index.ts` barrel** (`owner-middleware.ts`: `OwnerMiddleware`, owner only, throws if not; `admin-middleware.ts`: `AdminMiddleware`, owner or admin, throws if not). A middleware that gates access throws inside itself. `assertCanAssignRole` is not here despite being an authorization check too, see above for why (it needs the validated body, so it lives in `kit/shared/` as a plain function instead).

There used to be a third one, `AuthMiddleware` (formerly `auth-middleware.ts`): "any session, and that session's role must be allowed to use this instance" as one combined gate, for a self-service feature to build on. It was removed, no server function ever ended up calling it, and the self-service API-keys feature it was originally built for was removed entirely too. Worth remembering why, if something like it gets rebuilt: it was also briefly used by root's own session fetch (folding the allowed-roles check into one shared gate, reasoning this app has no authenticated-but-unpermitted consumer path to protect), but that broke a genuinely fresh instance: root's `beforeLoad` runs for every route including `/sign-in` and `/setup`, which exist specifically to handle the no-session case, and a middleware throwing a redirect there fired before those routes' own logic (particularly `/setup`'s "is there an owner yet") ever got a chance to run, redirect-looping `/setup` → `/sign-in` → `/setup` forever on an empty database. That's why root's `getSession` (`kit/auth/get-session.ts`) is deliberately non-throwing, just returns the session or `null`, and `_workspace/route.tsx`'s own `beforeLoad` does both checks itself (session presence, then `isAdminTier`) instead of delegating to a shared middleware. A throws-on-no-session contract is only safe for something reached from inside the already-gated dashboard, never for a route's own top-level session fetch.

**Every zod schema lives in the single flat `src/kit/schemas.ts`**, no per-domain files. A `kit/<domain>/*.ts` server function or a form always imports its validator/schema from there rather than declaring one inline; if the same shape needs a client-side form schema and a server-side payload schema, share the one schema unless the two genuinely validate different shapes. `completeSetupSchema` is deliberately just name/email/password/rememberMe, the setup flow used to also collect app name/security/methods/roles through a multi-step wizard with its own separate `wizardSchema`, both are gone, see the `_auth` routing note above for why.

**Every type used from more than one file lives in the single flat `src/kit/types.ts`**, no barrel of per-domain files. A domain type derived from a schema is `z.infer<typeof theSchema>` with the schema imported from `kit/schemas.ts`. For anything that comes back from `auth.api.*`, better-auth's plugins already export fully-typed shapes (`UserWithRole`, `SessionWithImpersonatedBy` from `better-auth/plugins/admin`), use those directly (`export type ListedUser = UserWithRole`) instead of re-deriving through `Awaited<ReturnType<typeof ourTool>>`, but verify the package's type actually matches what the specific endpoint returns first before trusting it blindly. Only fall back to `Awaited<ReturnType<typeof theTool>>` (the tool function imported via `import type` from `@/kit/<domain>`, so it never pulls runtime code into the type-only file) when no single upstream type covers the shape, like `UserDetail` (composite of a user, sessions, and a raw adapter query for linked accounts, from `getUserDetail`) or `UsersListData` (from `listUsers`, reused by the optimistic-update helpers in `kit/hypermedia/users/`). A type that's genuinely internal to one file (a widget's own generic column-def helper type, a route's local form-values type) stays colocated with that file instead of moving here.

**Access model** (`src/auth/permissions.ts`): roles are the fixed three, `owner`/`admin`/`user`, built statically by `buildRoles()` (no args, no KV) and passed to better-auth's `admin` plugin in `src/auth/index.ts`. Dashboard access is owner/admin only, hardcoded, `_workspace/route.tsx`'s `beforeLoad` checks `isAdminTier(session.user.role)` directly and redirects to `/unauthorized` otherwise; the plain `user` role can never sign into the dashboard, full stop, not a configurable instance setting. There used to be a Team & Roles page controlling this (an "allowed roles" list `user` could be added to, and before that, custom roles too) and both were removed entirely, same treatment as API keys and Providers elsewhere in this doc: this is fixed code now, not a setting. Within the dashboard, owner and admin are further distinguished: admin has broad access (add users, view everything, remove any non-owner account) but only owner can promote/demote roles, remove another owner, ban/unban, reset passwords, or impersonate. Add and remove follow the same shape but aren't identical: `kit/hypermedia/users/create-user.ts` lets admin create only `user` accounts (owner can create any role); `remove-user.ts` lets admin remove any account except an owner's (owner can remove anyone but themselves) — so "admin-allowed" is broader for removal than for creation, don't conflate the two checks. `isAdminTier(role)`/`isOwner(role)` (in `permissions.ts`) are the single source of truth for the tier check, used by `AdminMiddleware`/`OwnerMiddleware`/`_workspace/route.tsx` and by the inline checks throughout `features/users/`; never write `role !== "owner" && role !== "admin"` by hand. See `features/users/list-users.tsx` (`canManageRole` vs `canRemove`) and `get-user-detail.tsx` for where that split is enforced in the UI, and `kit/hypermedia/users/` for the same split enforced server-side (never trust the client-side hide alone; `remove-user.ts` re-fetches the target's current role before allowing a non-owner caller to proceed).

One known gap: impersonating anyone with the plain `user` role now lands the owner on `/unauthorized` immediately and unconditionally (`_workspace`'s `beforeLoad` enforces the owner/admin-only check on every dashboard route, including the one impersonation navigates to, and `user` can never pass it), and `/unauthorized` only offers "Sign out", not "stop impersonating", so the owner gets fully signed out rather than dropped back into their own session with one click. Worth fixing if impersonating `user`-role accounts becomes a common flow; today it's a dead end by construction, not just a corner case.

**`src/auth/index.ts` is now entirely static, nothing in this app's auth config is KV-backed anymore.** `appName`, `security`, `roles` (`buildRoles()`, fixed owner/admin/user), and `trustedOrigins`'s suffix list (`env.TRUSTED_ORIGINS`, a Worker var, not KV) are all plain constants or env vars, not `await`ed from anywhere at request or boot time. Sign-in methods (`emailAndPassword` always on, plus `twoFactor`, `username`, `passkey`) are registered unconditionally in the `plugins` array, same as before, just with no toggle UI left to control them (the Providers page that displayed them, and the KV-backed `methods.ts`/`methods-store.ts` behind its toggles, were removed entirely, not just disabled). Dashboard access (owner/admin only) and custom roles were both KV-backed features too (`access-store.ts`, `roles-store.ts`, the Team & Roles page) and were removed the same way; access is now the fixed `isAdminTier` check described in Access model above. Two plugins that existed at various points and were removed entirely: self-service API keys (`apiKey`, its own middleware, functions, hooks, route, schema, types) and magic links (`magicLink`). `anonymous`/`phoneNumber`/`emailOTP` were never built at all, out of scope for this project by default; self-hosters who want any of these back can add the plugin themselves (`better-auth/plugins`, same shape as `twoFactor`/`username`).

**Custom (non-better-auth-shipped) plugins live in `src/auth/plugins/<name>/`**, registered in `auth/index.ts`'s `plugins` array the same way as the shipped ones. Two so far: `objects` (R2 file storage) and `applications` (the applications registry, see below). `objects` (`src/auth/plugins/objects/`): per-user file storage backed by the `STORAGE` R2 binding (`wrangler.jsonc`), one file per concern (`constants.ts` the size/quota/allowlist numbers, `sniff-file-type.ts` magic-byte + heuristic content sniffing, `sanitize-svg.ts` wraps `sanitize-html`, `r2-paths.ts` key layout + `list()`-based usage accounting, `index.ts` the actual endpoints). Two fixed key slots per user: `{userId}/avatar/avatar.{ext}` (exactly one, "replace" means deleting whatever `avatar.*` currently exists, any extension, before writing the new one, so switching formats never leaves an orphan eating quota) and `{userId}/files/{filename}.{ext}` (many, general account documents). Allowlist, not denylist: images (png/webp/jpg/svg) and docs (pdf/json), validated by sniffing the actual bytes, never by trusting the extension or client-declared `Content-Type`, a renamed `.zip` claiming to be `.png` is still rejected. `MAX_FILE_BYTES` (2MB) and `MAX_USER_QUOTA_BYTES` (5MB) in `constants.ts` are the only numbers to touch if these need adjusting; quota usage is computed on demand by listing a user's objects and summing sizes, not tracked in a separate counter, deliberately, so it can never drift from what's actually in the bucket. SVGs are sanitized on upload (`sanitize-svg.ts`, strips `<script>`/event-handler attributes) since an inline-rendered SVG is a real XSS vector otherwise; the tag/attribute allowlist there is case-sensitive against the underlying HTML parser (`sanitize-html`), get `linearGradient`/`radialGradient`/`clipPath`'s casing wrong and the parser silently drops the whole element as "not allowed," it does not lowercase-normalize for you, confirmed by testing against the actual Workers runtime, not assumed. Avatar upload/replace writes directly to better-auth's existing `user.image` field (no new column) with a version-stamped URL (`?v=<timestamp>`) that changes on every replace, that versioning is the entire cache-invalidation strategy: the public `getAvatar` endpoint (`GET /objects/avatar/:userId`, no session required) serves with `Cache-Control: public, max-age=31536000, immutable`, safe only because a given exact URL never changes content once written. One non-obvious better-call detail this plugin hit: `createAuthEndpoint`'s content-type gate defaults to JSON only, `multipart/form-data` needs an explicit `metadata: { allowedMediaTypes: ["multipart/form-data"] }` per endpoint or the framework 415s before your handler ever runs; once allowed, better-call already parses the multipart body into `ctx.body` itself (File values survive intact), there's no need to also read `ctx.request.formData()` by hand. A second one: a plugin factory function must **not** be explicitly typed `(): BetterAuthPlugin`, that widens the return type and erases the specific endpoint keys, so `auth.api.<yourEndpointName>` stops type-checking anywhere else in the app; let TypeScript infer the literal return type instead. The dashboard-facing side is a real folder/file browser, not a "pick a user" list, deliberately: `browseObjects` (`GET /objects/browse?prefix=`, admin-only, distinct from the self-or-admin shape the upload endpoints use) calls `env.STORAGE.list({ prefix, delimiter: "/" })` directly, R2's own mechanism for this (S3-compatible), which returns `delimitedPrefixes` (subfolders one level deeper) separately from `objects` (files at exactly this level) — confirmed against the real local R2 binding, not assumed: at the bucket root that returns one `delimitedPrefixes` entry per user id and zero files, one level into a user id it returns the `avatar/`/`files/` subfolders, one level into `avatar/` it returns the actual file with zero subfolders. `downloadFile` (`GET /objects/download?key=`, admin-only) streams an arbitrary object back by its exact key for the browser to open/download. Both live in `kit/hypermedia/objects/fnc.ts` on the dashboard side (`AdminMiddleware`-gated, matching the plugin's own admin-only check), with `get-browse.ts` (`browseQueryOptions` + `useBrowseObjects`) importing `browseObjects` from `./fnc` the usual way. `features/storage/` is the UI: `index.tsx` owns the current `prefix` string and renders a breadcrumb from its `/`-split segments, `browse-objects.tsx` renders the actual grid (folder tiles navigate deeper by appending the folder's key as the new prefix, file tiles link straight to the download endpoint). Deliberately has zero dependency on the `users` domain, no name/email lookups, no cross-referencing, it's a raw view over what's actually in the bucket, keys and all; user-facing identity lives on the Users page, not here.

**`uploadAvatar` supports admin-on-behalf-of, not just self-service**: the multipart body's `userId` field is optional; omitted (or equal to the caller's own id) it behaves exactly as self-service always has, but a different `userId` requires the caller to be `isAdminTier` (`resolveTargetUserId` in `objects/index.ts`, checked before anything else in the handler) and writes to *that target's* own `{userId}/avatar/...` path and `user.image`, never the caller's. This is what backs the image control on the Users page's existing per-user "Details" panel (`features/users/update-user.tsx`) — there is no separate Profile page, editing your own image is just opening your own row in the Users table, same as editing your own name already worked before this. The client call constructs a `FormData` (`file` + `userId`) and passes it straight through as a server function's `data` argument; TanStack Start detects `data instanceof FormData` client-side and sends it as the raw fetch body instead of JSON-serializing it, and server-side hands that same `FormData` instance straight to `.validator()` unparsed (confirmed by reading `server-functions-handler.js`) — so a FormData-accepting kit action's validator is a plain function that does its own `.get()` extraction (see `uploadUserImage` in `kit/hypermedia/users/fnc.ts`), not a zod schema, zod has nothing to parse against a `FormData` instance's shape.

**Two more admin-only endpoints on the `objects` plugin**: `deleteObject` (`POST /objects/delete`, body `{key}`, one exact-key delete) and `deleteFolder` (`POST /objects/delete-folder`, body `{prefix}`, lists everything under the prefix via the existing `listAllObjects` paginated helper then batch-deletes in chunks of 1000, R2's batch-delete limit). Both are distinct from the older self-service `deleteFile` (caller's own `files/` prefix only, filename-based) — these accept an arbitrary key/prefix because they back the Storage browser's delete buttons, which any admin/owner can fire against any user's files. Wired with no confirmation dialog, firing immediately on click (`features/storage/browse-objects.tsx`); since both delete buttons sit inside an otherwise-clickable tile (folder tiles navigate on click, file tiles are download links), their `onClick` calls `stopPropagation` (and `preventDefault` for the file case, to stop the download link navigating) before firing the mutation.

**`updateUserDetailsSchema` (and `uploadUserImage`) are diff-only, never resend unchanged fields.** `name`/`email` are both optional in the schema (`.refine` just requires at least one present); `features/users/update-user.tsx`'s "Save details" only includes a field in the payload if it actually differs from `viewUser.user`, and `updateUser` (`kit/hypermedia/users/fnc.ts`) only forwards the fields present in `data` into `adminUpdateUser`'s `data` object rather than always sending both. This isn't just a payload-size nicety: better-auth's `adminUpdateUser` already throws `NO_DATA_TO_UPDATE` on an empty `data` object (confirmed live), so it was already built to expect partial patches, sending both fields unconditionally was working around that rather than matching it. Follow the same shape for any future "edit some subset of fields" form; don't reintroduce an always-send-everything payload.

**`kit/hypermedia/stats/`** is the dashboard's "Your business" numbers on `/` (`features/dashboard/business-stats.tsx`): `getStats` (`fnc.ts`) runs two `auth.api.listUsers` calls with `limit: 1` and reads their `total` — one with no filter (all users, "Total users"), one with `filterField: "updatedAt", filterOperator: "gte"` against a 30-day-ago cutoff ("Monthly active users", matching the "Last 30 days" label already in the UI copy). Deliberately goes through `auth.api.listUsers`'s adapter-level `countTotalUsers`, not a raw `env.AUTH_DB.prepare(...)` query, same reasoning as everywhere else in this doc: better-auth already owns the `user` table, a second raw-SQL path to the same data is a way for the two to quietly drift. `updatedAt` is a proxy for "active," not a real activity log (this project has no session-activity table, sessions live in KV via `secondaryStorage`, not queryable via SQL) — a user who never touched their profile but logs in daily wouldn't show as active by this measure. Acceptable given the "never exceed the free plan" constraint (a proper activity table was explicitly designed and shelved, see the on-hold Logs discussion), not a bug to silently fix later without revisiting that trade-off.

**Applications ("Database" page, `/database`) — the first piece of a deliberately narrow "apps" platform.** Scope was explicitly bounded through discussion before any code: this instance never hosts, proxies, or stores a connected application's actual data or execution, only *config/metadata about* it (App Check-equivalent identity, security rules, remote config, webhooks — only the first is built so far). `src/auth/plugins/applications/` is the plugin (`schema.ts` declares the `application` model via the same plugin-schema mechanism `twoFactor`/`admin` use — confirmed by reading `better-auth/dist/plugins/two-factor/schema.mjs` — so it rides the existing migration flow, no separate migration system). One non-obvious gotcha hit here: **a plugin-added model gets no automatic `id`/`createdAt`/`updatedAt` columns** (only better-auth's own core models do) — confirmed by inspecting the actual generated D1 table twice, once without and once with them explicitly declared (`type: "date"`, `defaultValue: () => new Date()`, `onUpdate: () => new Date()` for `updatedAt`); if a future plugin schema needs timestamps, declare them, don't assume they show up for free.

**Identity model: SSH-deploy-key style, not a shared secret.** A connecting application generates its own ECDSA P-256 keypair locally and only ever sends the **public** key (`registerApplicationKey`, `POST /applications/register`) — the private key never crosses the network, so even a leaked database can't be used to forge a signature. Bootstrapping that (there's no way to authenticate the *first* "here's my public key" call with public-key crypto alone) uses a one-time registration secret generated at `createApplication` time, hashed with plain SHA-256 (`secret.ts`'s `hashSecret`, via `crypto.subtle.digest`) rather than the project's slow PBKDF2 `password.ts` hasher — deliberately, a random 40-character secret is already high-entropy and doesn't need defending against brute-force the way a human password does. The secret is single-use: `registerApplicationKey`'s `adapter.update` uses `{identifier, registrationSecretHash}` as **both** the selector and the value-guard in its `where` clause, so a second call presenting an already-consumed secret matches zero rows and gets rejected — not the fully race-safe `consumeOne` primitive (that deletes the whole row, wrong here since the app row needs to survive with its new public key), but an accepted simplification since the only party who could race a legitimate app's registration is itself, not an attacker without the secret. `verify-signature.ts`'s `verifyApplicationSignature` (ECDSA/SHA-256 via `crypto.subtle.verify`, confirmed against the real Workers runtime with an actual generated keypair, not assumed) is the primitive future app-facing features (remote config, webhooks, App Check) will authenticate against — built now, not wired to any consuming endpoint yet.

**`identifier` is the app's one canonical name, generated (not app-chosen) at creation from a slugified `name`, collision-resolved with a numeric suffix loop** (`Second App` → `second-app`, a second app with the same name → `second-app-2`, confirmed live). It's immutable, and it's used identically everywhere: the URL segment, the `infraConfig` snippet a developer pastes into their app, and — once any future endpoint actually enforces it — the pinned value a signed request's claimed identity gets checked against. `active` (admin kill-switch) and `status` (`unverified | verified | locked`, the crypto verification state) are deliberately independent fields — a verified app can still be disabled, and a freshly-created unverified app is still `active` by default.

**Every raw `adapter.*` call on a custom model bypasses the schema's `returned: false`.** That flag is only honored by better-auth's own output-parsing for core models (user/session/etc.); a plugin querying its own custom table via `ctx.context.adapter` gets the field back regardless, confirmed live (an early version of `createApplication` leaked `registrationSecretHash` — the hash, not the plaintext secret, but still wrong — in its response). `listApplications` avoids this with an explicit `select` list; every other endpoint that returns a full row runs it through `index.ts`'s `redactApplication` first. Any new endpoint returning a custom-model row needs to make its own call on which fields are safe to expose — nothing does it automatically.

**`features/database/`** is a flat set of pieces composed directly by `routes/_workspace/database.tsx`'s `RouteComponent` (which owns the create-dialog/detail-drawer open state and the "Add application" button itself, per the route-is-the-page convention above): `list-applications.tsx` is the `DataTable` (status shown as a colored dot — green `verified`, red `unverified`, amber `locked` — plus the active/disabled badge), `create-application.tsx` is a two-phase dialog (name/identifier/type form, then a one-time reveal of the secret and a copyable `infraConfig` snippet — the secret is never shown again after this), `get-application-detail.tsx` is the per-app drawer. The identifier field in `create-application.tsx` auto-fills from the name (slugified client-side, a duplicate of `identifier.ts`'s `slugify` kept local rather than imported, so server-only plugin code never ends up in the client bundle) but stays editable until the admin picks their own — once they type into it directly, auto-sync stops. This is a management surface for the owner/admin, not an end-user product, so the detail drawer leans toward showing more rather than hiding: the identifier (copyable), the raw ID, `createdBy`, both timestamps, and — since a public key is not a secret, unlike the registration token — the actual registered public key once one exists, or an explicit "not yet connected" state when one doesn't. Logo upload reuses the same "click avatar to change" control built for `features/users/update-user.tsx`; rotate-secret gets its own one-time reveal, same pattern as create. `features/dashboard/application-grid.tsx` is the compact summary on the index page (`/`) — logo, name, identifier, type, status — that links into `/database` for actual management, the same relationship the index page's business-stats card has to the full pages elsewhere.

**The dashboard's own sign-in (`Login`, `src/features/auth/login.tsx`) is email+password only, always**, regardless of which other methods exist. Those methods (twoFactor as a second factor aside) exist for a future consumer-facing sign-in flow this project doesn't build yet, not for the admin dashboard: owner/admin access can never depend on a method, so it isn't given the choice. Don't add conditional rendering of passkey/username options to this form without deciding that trade-off deliberately first.

**Anonymous, phone number, and email OTP sign-in are not implemented at all** (removed from `AUTH_METHODS`, no plugin imports in `src/auth/index.ts`), unlike the methods above which are built but toggleable. This is a deliberate scope decision, not a gap: this project ships a smaller, curated set of methods and expects anyone self-hosting who wants one of these back to add the plugin themselves (`better-auth/plugins`' `anonymous`/`phoneNumber`/`emailOTP`, same shape as the methods still here), rather than the project carrying every better-auth plugin by default.

**Widgets, the only reusable pieces meant to be imported from anywhere, live in `components/widgets/`:**
- `widgets/tables/`: `DataTable` (search, per-column filters auto-detected from data shape, column visibility, sort, row selection + bulk actions, pagination, built on `@tanstack/react-table` v9's real API, not the deprecated `filterFns`/`sortFns` aggregate exports) and `DataTablePagination`. `aria-label` is a **required** prop (react-aria's underlying grid throws a dev warning without one, don't make it optional again).
- `widgets/blocks/`: the `useAppForm`/`withForm` TanStack Form setup (field components, submit button) used by every form in the app (sign-in, setup).
- `widgets/dialog-widget/`: `DialogWidget`, the one entry point for a drawer-style dialog (title/description/children/footer in, `Drawer`/`DrawerContent`/`DrawerHeader` wiring hidden).

Feature-specific things that use a widget but aren't reusable themselves (e.g. `UserDetailDrawer`) live in `components/dashboard/<feature>/`, not in `widgets/`.

**UI components follow shadcn's `aria-lyra` style** (`components.json`): built on `react-aria-components`, not Radix. **Never hand-author a file under `components/ui/`**, always `bunx shadcn add <component>`. The generated API (prop names, which sub-component wraps what) frequently differs from shadcn's default/Radix registry and from what you'd guess, e.g. `DropdownMenuTrigger` is the *root* wrapping both the trigger element and `DropdownMenu` (the content), not just the trigger button. When adding shadcn components, they land under `@/components/ui` per the aliases in `components.json` (`baseColor: olive`, icon library: `tabler`).

**Dates go through `date-fns`** (already a dependency), not `Date.prototype.toLocaleString`/`toLocaleDateString`. See any `*-columns.tsx` file for the `format(date, "PPP")` convention.

**Styling is Tailwind v4, CSS-first.** There is no `tailwind.config.js`; theme tokens, the `container` utility, and custom utilities (`no-scrollbar`, `dualTone`) are all defined in `src/styles/globals.css` via `@theme inline` and `@utility`. Colors are OKLCH and swap via a `.dark` class selector (see the `@custom-variant dark` line), even though the app is currently forced dark. `src/styles/typeset.css` holds prose/typography rules and is imported into `globals.css`.

**Path alias**: `@/*` maps to `src/*` (set in both `tsconfig.json` and consumed via `vite-tsconfig-paths` through `resolve.tsconfigPaths` in `vite.config.ts`).

**Responsive breakpoints diverge from Tailwind's defaults**: `src/lib/use-media-query.ts` defines its own `BREAKPOINTS` map (`md: 800`, plus `3xl: 1600` / `4xl: 2000` beyond Tailwind's stock scale) for the `useMediaQuery`/`useIsMobile` hooks, used for JS-driven layout decisions (e.g. the sidebar in `Dashboard`). `useIsMobile` itself is hardcoded to `(max-width: 768px)` rather than using the `md` entry from that same map, be aware of this mismatch if you touch mobile breakpoint logic.

## Known issues / cleanup backlog

Flagged but not yet done, read before assuming either is already handled:

- **`bun run dev` disables the Cloudflare Vite plugin's local AI-agent observability capture** (`X_LOCAL_OBSERVABILITY=false` in the `dev` script in `package.json`). This is deliberate, not an oversight: when the plugin detects it's running inside an AI coding agent (env vars like `CLAUDECODE`), it defaults to capturing every internal sub-operation, KV calls, D1 calls, and every internal module fetch during SSR, as a span in a local SQLite-backed store queryable at `/cdn-cgi/local/explorer/api/local/observability/query`. In practice this generated over 150,000 spans in about 20 minutes of normal interactive use (one single request's internal module loading alone produced 631 sub-spans), and the capture overhead was severe enough to make requests hang indefinitely (never erroring, never responding) once enough had accumulated, looking like the whole app had frozen. Idle time produces zero span growth, it's purely tied to request volume, so this reliably got worse the longer a session stayed open and the more it was used, and reproduced identically across multiple clean restarts regardless of what application code had most recently changed. This env var only controls the Vite plugin's Node-side local dev tooling (`X_LOCAL_EXPLORER`/`X_LOCAL_OBSERVABILITY`, both default `true` under an agent session), it's unrelated to and doesn't touch `wrangler.jsonc`'s `observability` block, which governs the real deployed Worker and is untouched. If a future debugging session needs that local trace/log capture back, run `X_LOCAL_OBSERVABILITY=true vite dev --port=3000` directly instead of `bun run dev`, understanding it will likely reproduce the same freeze if left running for a while under load.
