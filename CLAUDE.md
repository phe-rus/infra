# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Pherus: a self-hosted authentication backend (better-auth, on Cloudflare Workers + D1 + KV) plus "Infra", the admin dashboard for the person running the instance. One TanStack Start (React 19 + SSR) app, one Worker, serving both the dashboard UI and better-auth's HTTP API. See `README.md` for the product-level aim and approach — this file is the technical map.

Package manager: **bun** (`bun.lock` is the lockfile; `.vscode/settings.json` pins `npm.packageManager` to `bun`).

## Commands

```bash
bun install       # install dependencies
bun run dev       # start dev server on port 3000
bun run build     # production build (vite build)
bun run preview   # preview a production build
bun run test      # run the vitest suite once (vitest run)
bun run lint      # eslint
bun run format    # prettier --write across ts/tsx/js/jsx
bun run check     # prettier --check (no writes)
bun run typecheck # tsc --noEmit
```

There are no test files in the repo yet and no `vitest.config.*` — vitest currently runs against Vite's default config. When adding tests, run a single file with `bunx vitest run path/to/file.test.tsx` or a single test name with `bunx vitest run -t "test name"`.

## Architecture

**Routing is file-based and code-generated.** Routes live under `src/routes/`; `src/routeTree.gen.ts` is auto-generated by the `@tanstack/router-plugin` Vite plugin on dev/build — never hand-edit it (it's marked read-only in `.vscode/settings.json`). Three pathless layout routes sit at the top level:
- `_auth` (`src/routes/_auth/route.tsx`) — `sign-in` and `setup`; redirects away if a session already exists.
- `_workspace` (`src/routes/_workspace/route.tsx`) — everything behind the dashboard shell. `beforeLoad` does two checks in order: is there a session (else redirect to `/sign-in`), then is this session's role allowed to access the instance at all (else redirect to `/unauthorized`) — see **Access model** below.
- `_protected` (`src/routes/_protected/route.tsx`) — just `unauthorized.tsx` today; deliberately outside `_workspace` so it renders without the `Dashboard` shell (someone who lands here isn't authorized to see it).

Current `_workspace` pages: `index` (home), `providers` (sign-in methods + security settings), `team-roles` (role definitions + instance access), `users` (member management), `api-keys` (self-service API keys). `database`/`storage`/`api-keys`-adjacent/`environment-variables`/`logs`/`billing` exist as sidebar links in `Dashboard` with no route behind them yet.

**A route file's job is `Route` + its `component`, nothing else.** Loader logic, `beforeLoad` guards, and the top-level component belong in the route file; anything reusable across pages (a form field, a table, a drawer) does not — it lives under `components/widgets/` (generic) or `components/dashboard/<feature>/` (feature-specific, e.g. `components/dashboard/users/users-columns.tsx`), and the route imports it. Route files should stay readable as "what does this page load, guard, and render," not accumulate one-off UI logic.

**Shell / entry points**: `src/start.ts` creates the TanStack Start server instance and registers CSRF middleware scoped only to server-function requests. `src/router.tsx` builds the router and wraps it with `QueryProvider`. `src/routes/__root.tsx` renders the actual `<html>` document (theme is hardcoded to `dark` via a static class, not runtime-toggled), does the root `beforeLoad` (session + setup status, see below), and mounts `TanStackDevtools`.

**Query client is a client/server-aware singleton** (`src/lib/queryClient.tsx`): on the client, `getContext()` reuses one module-level `QueryClient` across navigations; on the server it always constructs a fresh one per request (standard SSR-safe pattern — don't change this to a plain module-level singleton, it would leak state across requests). The `QueryProvider` unconditionally mounts `TanStackDevtools` (Router + Query panels) — it is not gated behind a dev/prod check, so don't add one without checking whether that's intentional for this project.

**Errors surface as toasts globally**: the `QueryCache` in `queryClient.tsx` has an `onError` that calls `t.error(...)` (from `@/components/ui/sonner`, backed by `goey-toast`) for every failed query except `AbortError`. Individual query hooks generally don't need their own error handling/toast logic — it happens centrally for queries; mutations still set their own success/error toasts (see any `use*Hooks.ts` file).

**Data flow: loader `ensureQueryData` + `useSuspenseQuery`, not `Route.useLoaderData()`, for anything a mutation can change.** The loader prefetches into the query cache so SSR/first paint has data; the component then subscribes via `useSuspenseQuery(sameQueryOptions())` so that a mutation's `invalidateQueries` actually triggers a re-render. `Route.useLoaderData()` is a one-time snapshot — fine for values a form seeds itself with once (e.g. a settings form's `defaultValues`) and forgets about, wrong for anything meant to stay live (a table of users, a list of API keys).

**Server functions live in `src/functions/*Fn.ts`**, one file per domain (`usersFn.ts`, `apiKeysFn.ts`, `rolesFn.ts`, `settingsFn.ts`, `authFn.ts`, `setupFn.ts`). Each exports the `createServerFn(...)` calls plus a matching `*QueryOptions()` helper for use with `useSuspenseQuery`/`ensureQueryData`. Auth/role gating goes through `src/functions/protectionFn.ts`'s three middlewares — `AuthMiddleware` (any session, `context.sessions` may be null), `OwnerMiddleware` (owner only, throws if not), `AdminMiddleware` (owner or admin, throws if not). **Inside a handler that needs the request's headers for an `auth.api.*` call, use `getRequestHeaders()` from `@tanstack/react-start/server`** (synchronous — no `await`), assigned to its own `const headers = getRequestHeaders()` line, not called inline in the call args. Middleware bodies, by contrast, already receive `request` as a parameter from the framework and should use `request.headers` directly rather than also calling `getRequestHeaders()` — don't thread `headers` through middleware `context` for handlers to consume; every handler that needs it calls the utility itself.

**Access model** (`src/auth/permissions.ts`, `src/auth/settings/access-store.ts`, `src/functions/rolesFn.ts`): owner and admin can always sign into the dashboard. Every other role — the fixed `user` role and any custom role — needs to be explicitly added to the "allowed roles" list on the Teams & roles page before its holders can get past `_workspace`'s `beforeLoad`; `isRoleAllowed(role, allowedRoles)` is the single source of truth for that check, called both there and (implicitly, by not being needed) nowhere else — don't duplicate the check inline. Within the dashboard, owner and admin are further distinguished: admin has broad access (add users, view everything) but only owner can promote/demote roles, remove accounts, ban/unban, reset passwords, or impersonate — see `getUsersColumns`/`UserDetailDrawer` for where that split is enforced, and `usersFn.ts`/`apiKeysFn.ts` for the same split enforced server-side (never trust the client-side hide).

**Custom roles** (`src/auth/settings/roles-store.ts`) are stored as a flat list in KV and fed into better-auth's `admin` plugin (`buildRoles` in `permissions.ts`) at boot — changes take effect on the instance's next restart, not immediately, which is why every settings-save toast in this app says so.

**Widgets — the only reusable pieces meant to be imported from anywhere** live in `components/widgets/`:
- `widgets/tables/` — `DataTable` (search, per-column filters auto-detected from data shape, column visibility, sort, row selection + bulk actions, pagination — built on `@tanstack/react-table` v9's real API, not the deprecated `filterFns`/`sortFns` aggregate exports) and `DataTablePagination`. `aria-label` is a **required** prop (react-aria's underlying grid throws a dev warning without one — don't make it optional again).
- `widgets/blocks/` — the `useAppForm`/`withForm` TanStack Form setup (field components, submit button) used by every form in the app (setup wizard, providers, team-roles).
- `widgets/dialog-widget/` — `DialogWidget`, the one entry point for a drawer-style dialog (title/description/children/footer in, `Drawer`/`DrawerContent`/`DrawerHeader` wiring hidden).

Feature-specific things that use a widget but aren't reusable themselves (e.g. `getUsersColumns`, `UserDetailDrawer`, `getApiKeyColumns`) live in `components/dashboard/<feature>/`, not in `widgets/`.

**UI components follow shadcn's `aria-lyra` style** (`components.json`): built on `react-aria-components`, not Radix. **Never hand-author a file under `components/ui/`** — always `bunx shadcn add <component>`; the generated API (prop names, which sub-component wraps what) frequently differs from shadcn's default/Radix registry and from what you'd guess, e.g. `DropdownMenuTrigger` is the *root* wrapping both the trigger element and `DropdownMenu` (the content), not just the trigger button. When adding shadcn components, they land under `@/components/ui` per the aliases in `components.json` (`baseColor: olive`, icon library: `tabler`).

**Dates go through `date-fns`** (already a dependency), not `Date.prototype.toLocaleString`/`toLocaleDateString` — see any `*-columns.tsx` file for the `format(date, "PPP")` convention.

**Styling is Tailwind v4, CSS-first** — there is no `tailwind.config.js`; theme tokens, the `container` utility, and custom utilities (`no-scrollbar`, `dualTone`) are all defined in `src/styles/globals.css` via `@theme inline` and `@utility`. Colors are OKLCH and swap via a `.dark` class selector (see the `@custom-variant dark` line), even though the app is currently forced dark. `src/styles/typeset.css` holds prose/typography rules and is imported into `globals.css`.

**Path alias**: `@/*` maps to `src/*` (set in both `tsconfig.json` and consumed via `vite-tsconfig-paths` through `resolve.tsconfigPaths` in `vite.config.ts`).

**Responsive breakpoints diverge from Tailwind's defaults**: `src/lib/use-media-query.ts` defines its own `BREAKPOINTS` map (`md: 800`, plus `3xl: 1600` / `4xl: 2000` beyond Tailwind's stock scale) for the `useMediaQuery`/`useIsMobile` hooks, used for JS-driven layout decisions (e.g. the sidebar in `Dashboard`). `useIsMobile` itself is hardcoded to `(max-width: 768px)` rather than using the `md` entry from that same map — be aware of this mismatch if you touch mobile breakpoint logic.

## Lint/format notes

- `eslint.config.js` extends `@tanstack/eslint-config` but turns off `import/no-cycle`, `import/order`, `sort-imports`, `@typescript-eslint/array-type`, `@typescript-eslint/require-await`, and `pnpm/json-enforce-catalog` — don't reintroduce those as expectations when reviewing code.
- `bun run lint` currently fails outright (`typescript-eslint does not support TS 7.0`) — a version mismatch between the installed TypeScript and `typescript-eslint`, unrelated to any specific change. Don't treat a lint failure as caused by your edit without checking it's not just this.
- Prettier (`.prettierrc`): no semicolons, double quotes, `prettier-plugin-tailwindcss` for class sorting. Its `tailwindStylesheet` option points at `src/styles.css`, which does not exist (the real stylesheet is `src/styles/globals.css`) — this looks like a stale path from before the styles were moved into `src/styles/`; `bun run format`/`check` currently error on this rather than just skipping class-sorting. Needs fixing before either command is usable.

## Known issues / cleanup backlog

Flagged but not yet done — read before assuming either is already handled:

- **Zod schemas are inline in every `*Fn.ts` file** (`createUserSchema`, `banUserSchema`, `setUserRoleSchema`, etc., each private to its file). The intent going forward is a top-level `schemas/` folder, one place to find every input schema, instead of them being scattered one-per-server-function.
- **Shared types are inline/exported ad hoc** (`ListedUser`, `ApiKey`, `UserDetail`, `CustomRole`, etc., each defined next to the server function that happens to need it first, e.g. `export type ListedUser = Awaited<ReturnType<typeof listUsersFn>>["users"][number]` in `usersFn.ts`). The intent is a top-level `types/` folder for anything used across more than one file, instead of hunting through function files to find a type's origin.
- **Possible redundant network calls, not yet audited.** Root `beforeLoad` fetches session + setup-status on every navigation; `_workspace`'s `beforeLoad` fetches allowed-roles on top of that; individual pages (`users.tsx`, `api-keys.tsx`) do their own inline role check again against `context.user.role` before rendering. Each layer exists for a real reason (defense in depth: client guard + server middleware both check role since the client check alone isn't trustworthy), but nobody has gone through with a network tab and confirmed there's no accidental double-fetch of the same query, or collapsed the repeated `role !== "owner" && role !== "admin"` checks into one shared helper instead of copy-pasted per file.
- **An "aria-label or aria-labelledby prop is required" console warning attributed to `__root.tsx`** was seen but not conclusively traced — `__root.tsx` itself has no unlabeled interactive elements; the most likely source is inside `TanStackDevtools`' own UI (third-party, always-mounted per the note above), but that hasn't been confirmed by isolating it (e.g. temporarily unmounting `TanStackDevtools` and checking if the warning disappears). If you hit this again, check there first before assuming it's app code.
- **`getUsersColumns` and `getApiKeyColumns` duplicate structure** (both build a select checkbox, a dropdown-menu actions column, similar owner/self-guard logic) that could likely share more than they currently do.
