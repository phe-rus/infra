# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

This repo is both a self-hosted authentication backend (better-auth, on Cloudflare Workers + D1 + KV) and its admin dashboard: one TanStack Start (React 19 + SSR) app, one Worker, serving both the dashboard UI and better-auth's HTTP API. See `README.md` for what the project is and why it exists; this file is the technical map.

Package manager: **bun** (`bun.lock` is the lockfile; `.vscode/settings.json` pins `npm.packageManager` to `bun`).

## Commands

```bash
bun install       # install dependencies
bun run dev       # start dev server on port 3000
bun run build     # production build (vite build)
bun run preview   # preview a production build
bun run test      # run the vitest suite once (vitest run)
bun run lint      # eslint
bun run format    # prettier --write across ts/tsx/js/jsx
bun run check     # prettier --check (no writes)
bun run typecheck # tsc --noEmit
```

There are no test files in the repo yet and no `vitest.config.*`, vitest currently runs against Vite's default config. When adding tests, run a single file with `bunx vitest run path/to/file.test.tsx` or a single test name with `bunx vitest run -t "test name"`.

## Architecture

**Routing is file-based and code-generated.** Routes live under `src/routes/`; `src/routeTree.gen.ts` is auto-generated by the `@tanstack/router-plugin` Vite plugin on dev/build, never hand-edit it (it's marked read-only in `.vscode/settings.json`). Three pathless layout routes sit at the top level:
- `_auth` (`src/routes/_auth/route.tsx`): `sign-in` and `setup`, redirects away if a session already exists. `setup` is two phases in one route file, not a multi-step wizard: initialize (runs migrations, mandatory before an owner can exist, `runSetupMigrations`) then create the owner account (name/email/password only). Nothing else gets collected here, app name/security/email-verification/sign-in methods/custom roles all have sensible defaults the moment KV has never been written to (see each `src/auth/settings/*.ts` getter) and stay editable afterward from the dashboard's own Settings/Providers/Team & roles pages. An earlier five-step wizard (`components/auth/setup/`) collected all of that upfront; it was deleted, not because the settings don't matter, but because forcing them into a one-time form added friction for zero benefit over just defaulting sensibly and letting an owner change them whenever.
- `_workspace` (`src/routes/_workspace/route.tsx`): everything behind the dashboard shell. `beforeLoad` does two checks in order: is there a session (else redirect to `/sign-in`), then is this session's role allowed to access the instance at all (else redirect to `/unauthorized`), see **Access model** below. Root's own session fetch (`getSession` in `authFn.ts`) is deliberately non-throwing, it runs for every route including `/sign-in`/`/setup`, which exist to handle the no-session case, so this is the layout where "you actually need a session" gets enforced, not root.
- `_protected` (`src/routes/_protected/route.tsx`): just `unauthorized.tsx` today, deliberately outside `_workspace` so it renders without the `Dashboard` shell (someone who lands here isn't authorized to see it).

Current `_workspace` pages: `index` (home), `providers` (sign-in methods + security settings), `team-roles` (role definitions + instance access), `users` (member management), `api-keys` (self-service API keys). `database`/`storage`/`environment-variables`/`logs`/`billing` exist as sidebar links in `Dashboard` with no route behind them yet.

**A route file's job is `Route` + one `RouteComponent`, and everything the page needs lives inside that single function.** Column definitions for a `DataTable`, an add-item form, per-row actions: all of it is written directly inside `RouteComponent` (state, handlers, and the `useMemo(() => [...], [])`-wrapped column array all in one place), not split into a separate `get*Columns()` factory or a page-specific sub-component file. This was tried the other way (a `components/dashboard/<feature>/*-columns.tsx` file per page) and reverted: those files existed to satisfy an abstraction, not because anything else imported them. See `users.tsx`/`api-keys.tsx`/`team-roles.tsx` for the current shape.

The one real exception is something genuinely reused by more than one call site. `components/widgets/` holds pieces reusable from anywhere (`DataTable`, the `useAppForm` blocks setup, `DialogWidget`), always imported, never inlined. `components/dashboard/` currently holds only the `Dashboard` shell itself, both `UserDetailDrawer` and `RevealApiKeyDialog` were later inlined into `users.tsx`/`api-keys.tsx` too, on the reasoning that a single-caller dialog is still easier to debug inline than jumped-to; that's a judgment call on size and reuse, not a hard rule, but when in doubt, inline it into the route first.

**Shell / entry points**: `src/start.ts` creates the TanStack Start server instance and registers CSRF middleware scoped only to server-function requests. `src/router.tsx` builds the router and wraps it with `QueryProvider`. `src/routes/__root.tsx` renders the actual `<html>` document (theme is hardcoded to `dark` via a static class, not runtime-toggled), does the root `beforeLoad` (session + setup status, see below), and mounts `TanStackDevtools`.

**Query client is a client/server-aware singleton** (`src/lib/queryClient.tsx`): on the client, `getContext()` reuses one module-level `QueryClient` across navigations; on the server it always constructs a fresh one per request (standard SSR-safe pattern, don't change this to a plain module-level singleton, it would leak state across requests). The `QueryProvider` unconditionally mounts `TanStackDevtools` (Router + Query panels). It is not gated behind a dev/prod check, so don't add one without checking whether that's intentional for this project.

**`queryClient.tsx` overrides `focusManager` to always report focused**, plus `queries.networkMode: 'always'` and a fixed `retryDelay: 1000`, none of which are the defaults. React-query's retryer pauses a scheduled **query** retry (this does not apply to mutations, they default to `retry: 0` here and none of the domain hooks override that, so this whole override has no effect on mutation behavior) whenever the tab isn't visible (`document.visibilityState`, via `focusManager`) or (with the default `networkMode`) offline, and a paused retry only resumes on the next focus/online event, which can leave a query stuck "pending" indefinitely if the tab stays backgrounded, showing as a stuck loading spinner rather than an error, since pending is not rejected, so it never reaches the error boundary. The `focusManager.setEventListener` override removes the visibility-based pause path entirely (it always reports focused, so that check never fails); `networkMode: 'always'` removes the online-check path the same way, this app has no offline use case; the fixed 1s `retryDelay` (instead of default exponential backoff up to 30s) means a retry is also more likely to simply complete before anything else interrupts it. The deliberate trade-off: `refetchOnWindowFocus` is now inert app-wide (same underlying `focusManager` event, which no longer fires on real visibility changes), no more automatic refetch when returning to a tab, acceptable here since every mutation already invalidates its own affected queries explicitly. If you ever need real refetch-on-focus back, that override is the first thing to remove. Note this override alone does not prevent a query from hanging, a paused retry only happens *after* a rejection, an unbounded `fetch()` that never resolves or rejects at all bypasses retry logic entirely, that's what `withTimeout` (below) actually guards against.

**Errors surface as toasts globally**: the `QueryCache` in `queryClient.tsx` has an `onError` that calls `t.error(...)` (from `@/components/ui/sonner`, backed by `goey-toast`) for every failed query except `AbortError`. Individual query hooks generally don't need their own error handling/toast logic for reads, it happens centrally.

**Every mutation hook builds on `useAppMutation` (`src/hooks/useAppMutation.ts`)** instead of calling `useMutation` directly. It reads the query client via `useQueryClient()` (React context, the same instance every `useSuspenseQuery` in the tree reads from) rather than each hook grabbing its own reference, takes an `invalidates` array of query keys and fires `invalidateQueries` for each one in `onSettled` (not awaited, callers don't need to see the refetch land before `mutateAsync` resolves), and applies the standard success/error toast pair from `successMessage`/`successDescription`/`errorMessage` so a hook only states its own keys and copy. `optimisticUpdate`'s `cancelQueries` call in `onMutate` **is** awaited, matching the documented react-query pattern (narrows the window where an in-flight refetch could land after the optimistic write and clobber it); an earlier version of this hook made it non-awaited chasing a "hang" theory that turned out to be wrong (confirmed by reading `query-core`'s `retryer.ts` directly: `cancelQueries` rejects synchronously, it can't hang `onMutate`). The actual thing that could hang a mutation or query forever is an unbounded `fetch()` inside the `mutationFn`/`queryFn` itself, that's what `withTimeout` (above) exists to bound, not anything in this hook's callbacks. The optimistic rollback in `onError` only restores the pre-mutation snapshot if the cache still holds exactly what this mutation wrote, skipping it if a second mutation on the same key wrote something newer in the meantime, otherwise the rollback would silently erase that concurrent change. See any `use*Hooks.ts` file for the shape. The exceptions are sign-in/sign-out/impersonation/complete-setup in `authHooks.ts`/`usersHooks.ts`/`setupHooks.ts`, which swap out the session identity entirely and need `q.clear()` plus a navigation rather than a targeted invalidate, so they still call `useMutation` directly against the module-level `getContext()` client (but their `mutationFn` is still wrapped in `withTimeout`, same as everything else).

**Data flow: loader `ensureQueryData` + `useSuspenseQuery`, not `Route.useLoaderData()`, for anything a mutation can change.** The loader prefetches into the query cache so SSR/first paint has data; the component then subscribes via `useSuspenseQuery(sameQueryOptions())` so that a mutation's `invalidateQueries` actually triggers a re-render. `Route.useLoaderData()` is a one-time snapshot, fine for values a form seeds itself with once (e.g. a settings form's `defaultValues`) and forgets about, wrong for anything meant to stay live (a table of users, a list of API keys).

**Server functions live in `src/functions/*Fn.ts`**, one file per domain (`usersFn.ts`, `apiKeysFn.ts`, `rolesFn.ts`, `settingsFn.ts`, `instanceFn.ts`, `authFn.ts`, `setupFn.ts`), and export only the `createServerFn(...)` calls, nothing query-shaped. Inside a handler that needs the request's headers for an `auth.api.*` call, use `getRequestHeaders()` from `@tanstack/react-start/server` (synchronous, no `await`), assigned to its own `const headers = getRequestHeaders()` line, not called inline in the call args. Middleware bodies, by contrast, already receive `request` as a parameter from the framework and should use `request.headers` directly rather than also calling `getRequestHeaders()`. Don't thread `headers` through middleware `context` for handlers to consume; every handler that needs it calls the utility itself. A handler gated by `AuthMiddleware`/`AdminMiddleware`/`OwnerMiddleware` never re-checks `if (!sessions)`, the middleware already guarantees a session (and, for Admin/Owner, the required role tier) before the handler runs; re-checking is dead code.

**`*QueryOptions()` helpers live in `src/hooks/*Hooks.ts`**, one file per domain, matching the `*Fn.ts` files (`apiKeysQueryOptions` in `apiKeysHooks.ts`, `usersQueryOptions`/`userDetailQueryOptions` in `usersHooks.ts`, and so on), not in the `*Fn.ts` files themselves. A `*QueryOptions()` factory is a client-side React Query construct built around a server function, not part of the server function's own definition, so it belongs next to the hooks that consume it. Route loaders and components import query options from `@/hooks/*Hooks`, never from `@/functions/*Fn`.

**Every `queryFn`/`mutationFn` that calls a server function goes through `withTimeout` (`src/lib/with-timeout.ts`)**, e.g. `queryFn: () => withTimeout(listUsersFn)()`, `mutationFn: withTimeout(createApiKeyFn)`. It wraps the function so every call gets an `AbortSignal.timeout(15000)` (30s for `completeSetup`, which bundles several sequential writes). A plain `fetch()` has no default timeout, and the local dev runtime has, under load, accepted a request and never responded to it at all, neither resolving nor rejecting. react-query's `isPending` only flips to `false` once the `mutationFn`/`queryFn` promise itself settles (confirmed by reading `query-core`'s `Mutation.execute()` directly, not just docs), so an unbounded fetch is the one thing that can genuinely hang a query or mutation forever, no callback-level fix (`onMutate`/`onSuccess`/`onSettled` tuning) touches this, they only run after the fetch has already settled. Every new server-function call site added to a `*Hooks.ts` file needs this wrapper, it's easy to forget since the code still typechecks and mostly works without it.

**Every mutating `auth.api.*` call forwards its response headers**, not just Set-Cookie. `src/auth/forward-headers.ts`'s `forwardAuthHeaders(headers)` wraps `setResponseHeaders()` (from `@tanstack/react-start/server`) to propagate the entire header set better-auth returns, not a hand-parsed Set-Cookie subset, since better-auth can set more than one cookie-shaped header on a write. Call the `auth.api.*` method with `returnHeaders: true` and pass its `headers` straight to `forwardAuthHeaders`. Note the response shape changes when `returnHeaders: true` is added: an endpoint that normally returns a real payload gets wrapped as `{ response: T, headers }` (destructure `{ response: { user }, headers: responseHeaders }`), while an endpoint with no meaningful body stays flat as `{ headers }`.

**Every middleware lives in `src/middleware/`, one file per middleware** (`auth-middleware.ts`: `AuthMiddleware`, requires a session AND that the session's role is allowed to use this instance (`isRoleAllowed`), redirects to `/sign-in` or `/unauthorized` otherwise, `context.sessions` is never null past this point; `owner-middleware.ts`: `OwnerMiddleware`, owner only, throws if not; `admin-middleware.ts`: `AdminMiddleware`, owner or admin, throws if not; `apikey-middleware.ts`: `ApiKeyEnabledMiddleware`, puts `context.apiKeyEnabled` from the settings store, doesn't throw, each handler decides what disabled means for it). A middleware that gates access throws inside itself; a middleware that just informs a decision (like `ApiKeyEnabledMiddleware`) puts a value in context and leaves the throw/fallback choice to the handler.

`AuthMiddleware` is only used by `apiKeysFn.ts` now, not by root's own session fetch. It was briefly used there too (folding the allowed-roles check into one shared "do you have a session and is it allowed" gate, reasoning this app has no authenticated-but-unpermitted consumer path to protect), but that broke a genuinely fresh instance: root's `beforeLoad` runs for every route including `/sign-in` and `/setup`, which exist specifically to handle the no-session case, and `AuthMiddleware` throwing a redirect there fired before those routes' own logic (particularly `/setup`'s "is there an owner yet") ever got a chance to run, redirect-looping `/setup` → `/sign-in` → `/setup` forever on an empty database. Root's `getSession` (`authFn.ts`) is deliberately non-throwing now, just returns the session or `null`, and `_workspace/route.tsx`'s own `beforeLoad` is back to doing both checks itself (session presence, then `isRoleAllowed`). `AuthMiddleware`'s throw-based contract is still correct for `apiKeysFn.ts`'s handlers, those are only ever reached from inside the already-gated dashboard, so a throw there is genuine defense in depth, not the primary gate.

**Every zod schema lives in `src/schemas/`, one file per domain** (`auth.ts`, `setup.ts`, `providers.ts`, `team-roles.ts`, `users.ts`, `api-keys.ts`, `role.ts` for the shared `customRoleSchema` building block reused by the other three). A `*Fn.ts` server function or a form always imports its validator/schema from there rather than declaring one inline; if the same shape needs a client-side form schema and a server-side payload schema, share the one schema unless the two genuinely validate different shapes. `schemas/setup.ts`'s `completeSetupSchema` is deliberately the only schema there now (name/email/password/rememberMe), the setup flow used to also collect app name/security/methods/roles through a multi-step wizard with its own separate `wizardSchema`, both are gone, see the `_auth` routing note above for why.

**Every type used from more than one file lives in `src/types/`**, one file per domain (`role.ts`, `user.ts`, `api-key.ts`). A domain type derived from a schema (`CustomRole`) is `z.infer<typeof theSchema>` with the schema imported from `schemas/`. For anything that comes back from `auth.api.*`, better-auth's plugins already export fully-typed shapes (`UserWithRole`, `SessionWithImpersonatedBy` from `better-auth/plugins/admin`, `ApiKey` from `@better-auth/api-key/types`), use those directly (`export type ListedUser = UserWithRole`) instead of re-deriving through `Awaited<ReturnType<typeof ourWrapperFn>>`, but verify the package's type actually matches what the specific endpoint returns first: `@better-auth/api-key`'s own `ApiKey` type includes a `key` field (the hashed value) that `listApiKeys` never actually returns, so `types/api-key.ts` deliberately still derives from `listApiKeysFn`'s real return shape rather than using the package export, see the comment there. Only fall back to `Awaited<ReturnType<typeof theServerFn>>` (function imported via `import type`, so it never pulls runtime code into the type-only file) when no single upstream type covers the shape, like `UserDetail`, which is our own composite of a user, sessions, and a raw adapter query for linked accounts. A type that's genuinely internal to one file (a widget's own generic column-def helper type, a route's local form-values type) stays colocated with that file instead of moving here.

**Access model** (`src/auth/permissions.ts`, `src/auth/settings/access-store.ts`, `src/functions/rolesFn.ts`): owner and admin can always sign into the dashboard. Every other role, the fixed `user` role and any custom role, needs to be explicitly added to the "allowed roles" list on the Teams & roles page before its holders can get past `_workspace`'s `beforeLoad`. `isRoleAllowed(role, allowedRoles)` is the single source of truth for that check; don't duplicate it inline. Within the dashboard, owner and admin are further distinguished: admin has broad access (add users, view everything) but only owner can promote/demote roles, remove accounts, ban/unban, reset passwords, or impersonate. `isAdminTier(role)`/`isOwner(role)` (also in `permissions.ts`) are the single source of truth for that tier check, used by `AdminMiddleware`/`OwnerMiddleware` and by the inline checks in `users.tsx`/`team-roles.tsx`; never write `role !== "owner" && role !== "admin"` by hand. See `users.tsx`'s columns and its inlined user-detail dialog for where that split is enforced in the UI, and `usersFn.ts`/`apiKeysFn.ts` for the same split enforced server-side (never trust the client-side hide alone).

One known gap: impersonating a user whose role isn't on the allowed-roles list lands them on `/unauthorized` immediately (`_workspace`'s `beforeLoad` enforces the allowed-roles check on every dashboard route, including the one impersonation navigates to), and `/unauthorized` only offers "Sign out", not "stop impersonating", so the owner gets fully signed out rather than dropped back into their own session with one click. Worth fixing if impersonating non-dashboard roles becomes a common flow.

**Custom roles** (`src/auth/settings/roles-store.ts`) are stored as a flat list in KV and fed into better-auth's `admin` plugin (`buildRoles` in `permissions.ts`) at boot. Changes take effect on the instance's next restart, not immediately, which is why every settings-save toast in this app says so.

**Toggleable sign-in methods** (`src/auth/settings/methods.ts`: `AUTH_METHODS`, currently `emailAndPassword` (always on), `twoFactor`, `username`, `passkey`, `magicLink`, `apiKey`) are all registered unconditionally in `src/auth/index.ts`'s `plugins` array, then gated per-request in `hooks.before` (`createAuthMiddleware` from `better-auth/api`, the officially documented pattern for conditional endpoint access, confirmed against better-auth's own docs before building this, not a bespoke workaround). `GATED_PATH_PREFIXES`/`GATED_EXACT_PATHS` in `src/auth/index.ts` map each method's actual better-auth route paths (confirmed by grepping the installed plugin source for its literal path strings, e.g. `/two-factor/`, `/passkey/`, `/api-key/`, `/sign-in/username`, `/sign-in/magic-link`, not guessed) to a fresh `getEnabledMethods()` KV read; a disabled method's endpoints throw `APIError("NOT_FOUND")`, so a disabled feature looks like it doesn't exist rather than like it exists-but-is-forbidden. Registering conditionally instead (`...(enabledMethods.X ? [plugin()] : [])`, gated only at Worker-isolate-cold-start time) was tried and reverted: `enabledMethods` read once per isolate could disagree with a fresh per-request KV read after a toggle, so an isolate that booted before the toggle would have no plugin at all while a request thought the feature was on, throwing instead of working, inconsistently depending on which isolate a request landed on. `emailAndPassword` is the one exception, hardcoded `enabled: true`, never read from KV at all: it's the only method the dashboard's own sign-in page uses (see below), so it can never be a toggle without risking locking every admin out of their own instance. `ApiKeyEnabledMiddleware` (`src/middleware/apikey-middleware.ts`) still exists separately and still matters: `hooks.before` only intercepts requests through `auth.handler` (the raw HTTP catch-all at `src/routes/api/auth/$.ts`), while this app's own wrapper functions in `apiKeysFn.ts` call `auth.api.createApiKey` etc. directly in-process, never touching that HTTP layer, so they need their own gate. Both layers now exist; before this, only the wrapper-function layer did, leaving the raw HTTP routes reachable regardless of the toggle.

**The dashboard's own sign-in (`AuthForm`, `src/components/auth/auth-form.tsx`) is email+password only, always**, regardless of which other methods are toggled on. Those toggles exist for a future consumer-facing sign-in flow this project doesn't build yet, not for the admin dashboard: owner/admin access can never depend on a method that could be toggled off, so it isn't given the choice. Don't add conditional rendering of magic-link/passkey/username options to this form without deciding that trade-off deliberately first.

**Anonymous, phone number, and email OTP sign-in are not implemented at all** (removed from `AUTH_METHODS`, no plugin imports in `src/auth/index.ts`), unlike the methods above which are built but toggleable. This is a deliberate scope decision, not a gap: this project ships a smaller, curated set of methods and expects anyone self-hosting who wants one of these back to add the plugin themselves (`better-auth/plugins`' `anonymous`/`phoneNumber`/`emailOTP`, same shape as the methods still here), rather than the project carrying every better-auth plugin by default.

**Widgets, the only reusable pieces meant to be imported from anywhere, live in `components/widgets/`:**
- `widgets/tables/`: `DataTable` (search, per-column filters auto-detected from data shape, column visibility, sort, row selection + bulk actions, pagination, built on `@tanstack/react-table` v9's real API, not the deprecated `filterFns`/`sortFns` aggregate exports) and `DataTablePagination`. `aria-label` is a **required** prop (react-aria's underlying grid throws a dev warning without one, don't make it optional again).
- `widgets/blocks/`: the `useAppForm`/`withForm` TanStack Form setup (field components, submit button) used by every form in the app (sign-in, setup, providers, team-roles).
- `widgets/dialog-widget/`: `DialogWidget`, the one entry point for a drawer-style dialog (title/description/children/footer in, `Drawer`/`DrawerContent`/`DrawerHeader` wiring hidden).

Feature-specific things that use a widget but aren't reusable themselves (e.g. `getUsersColumns`, `UserDetailDrawer`, `getApiKeyColumns`) live in `components/dashboard/<feature>/`, not in `widgets/`.

**UI components follow shadcn's `aria-lyra` style** (`components.json`): built on `react-aria-components`, not Radix. **Never hand-author a file under `components/ui/`**, always `bunx shadcn add <component>`. The generated API (prop names, which sub-component wraps what) frequently differs from shadcn's default/Radix registry and from what you'd guess, e.g. `DropdownMenuTrigger` is the *root* wrapping both the trigger element and `DropdownMenu` (the content), not just the trigger button. When adding shadcn components, they land under `@/components/ui` per the aliases in `components.json` (`baseColor: olive`, icon library: `tabler`).

**Dates go through `date-fns`** (already a dependency), not `Date.prototype.toLocaleString`/`toLocaleDateString`. See any `*-columns.tsx` file for the `format(date, "PPP")` convention.

**Styling is Tailwind v4, CSS-first.** There is no `tailwind.config.js`; theme tokens, the `container` utility, and custom utilities (`no-scrollbar`, `dualTone`) are all defined in `src/styles/globals.css` via `@theme inline` and `@utility`. Colors are OKLCH and swap via a `.dark` class selector (see the `@custom-variant dark` line), even though the app is currently forced dark. `src/styles/typeset.css` holds prose/typography rules and is imported into `globals.css`.

**Path alias**: `@/*` maps to `src/*` (set in both `tsconfig.json` and consumed via `vite-tsconfig-paths` through `resolve.tsconfigPaths` in `vite.config.ts`).

**Responsive breakpoints diverge from Tailwind's defaults**: `src/lib/use-media-query.ts` defines its own `BREAKPOINTS` map (`md: 800`, plus `3xl: 1600` / `4xl: 2000` beyond Tailwind's stock scale) for the `useMediaQuery`/`useIsMobile` hooks, used for JS-driven layout decisions (e.g. the sidebar in `Dashboard`). `useIsMobile` itself is hardcoded to `(max-width: 768px)` rather than using the `md` entry from that same map, be aware of this mismatch if you touch mobile breakpoint logic.

## Lint/format notes

- `eslint.config.js` extends `@tanstack/eslint-config` but turns off `import/no-cycle`, `import/order`, `sort-imports`, `@typescript-eslint/array-type`, `@typescript-eslint/require-await`, and `pnpm/json-enforce-catalog`. Don't reintroduce those as expectations when reviewing code.
- `bun run lint` currently fails outright (`typescript-eslint does not support TS 7.0`), a version mismatch between the installed TypeScript and `typescript-eslint`, unrelated to any specific change. Don't treat a lint failure as caused by your edit without checking it's not just this.
- Prettier (`.prettierrc`): no semicolons, double quotes, `prettier-plugin-tailwindcss` for class sorting. Its `tailwindStylesheet` option points at `src/styles.css`, which does not exist (the real stylesheet is `src/styles/globals.css`), this looks like a stale path from before the styles were moved into `src/styles/`. `bun run format`/`check` currently error on this rather than just skipping class-sorting. Needs fixing before either command is usable.

## Known issues / cleanup backlog

Flagged but not yet done, read before assuming either is already handled:

- **`bun run dev` disables the Cloudflare Vite plugin's local AI-agent observability capture** (`X_LOCAL_OBSERVABILITY=false` in the `dev` script in `package.json`). This is deliberate, not an oversight: when the plugin detects it's running inside an AI coding agent (env vars like `CLAUDECODE`), it defaults to capturing every internal sub-operation, KV calls, D1 calls, and every internal module fetch during SSR, as a span in a local SQLite-backed store queryable at `/cdn-cgi/local/explorer/api/local/observability/query`. In practice this generated over 150,000 spans in about 20 minutes of normal interactive use (one single request's internal module loading alone produced 631 sub-spans), and the capture overhead was severe enough to make requests hang indefinitely (never erroring, never responding) once enough had accumulated, looking like the whole app had frozen. Idle time produces zero span growth, it's purely tied to request volume, so this reliably got worse the longer a session stayed open and the more it was used, and reproduced identically across multiple clean restarts regardless of what application code had most recently changed. This env var only controls the Vite plugin's Node-side local dev tooling (`X_LOCAL_EXPLORER`/`X_LOCAL_OBSERVABILITY`, both default `true` under an agent session), it's unrelated to and doesn't touch `wrangler.jsonc`'s `observability` block, which governs the real deployed Worker and is untouched. If a future debugging session needs that local trace/log capture back, run `X_LOCAL_OBSERVABILITY=true vite dev --port=3000` directly instead of `bun run dev`, understanding it will likely reproduce the same freeze if left running for a while under load.
- **`getUsersColumns` and `getApiKeyColumns`** no longer exist, both `users.tsx` and `api-keys.tsx` inline their columns directly per the route-file convention above; ignore any earlier reference to those names.
