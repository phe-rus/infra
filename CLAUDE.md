# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

This repo is both a self-hosted authentication backend (better-auth, on Cloudflare Workers + D1 + KV) and its admin dashboard: one TanStack Start (React 19 + SSR) app, one Worker, serving both the dashboard UI and better-auth's HTTP API. See `README.md` for what the project is and why it exists; this file is the technical map.

Package manager: **bun** (`bun.lock` is the lockfile; `.vscode/settings.json` pins `npm.packageManager` to `bun`).

## Commands

```bash
bun install       # install dependencies
bun run dev       # start dev server on port 3000
bun run build     # production build (vite build)
bun run preview   # preview a production build
bun run test      # run the vitest suite once (vitest run)
bun run lint      # eslint
bun run format    # prettier --write across ts/tsx/js/jsx
bun run check     # prettier --check (no writes)
bun run typecheck # tsc --noEmit
```

There are no test files in the repo yet and no `vitest.config.*`, vitest currently runs against Vite's default config. When adding tests, run a single file with `bunx vitest run path/to/file.test.tsx` or a single test name with `bunx vitest run -t "test name"`.

## Architecture

**Routing is file-based and code-generated.** Routes live under `src/routes/`; `src/routeTree.gen.ts` is auto-generated by the `@tanstack/router-plugin` Vite plugin on dev/build, never hand-edit it (it's marked read-only in `.vscode/settings.json`). Three pathless layout routes sit at the top level:
- `_auth` (`src/routes/_auth/route.tsx`): `sign-in` and `setup`, redirects away if a session already exists. `setup` is two phases in one route file, not a multi-step wizard: initialize (runs migrations, mandatory before an owner can exist, `runSetupMigrations`) then create the owner account (name/email/password only). Nothing else gets collected here: app name, security, email-verification, sign-in methods, and instance access (owner/admin only, `user` never) are all static now, nothing left to configure afterward from a dashboard settings page, that whole category of "editable after setup" no longer exists in this app. An earlier five-step wizard (`components/auth/setup/`) collected all of that upfront; it was deleted, not because the settings don't matter, but because forcing them into a one-time form added friction for zero benefit over just defaulting sensibly and letting an owner change them whenever.
- `_workspace` (`src/routes/_workspace/route.tsx`): everything behind the dashboard shell. `beforeLoad` does two checks in order: is there a session (else redirect to `/sign-in`), then is this session's role allowed to access the instance at all (else redirect to `/unauthorized`), see **Access model** below. Root's own session fetch (`getSession` in `kit/auth/get-session.ts`) is deliberately non-throwing, it runs for every route including `/sign-in`/`/setup`, which exist to handle the no-session case, so this is the layout where "you actually need a session" gets enforced, not root.
- `_protected` (`src/routes/_protected/route.tsx`): just `unauthorized.tsx` today, deliberately outside `_workspace` so it renders without the `Dashboard` shell (someone who lands here isn't authorized to see it).

Current `_workspace` pages: `index` (home), `users` (member management). `database`/`storage`/`logs`/`billing` exist as sidebar links in `Dashboard` with no route behind them yet. Team & Roles existed too (instance access, then later custom roles as well) and was removed entirely, same treatment as Providers and API keys elsewhere in this doc: access is fixed code now (see Access model below), nothing left to manage on a page. There is no self-service API keys feature, it was built, then removed entirely (plugin, middleware, functions, hooks, route, schema, types) as a deliberate scope decision, not a gap; don't reintroduce it without that decision being revisited.

**A route file's job is `Route` + one thin `RouteComponent`, nothing else.** For a small page, that means everything lives inline in `RouteComponent` (state, handlers, a `useMemo(() => [...], [])`-wrapped column array, whatever it needs), not split into a separate `get*Columns()` factory or a page-specific sub-component file just to satisfy an abstraction nothing else imports; `sign-in.tsx`/`setup.tsx` are this shape. Once a page genuinely outgrows a single file, it moves to `src/features/<domain>/` instead of getting split apart in place: `features/<domain>/index.tsx` is the actual page component (page-level state, wiring up mutations, composing the pieces below), and every extracted piece sits flat, directly in `features/<domain>/`, no nested `components/` subfolder and no generic `-section`/`-drawer` suffixes. A piece is named after the action or resource it's built around, matching its `kit/hypermedia/<resource>/` counterpart file-for-file wherever one exists: `features/users/list-users.tsx` (table + columns, one file, not split further), `create-user.tsx`, `get-user-detail.tsx` (the detail dialog shell), `update-user.tsx`, `ban-user.tsx`, `revoke-user-sessions.tsx`, `set-user-password.tsx`, `impersonate-user.tsx`; `user-accounts.tsx` has no `kit` counterpart (accounts come bundled in `get-user-detail`'s response, not their own action) so it's just named plainly, no `-section` filler. The route file under `src/routes/` shrinks down to `Route` (`beforeLoad`/`loader`) plus a `RouteComponent` that renders the imported feature component with whatever route context it needs as props; `users.tsx` is ~20 lines. `src/features/` is for this, page/domain-specific UI that's too large to inline; it is not where `components/ui/` (shadcn primitives), `components/widgets/` (generic reusable pieces), or `components/dashboard/` (the shell) belong, those three stay exactly where they are.

The one real exception is something genuinely reused by more than one call site. `components/widgets/` holds pieces reusable from anywhere (`DataTable`, the `useAppForm` blocks setup, `DialogWidget`), always imported, never inlined. `components/dashboard/` currently holds only the `Dashboard` shell itself. A feature-specific standalone dialog with only one caller, like the user-detail dialog, is not a `components/dashboard/` thing (that folder is for the shell), it lives flat in `features/<domain>/` per the note above; when in doubt for a small page, inline it into the route first, and only reach for `features/` once it's genuinely too large to.

**Shell / entry points**: `src/start.ts` creates the TanStack Start server instance and registers CSRF middleware scoped only to server-function requests. `src/router.tsx` builds the router and wraps it with `QueryProvider`. `src/routes/__root.tsx` renders the actual `<html>` document (theme is hardcoded to `dark` via a static class, not runtime-toggled), does the root `beforeLoad` (session + setup status, see below), and mounts `TanStackDevtools`.

**Query client is a client/server-aware singleton** (`src/lib/queryClient.tsx`): on the client, `getContext()` reuses one module-level `QueryClient` across navigations; on the server it always constructs a fresh one per request (standard SSR-safe pattern, don't change this to a plain module-level singleton, it would leak state across requests). The `QueryProvider` unconditionally mounts `TanStackDevtools` (Router + Query panels). It is not gated behind a dev/prod check, so don't add one without checking whether that's intentional for this project.

**`queryClient.tsx` overrides `focusManager` to always report focused**; `networkMode` and `retryDelay` are both back to react-query's defaults (an earlier version fixed `retryDelay` at 1s and set `networkMode: 'always'`, both were removed, along with the per-call `withTimeout` wrapper every `use*Hooks.ts` mutation/query used to be wrapped in — none of that is the app's problem to solve right now; if the local dev runtime's occasional unresponsiveness becomes disruptive again, that's the first place to look, not something to reintroduce speculatively). The one non-default piece left is queries' `retry`: a predicate that skips retrying on a `401`/`403` status and otherwise retries up to twice (mutations still default to `retry: 0`, untouched by any of this). The `focusManager.setEventListener` override still means `refetchOnWindowFocus` is inert app-wide (the tab is always reported focused, so the underlying visibility event this depends on never fires), no automatic refetch when returning to a tab; acceptable here since every mutation already invalidates its own affected queries explicitly. If you ever need real refetch-on-focus back, that override is the first thing to remove. With `networkMode` back to default, a query retry now *can* genuinely pause while the browser is offline and only resume on the next `online` event, unlike when `networkMode: 'always'` was set; this doesn't affect the local dev experience but is worth knowing if this app ever needs to behave differently offline.

**Errors surface as toasts globally**: the `QueryCache` in `queryClient.tsx` has an `onError` that calls `t.error(...)` (from `@/components/ui/sonner`, backed by `goey-toast`) for every failed query except `AbortError`. Individual query hooks generally don't need their own error handling/toast logic for reads, it happens centrally.

**Every mutation hook builds on `useAppMutation` (`src/kit/shared/use-app-mutation.ts`)** instead of calling `useMutation` directly. It reads the query client via `useQueryClient()` (React context, the same instance every `useSuspenseQuery` in the tree reads from) rather than each hook grabbing its own reference, takes an `invalidates` array of query keys and fires `invalidateQueries` for each one in `onSettled` (not awaited, callers don't need to see the refetch land before `mutateAsync` resolves), and applies the standard success/error toast pair from `successMessage`/`successDescription`/`errorMessage` so a hook only states its own keys and copy. `optimisticUpdate`'s `cancelQueries` call in `onMutate` **is** awaited, matching the documented react-query pattern (narrows the window where an in-flight refetch could land after the optimistic write and clobber it); an earlier version of this hook made it non-awaited chasing a "hang" theory that turned out to be wrong (confirmed by reading `query-core`'s `retryer.ts` directly: `cancelQueries` rejects synchronously, it can't hang `onMutate`). The optimistic rollback in `onError` only restores the pre-mutation snapshot if the cache still holds exactly what this mutation wrote, skipping it if a second mutation on the same key wrote something newer in the meantime, otherwise the rollback would silently erase that concurrent change. See any `kit/<domain>/use-*.ts` file for the shape. The exceptions are sign-in/sign-out/impersonation/complete-setup (`kit/auth/use-sign-in.ts`, `use-logout.ts`, `use-complete-setup.ts`, `kit/hypermedia/users/use-impersonate-user.ts`, `use-stop-impersonating.ts`), which swap out the session identity entirely and need `q.clear()` plus a navigation rather than a targeted invalidate, so they still call `useMutation` directly against the module-level `getContext()` client.

**Data flow: loader `ensureQueryData` + `useSuspenseQuery`, not `Route.useLoaderData()`, for anything a mutation can change.** The loader prefetches into the query cache so SSR/first paint has data; the component then subscribes via `useSuspenseQuery(sameQueryOptions())` so that a mutation's `invalidateQueries` actually triggers a re-render. `Route.useLoaderData()` is a one-time snapshot, fine for values a form seeds itself with once (e.g. a settings form's `defaultValues`) and forgets about, wrong for anything meant to stay live (a table of users, a list of API keys).

**`src/kit/` is the one place all backend-adjacent code lives**: `kit/auth/` (session/sign-in/setup), `kit/hypermedia/<resource>/` (currently just `users/`, more resources nest alongside it as they show up), `kit/middleware/` (`AdminMiddleware`/`OwnerMiddleware`), `kit/shared/` (cross-cutting helpers with no one domain), plus three flat root files: `kit/schemas.ts` (every zod schema), `kit/types.ts` (every shared type), `kit/index.ts` (a flat barrel re-exporting all of the above, for the rare case something needs a bit of everything). `src/auth/` (the better-auth config itself) and `src/components/` are deliberately outside `kit/`, this is about the server-function/hooks/schema/type layer, not the auth library setup or the UI.

**A domain folder holds a server function and its hook side by side, one file per export, no separate hooks tree.** `kit/hypermedia/users/create-user.ts` exports `createUser` (a `createServerFn(...)`, no `Fn` suffix); `use-create-user.ts` right next to it exports the `useCreateUser` hook that wraps it. Same for `kit/auth/`: `sign-in.ts`/`use-sign-in.ts`, `complete-setup.ts`/`use-complete-setup.ts`, and so on. `*QueryOptions()` factories (`users-query-options.ts`, `me-query-options.ts`) live there too, colocated the same way; a `*QueryOptions()` factory is a client-side React Query construct built around a server function, not part of the server function's own definition, but it still belongs next to it, not in a separate tree. Every domain folder has an `index.ts` barrel re-exporting everything in it; import from `@/kit/<domain>` (or `@/kit/hypermedia/<resource>`), not the individual file, unless you're inside that same folder, where relative imports between colocated files are normal. Inside a handler that needs the request's headers for an `auth.api.*` call, use `getRequestHeaders()` from `@tanstack/react-start/server` (synchronous, no `await`), assigned to its own `const headers = getRequestHeaders()` line, not called inline in the call args. Middleware bodies, by contrast, already receive `request` as a parameter from the framework and should use `request.headers` directly rather than also calling `getRequestHeaders()`. Don't thread `headers` through middleware `context` for handlers to consume; every handler that needs it calls the utility itself. A handler gated by `AdminMiddleware`/`OwnerMiddleware` never re-checks `if (!sessions)`, the middleware already guarantees a session (and the required role tier) before the handler runs; re-checking is dead code. A check that needs the *validated body* (not just the session), like `create-user.ts`'s "admin can only hand out the `user` role" rule, can't live in a `createMiddleware()` at all: TanStack Start always runs `.middleware([...])` before the server function's own `.validator()`, regardless of call order in the source, so a middleware here only ever sees the raw unvalidated body. Those live as plain guard functions in `kit/shared/` instead (`assert-can-assign-role.ts`'s `assertCanAssignRole`), called from inside the handler where `data` is already typed. `kit/shared/` is also where `useAppMutation`/`settleAll` (`use-app-mutation.ts`) and cache-patch helpers reused across a domain's mutation hooks (`patch-user-cache.ts`'s `patchUserInCache`, used by several of `hypermedia/users/`'s `use-*.ts` hooks) live, since none of those belong to one specific action file.

**Every mutating `auth.api.*` call forwards its response headers**, not just Set-Cookie. `src/auth/forward-headers.ts`'s `forwardAuthHeaders(headers)` wraps `setResponseHeaders()` (from `@tanstack/react-start/server`) to propagate the entire header set better-auth returns, not a hand-parsed Set-Cookie subset, since better-auth can set more than one cookie-shaped header on a write. Call the `auth.api.*` method with `returnHeaders: true` and pass its `headers` straight to `forwardAuthHeaders`. Note the response shape changes when `returnHeaders: true` is added: an endpoint that normally returns a real payload gets wrapped as `{ response: T, headers }` (destructure `{ response: { user }, headers: responseHeaders }`), while an endpoint with no meaningful body stays flat as `{ headers }`.

**Every middleware lives in `src/kit/middleware/`, one file per middleware, with its own `index.ts` barrel** (`owner-middleware.ts`: `OwnerMiddleware`, owner only, throws if not; `admin-middleware.ts`: `AdminMiddleware`, owner or admin, throws if not). A middleware that gates access throws inside itself. `assertCanAssignRole` is not here despite being an authorization check too, see above for why (it needs the validated body, so it lives in `kit/shared/` as a plain function instead).

There used to be a third one, `AuthMiddleware` (formerly `auth-middleware.ts`): "any session, and that session's role must be allowed to use this instance" as one combined gate, for a self-service feature to build on. It was removed, no server function ever ended up calling it, and the self-service API-keys feature it was originally built for was removed entirely too. Worth remembering why, if something like it gets rebuilt: it was also briefly used by root's own session fetch (folding the allowed-roles check into one shared gate, reasoning this app has no authenticated-but-unpermitted consumer path to protect), but that broke a genuinely fresh instance: root's `beforeLoad` runs for every route including `/sign-in` and `/setup`, which exist specifically to handle the no-session case, and a middleware throwing a redirect there fired before those routes' own logic (particularly `/setup`'s "is there an owner yet") ever got a chance to run, redirect-looping `/setup` → `/sign-in` → `/setup` forever on an empty database. That's why root's `getSession` (`kit/auth/get-session.ts`) is deliberately non-throwing, just returns the session or `null`, and `_workspace/route.tsx`'s own `beforeLoad` does both checks itself (session presence, then `isAdminTier`) instead of delegating to a shared middleware. A throws-on-no-session contract is only safe for something reached from inside the already-gated dashboard, never for a route's own top-level session fetch.

**Every zod schema lives in the single flat `src/kit/schemas.ts`**, no per-domain files. A `kit/<domain>/*.ts` server function or a form always imports its validator/schema from there rather than declaring one inline; if the same shape needs a client-side form schema and a server-side payload schema, share the one schema unless the two genuinely validate different shapes. `completeSetupSchema` is deliberately just name/email/password/rememberMe, the setup flow used to also collect app name/security/methods/roles through a multi-step wizard with its own separate `wizardSchema`, both are gone, see the `_auth` routing note above for why.

**Every type used from more than one file lives in the single flat `src/kit/types.ts`**, no barrel of per-domain files. A domain type derived from a schema is `z.infer<typeof theSchema>` with the schema imported from `kit/schemas.ts`. For anything that comes back from `auth.api.*`, better-auth's plugins already export fully-typed shapes (`UserWithRole`, `SessionWithImpersonatedBy` from `better-auth/plugins/admin`), use those directly (`export type ListedUser = UserWithRole`) instead of re-deriving through `Awaited<ReturnType<typeof ourTool>>`, but verify the package's type actually matches what the specific endpoint returns first before trusting it blindly. Only fall back to `Awaited<ReturnType<typeof theTool>>` (the tool function imported via `import type` from `@/kit/<domain>`, so it never pulls runtime code into the type-only file) when no single upstream type covers the shape, like `UserDetail` (composite of a user, sessions, and a raw adapter query for linked accounts, from `getUserDetail`) or `UsersListData` (from `listUsers`, reused by the optimistic-update helpers in `kit/hypermedia/users/`). A type that's genuinely internal to one file (a widget's own generic column-def helper type, a route's local form-values type) stays colocated with that file instead of moving here.

**Access model** (`src/auth/permissions.ts`): roles are the fixed three, `owner`/`admin`/`user`, built statically by `buildRoles()` (no args, no KV) and passed to better-auth's `admin` plugin in `src/auth/index.ts`. Dashboard access is owner/admin only, hardcoded, `_workspace/route.tsx`'s `beforeLoad` checks `isAdminTier(session.user.role)` directly and redirects to `/unauthorized` otherwise; the plain `user` role can never sign into the dashboard, full stop, not a configurable instance setting. There used to be a Team & Roles page controlling this (an "allowed roles" list `user` could be added to, and before that, custom roles too) and both were removed entirely, same treatment as API keys and Providers elsewhere in this doc: this is fixed code now, not a setting. Within the dashboard, owner and admin are further distinguished: admin has broad access (add users, view everything, remove any non-owner account) but only owner can promote/demote roles, remove another owner, ban/unban, reset passwords, or impersonate. Add and remove follow the same shape but aren't identical: `kit/hypermedia/users/create-user.ts` lets admin create only `user` accounts (owner can create any role); `remove-user.ts` lets admin remove any account except an owner's (owner can remove anyone but themselves) — so "admin-allowed" is broader for removal than for creation, don't conflate the two checks. `isAdminTier(role)`/`isOwner(role)` (in `permissions.ts`) are the single source of truth for the tier check, used by `AdminMiddleware`/`OwnerMiddleware`/`_workspace/route.tsx` and by the inline checks throughout `features/users/`; never write `role !== "owner" && role !== "admin"` by hand. See `features/users/list-users.tsx` (`canManageRole` vs `canRemove`) and `get-user-detail.tsx` for where that split is enforced in the UI, and `kit/hypermedia/users/` for the same split enforced server-side (never trust the client-side hide alone; `remove-user.ts` re-fetches the target's current role before allowing a non-owner caller to proceed).

One known gap: impersonating anyone with the plain `user` role now lands the owner on `/unauthorized` immediately and unconditionally (`_workspace`'s `beforeLoad` enforces the owner/admin-only check on every dashboard route, including the one impersonation navigates to, and `user` can never pass it), and `/unauthorized` only offers "Sign out", not "stop impersonating", so the owner gets fully signed out rather than dropped back into their own session with one click. Worth fixing if impersonating `user`-role accounts becomes a common flow; today it's a dead end by construction, not just a corner case.

**`src/auth/index.ts` is now entirely static, nothing in this app's auth config is KV-backed anymore.** `appName`, `security`, `roles` (`buildRoles()`, fixed owner/admin/user), and `trustedOrigins`'s suffix list (`env.TRUSTED_ORIGINS`, a Worker var, not KV) are all plain constants or env vars, not `await`ed from anywhere at request or boot time. Sign-in methods (`emailAndPassword` always on, plus `twoFactor`, `username`, `passkey`) are registered unconditionally in the `plugins` array, same as before, just with no toggle UI left to control them (the Providers page that displayed them, and the KV-backed `methods.ts`/`methods-store.ts` behind its toggles, were removed entirely, not just disabled). Dashboard access (owner/admin only) and custom roles were both KV-backed features too (`access-store.ts`, `roles-store.ts`, the Team & Roles page) and were removed the same way; access is now the fixed `isAdminTier` check described in Access model above. Two plugins that existed at various points and were removed entirely: self-service API keys (`apiKey`, its own middleware, functions, hooks, route, schema, types) and magic links (`magicLink`). `anonymous`/`phoneNumber`/`emailOTP` were never built at all, out of scope for this project by default; self-hosters who want any of these back can add the plugin themselves (`better-auth/plugins`, same shape as `twoFactor`/`username`).

**The dashboard's own sign-in (`AuthForm`, `src/components/auth/auth-form.tsx`) is email+password only, always**, regardless of which other methods exist. Those methods (twoFactor as a second factor aside) exist for a future consumer-facing sign-in flow this project doesn't build yet, not for the admin dashboard: owner/admin access can never depend on a method, so it isn't given the choice. Don't add conditional rendering of passkey/username options to this form without deciding that trade-off deliberately first.

**Anonymous, phone number, and email OTP sign-in are not implemented at all** (removed from `AUTH_METHODS`, no plugin imports in `src/auth/index.ts`), unlike the methods above which are built but toggleable. This is a deliberate scope decision, not a gap: this project ships a smaller, curated set of methods and expects anyone self-hosting who wants one of these back to add the plugin themselves (`better-auth/plugins`' `anonymous`/`phoneNumber`/`emailOTP`, same shape as the methods still here), rather than the project carrying every better-auth plugin by default.

**Widgets, the only reusable pieces meant to be imported from anywhere, live in `components/widgets/`:**
- `widgets/tables/`: `DataTable` (search, per-column filters auto-detected from data shape, column visibility, sort, row selection + bulk actions, pagination, built on `@tanstack/react-table` v9's real API, not the deprecated `filterFns`/`sortFns` aggregate exports) and `DataTablePagination`. `aria-label` is a **required** prop (react-aria's underlying grid throws a dev warning without one, don't make it optional again).
- `widgets/blocks/`: the `useAppForm`/`withForm` TanStack Form setup (field components, submit button) used by every form in the app (sign-in, setup).
- `widgets/dialog-widget/`: `DialogWidget`, the one entry point for a drawer-style dialog (title/description/children/footer in, `Drawer`/`DrawerContent`/`DrawerHeader` wiring hidden).

Feature-specific things that use a widget but aren't reusable themselves (e.g. `UserDetailDrawer`) live in `components/dashboard/<feature>/`, not in `widgets/`.

**UI components follow shadcn's `aria-lyra` style** (`components.json`): built on `react-aria-components`, not Radix. **Never hand-author a file under `components/ui/`**, always `bunx shadcn add <component>`. The generated API (prop names, which sub-component wraps what) frequently differs from shadcn's default/Radix registry and from what you'd guess, e.g. `DropdownMenuTrigger` is the *root* wrapping both the trigger element and `DropdownMenu` (the content), not just the trigger button. When adding shadcn components, they land under `@/components/ui` per the aliases in `components.json` (`baseColor: olive`, icon library: `tabler`).

**Dates go through `date-fns`** (already a dependency), not `Date.prototype.toLocaleString`/`toLocaleDateString`. See any `*-columns.tsx` file for the `format(date, "PPP")` convention.

**Styling is Tailwind v4, CSS-first.** There is no `tailwind.config.js`; theme tokens, the `container` utility, and custom utilities (`no-scrollbar`, `dualTone`) are all defined in `src/styles/globals.css` via `@theme inline` and `@utility`. Colors are OKLCH and swap via a `.dark` class selector (see the `@custom-variant dark` line), even though the app is currently forced dark. `src/styles/typeset.css` holds prose/typography rules and is imported into `globals.css`.

**Path alias**: `@/*` maps to `src/*` (set in both `tsconfig.json` and consumed via `vite-tsconfig-paths` through `resolve.tsconfigPaths` in `vite.config.ts`).

**Responsive breakpoints diverge from Tailwind's defaults**: `src/lib/use-media-query.ts` defines its own `BREAKPOINTS` map (`md: 800`, plus `3xl: 1600` / `4xl: 2000` beyond Tailwind's stock scale) for the `useMediaQuery`/`useIsMobile` hooks, used for JS-driven layout decisions (e.g. the sidebar in `Dashboard`). `useIsMobile` itself is hardcoded to `(max-width: 768px)` rather than using the `md` entry from that same map, be aware of this mismatch if you touch mobile breakpoint logic.

## Lint/format notes

- `eslint.config.js` extends `@tanstack/eslint-config` but turns off `import/no-cycle`, `import/order`, `sort-imports`, `@typescript-eslint/array-type`, `@typescript-eslint/require-await`, and `pnpm/json-enforce-catalog`. Don't reintroduce those as expectations when reviewing code.
- `bun run lint` currently fails outright (`typescript-eslint does not support TS 7.0`), a version mismatch between the installed TypeScript and `typescript-eslint`, unrelated to any specific change. Don't treat a lint failure as caused by your edit without checking it's not just this.
- Prettier (`.prettierrc`): no semicolons, double quotes, `prettier-plugin-tailwindcss` for class sorting. Its `tailwindStylesheet` option points at `src/styles.css`, which does not exist (the real stylesheet is `src/styles/globals.css`), this looks like a stale path from before the styles were moved into `src/styles/`. `bun run format`/`check` currently error on this rather than just skipping class-sorting. Needs fixing before either command is usable.

## Known issues / cleanup backlog

Flagged but not yet done, read before assuming either is already handled:

- **`bun run dev` disables the Cloudflare Vite plugin's local AI-agent observability capture** (`X_LOCAL_OBSERVABILITY=false` in the `dev` script in `package.json`). This is deliberate, not an oversight: when the plugin detects it's running inside an AI coding agent (env vars like `CLAUDECODE`), it defaults to capturing every internal sub-operation, KV calls, D1 calls, and every internal module fetch during SSR, as a span in a local SQLite-backed store queryable at `/cdn-cgi/local/explorer/api/local/observability/query`. In practice this generated over 150,000 spans in about 20 minutes of normal interactive use (one single request's internal module loading alone produced 631 sub-spans), and the capture overhead was severe enough to make requests hang indefinitely (never erroring, never responding) once enough had accumulated, looking like the whole app had frozen. Idle time produces zero span growth, it's purely tied to request volume, so this reliably got worse the longer a session stayed open and the more it was used, and reproduced identically across multiple clean restarts regardless of what application code had most recently changed. This env var only controls the Vite plugin's Node-side local dev tooling (`X_LOCAL_EXPLORER`/`X_LOCAL_OBSERVABILITY`, both default `true` under an agent session), it's unrelated to and doesn't touch `wrangler.jsonc`'s `observability` block, which governs the real deployed Worker and is untouched. If a future debugging session needs that local trace/log capture back, run `X_LOCAL_OBSERVABILITY=true vite dev --port=3000` directly instead of `bun run dev`, understanding it will likely reproduce the same freeze if left running for a while under load.
