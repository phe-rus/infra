# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`www` ("Infraccount") is the end-user "my account" app for the `infra` identity/payments platform — think myaccount.google.com. It runs no auth server of its own: it's purely a consumer of `infra` via `better-auth/react`'s `createAuthClient` (`lib/auth-client.ts`), pointed at `infra`'s URL. It hosts the OAuth provider's own end-user pages (`/sign-in`, `/create-account`, `/two-factor`, `/consent`, `/forgot-password`, `/reset-password`) and the signed-in account surfaces under `_workspace` (profile, security, the wallets/payments home page) plus the `/pay/confirm` payment-intent confirmation page. See the monorepo root `CLAUDE.md` for the `infra`/`www` split, and `infra/CLAUDE.md` for the identity/payments server this app talks to.

Package manager: **bun** (`bun.lock` is the lockfile, gitignored, autogenerated by `bun install`, never committed).

## Commands

```bash
bun install       # install dependencies
bun run dev       # start dev server on port 3001
bun run build     # production build (vite build)
bun run deploy    # build and deploy to your Cloudflare account (wrangler deploy)
bun run preview   # preview a production build
bun run typecheck # tsc --noEmit
bun run type-gen  # wrangler types, regenerates worker-configuration.d.ts from wrangler.jsonc + .env.local
```

No `lint`/`format`/`check` here either — those are root-only Biome (see the root `CLAUDE.md`). No test suite exists for this app yet.

`worker-configuration.d.ts` and `src/routeTree.gen.ts` are both gitignored and autogenerated (the latter by the `@tanstack/router-plugin` Vite plugin on dev/build) — never hand-edit either. If a route file moves or a new one appears and typecheck complains the route string "is not assignable to `keyof FileRoutesByPath`", `routeTree.gen.ts` is stale: run `bun run dev` briefly (or `bun run build`) to force regeneration, then re-run typecheck.

## Architecture

**Path alias**: `@/*` maps to `./*`, the app root (set in `tsconfig.json`'s `paths` and mirrored in `vite.config.ts`'s `resolve.alias`, both must stay in sync) — same as `infra`. Only routing (`routeTree.gen.ts`, `router.tsx`, `server.ts`, `start.ts`, `routes/`) lives under `src/`; `domains/`, `middleware/`, `lib/`, `components/` all sit at the app root.

**Routing is file-based and code-generated.** Three pathless layout routes:
- `_auth` (`src/routes/_auth/route.tsx`): guard-only + `<Outlet/>`, no loader. `sign-in`, `create-account`, `two-factor`, `forgot-password`, `reset-password` — each is a genuinely one-off page, so its full form JSX lives directly in the route file, not extracted into a `domains/*/views/` component (the same reasoning `infra`'s `_auth` pages follow: a page used by exactly one route, with no other page composing multiple such pieces together, stays inline).
- `_workspace` (`src/routes/_workspace/route.tsx`): `loader` redirects to `/sign-in` if there's no session, and renders `<Headers/>` (from `@/components/headers`, the sticky nav shell — cross-cutting chrome, not a domain, same role as `infra/components/dashboard/`) around `<Outlet/>`. Pages: `index` (home — wallet/expenditure/transaction-history), `profile` (personal info — a single-piece one-off page, inlined the same way `_auth`'s pages are), `security` (2FA/passkeys/sessions/delete-account, composing four separate `domains/security/views/*` pieces on one page).
- `_protected` (`src/routes/_protected/route.tsx`): the shared guard for pages that require a session but aren't part of the `_workspace` dashboard shell (no `<Headers/>`) — `beforeLoad` redirects to `/sign-in` (preserving the current search string) if there's no session. Holds `consent` (the OAuth authorize-flow consent screen `infra`'s `oauthProvider` points `consentPage` at) and `pay/confirm` (the payment-intent confirmation page a connected app's checkout redirects the customer to). Both used to hand-roll this exact same `beforeLoad` check individually before it was centralized here.

**`domains/<name>/` is the one place all backend-adjacent code lives, one folder per domain** — `auth`, `payments`, `security` (this one absorbs what used to look like a separate `sessions` concern: session list/revoke is only ever rendered inside the security page, so it's not an independent domain). Same shape as `infra`:
```
domains/<name>/
├── index.ts        — barrel: export * from every file below
├── types/index.ts  — zod schemas for the domain (only `auth` and `payments` need one so far)
├── func.ts         — createServerFn actions, one per action, wrapping authClient.* calls
├── get-<name>.ts    — PURE queryOptions() factories, no hooks
├── use-<name>.ts    — every hook built on those options: queries AND mutations together
└── views/           — page-level .tsx components, only for pieces a route composes alongside
                       others on the same page (see the `_auth`/`profile` inlining note above for
                       the alternative — a page that's the ONLY thing on its route doesn't need one)
```
**Mutation hooks here take their input directly** (`useAddWallet()`'s `mutate(variables)`, not `mutate({ data: variables })`) — this differs from `infra`'s own mutation-call convention (`mutate({ data: {...} })`); don't blindly copy one app's calling shape into the other.

**A read wrapped in `createServerFn` forwards `getRequestHeaders()`** the same way `infra`'s own domains do (see `infra/CLAUDE.md`'s note on this) — necessary here specifically because `authClient.*()` has no cookies to send during SSR (`www`'s server has no browser cookie jar to draw from), which would otherwise silently 500 a route's loader on a cold load. Every domain's `func.ts` follows this. Mutations skip it: they only ever fire from a browser after hydration, where `authClient` already carries real cookies.

**`middleware/session-middleware.ts`'s `authMiddleware` attaches session to context but never throws** — deliberately looser than `infra`'s throwing `SessionMiddleware`, since `domains/auth/func.ts`'s `currentUser` (the root session-bootstrap read `__root.tsx`/every route's context depends on) needs to work with *no* session too, returning `null` rather than failing. Page-level "no session, redirect" enforcement lives per-route-group instead (`_workspace/route.tsx`'s `loader`, `_protected/route.tsx`'s `beforeLoad`), not centrally in the middleware.

**`domains/payments/`'s payment-intent flow** (`usePaymentIntent`/`useConfirmPaymentIntent` in `use-payments.ts`, `paymentIntentOptions` in `get-payments.ts`) is the customer-facing counterpart to a connected app's checkout redirect: dynamic-interval polling (fast at first, backing off, giving up after a real ceiling — see the constants at the top of `use-payments.ts`) against `authClient.pay.intent.get`, a `useConfirmPaymentIntent` mutation for submitting the mobile-money number, and a token-carrying redirect back to the requesting app's `returnUrl` once PawaPay resolves (the requesting app trusts only the signed token in that redirect, verified against `infra`'s own JWKS on its end, never the redirect itself). `domains/payments/use-payment-fields.ts`'s `usePaymentFields` (the country → provider → phone-prefix cascade) is a deliberate small separate copy of `infra/domains/payments/use-payment-fields.ts`'s same-shaped hook, not shared — it's app-level `useState`, and neither `@infra/ui` (UI-only) nor `@infra/payment` (framework-agnostic on purpose) is a clean home for it. Keep the two in sync if the cascade logic itself changes.

**`components/`** holds only cross-cutting shell chrome reused across the whole app, not domain-specific — currently just `headers.tsx` (the sticky top nav + mobile menu dialog, wrapping every `_workspace` page).

**Query client, mutation conventions, error toasts**: `lib/queryClient.tsx`'s `getContext()`/`QueryProvider` and the `useAppMutation` pattern work exactly as `infra/CLAUDE.md` documents for its own `lib/queryClient.tsx`/`@infra/ui/hooks`'s `useAppMutation` — same package, same behavior, not reimplemented here.
