# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

This repo is both a self-hosted authentication backend (better-auth, on Cloudflare Workers + D1 + KV + R2) and its admin dashboard: one TanStack Start (React 19 + SSR) app, one Worker, serving both the dashboard UI and better-auth's HTTP API. It also runs a real OAuth 2.1 / OIDC provider (`@better-auth/oauth-provider`), so connected applications can use this instance as their identity provider. See `README.md` for what the project is and why it exists; this file is the technical map.

Package manager: **bun** (`bun.lock` is the lockfile, gitignored, it's autogenerated by `bun install`, never committed; `.vscode/settings.json` pins `npm.packageManager` to `bun`).

## Commands

```bash
bun install       # install dependencies
bun run dev       # start dev server on port 3000
bun run build     # production build (vite build)
bun run deploy    # build and deploy to your Cloudflare account (wrangler deploy)
bun run preview   # preview a production build
bun run test      # run the vitest suite once (vitest run)
bun run typecheck # tsc --noEmit
bun run type-gen  # wrangler types, regenerates worker-configuration.d.ts from wrangler.jsonc + .env.local
```

There is no per-package `lint`/`format`/`check` here: those moved to one root-level Biome config, run from the monorepo root (see the root `CLAUDE.md`), not from inside `infra/`.

`bun run dev` needs a `.env.local` file (gitignored) with real secrets, copy `.env.example` and fill it in. `worker-configuration.d.ts` (the `Env` type) and `src/routeTree.gen.ts` (file-based routing) are both gitignored and autogenerated: `worker-configuration.d.ts` by `bun run type-gen` whenever `wrangler.jsonc` or `.env.local` change, `routeTree.gen.ts` automatically by the `@tanstack/router-plugin` Vite plugin on dev/build. Never hand-edit either.

There's a real `vitest.config.ts` and a growing `tests/` folder (mirroring the source tree, e.g. `tests/domains/console/assert-owns-app.test.ts`) — test files always live under `tests/`, never colocated next to the source they test. Run a single file with `bunx vitest run path/to/file.test.ts` or a single test name with `bunx vitest run -t "test name"`.

## Architecture

**Routing is file-based and code-generated.** Routes live under `src/routes/`; `src/routeTree.gen.ts` is auto-generated, never hand-edit it. Three pathless layout routes sit at the top level:
- `_auth` (`src/routes/_auth/route.tsx`): `sign-in`, `setup`, `forgot-password`, `reset-password`, redirects away if a session already exists (with a `/consent` exception, which skips that redirect). `setup` is two phases toggled by one `initialized` boolean, not a wizard: run pending migrations, then create the first (admin) user, name/email/password only. `create-account` (self-service signup for OAuth end-users) and `consent` (the OAuth authorize-flow consent screen) are **not** infra routes: `oauthProvider`'s `loginPage`/`consentPage`/`signUp.page`, configured via `auth.ts`'s `oauth: {...}` block (see **Console** below for where the actual `oauthProvider(...)` call lives), all point at `${env.ACCOUNTS_URL}/...`, so `accounts` hosts those pages; infra only keeps the admin-facing `/setup`, `/sign-in`, and `/forgot-password`/`/reset-password`. See the monorepo root `CLAUDE.md` for the `infra`/`accounts`/`www` split.
- `_workspace` (`src/routes/_workspace/route.tsx`): everything behind the admin `Dashboard` shell. Its `beforeLoad` does one thing: `q.ensureQueryData(protectedOptions())`, which resolves `protectedSession` (`domains/auth/func.ts`) — a server fn gated by `.middleware([AdminMiddleware])`, so admin-tier enforcement is centralized there, not a sequence of explicit redirects in the route file itself. Every child domain (see below) *also* independently re-checks `isAdminTier` in its own `route.tsx` loader — redundant defense-in-depth on top of the central gate, not the only enforcement point.
- `_protected` (`src/routes/_protected/route.tsx`): just `unauthorized.tsx`, deliberately outside `_workspace` so it renders without the `Dashboard` shell.

Current `_workspace` pages: `index` (home/business stats), `users`, `storage`, `console`, `logs` (a placeholder page: the route and its sidebar link both exist, but it doesn't render real log data yet), `settings` (also a stub placeholder, no real content yet). There is no self-service API keys feature: it was built, then removed entirely, a deliberate scope decision; don't reintroduce it without that decision being revisited. Team & Roles (an "allowed roles" list, then custom roles) was removed the same way: access is fixed code now (see Access model), nothing left to manage on a page. Payments (a plugin, a `domains/payments/`, and a `/billing` page) existed for a while but were removed entirely: each app now wires its own payment integration if it needs one, rather than `infra` shipping a shared one — don't reintroduce it without that decision being revisited.

**Every `_workspace` domain page is a folder route with an identical two-file shape.** `<domain>/route.tsx` does *only* the admin-tier guard — `loader: ({ context: { user } }) => { if (!isAdminTier(user.role ?? "")) throw redirect({ to: "/unauthorized", replace: true }) }`, `component` is just `<Outlet />` — and does no data-fetching of its own; `<domain>/index.tsx` does its own `loader: async ({ context: { q } }) => { await q.ensureQueryData(<domain>Options()) }` (or a `Promise.all` of several, for a domain with more than one query) and renders the actual page in `RouteComponent`. `users`, `console`, `storage`, and `logs` all match this shape exactly now (spot-check any one `route.tsx` against another — they're byte-for-byte the same guard). A detail sub-route (`console/$client_id/`) reads its own param and renders a detail view, using its domain's own parameterized hook (e.g. `useApp(clientId)`) rather than a raw `useSuspenseQuery(xOptions(id))` call inline in the route.

**`domains/<name>/views/` holds only the individual pieces a page composes** (`list-users.tsx`, `list-applications.tsx`, ...), flat, no nested `components/` subfolder, no generic `-section`/`-drawer` suffixes, named after the action or resource it's built around — see the **`domains/`** section below for the full domain-folder shape (`types/`, `func.ts`, `get-<domain>.ts`, `use-<domain>.ts`, `views/`, `index.ts`). There is no separate `src/features/` folder in this app; that's where page-composing pieces used to live before the `kit/` → `domains/` restructuring folded them in as each domain's own `views/`.

The one real exception is something genuinely reused by more than one call site. That's `@infra/ui`'s `widgets/` now (`DataTable`, the `useAppForm` blocks setup, `DialogWidget`, see the root `CLAUDE.md`), imported via `@infra/ui/widgets/tables`, `@infra/ui/widgets/blocks`, `@infra/ui/widgets/dialog-widget`, never inlined. The one thing still local to infra is `domains/console/views/framework-icon.tsx`: it's tied to infra's own console `Framework` type, so it can't move to the app-agnostic shared package. `components/dashboard/` currently holds only the `Dashboard` shell itself. A feature-specific standalone dialog with only one caller is not a `components/dashboard/` thing (that folder is for the shell), it lives flat in `domains/<name>/views/` per the note above; when in doubt for a small page, inline it into the route first, and only reach for `views/` once it's genuinely too large to.

**Shell / entry points**: `src/start.ts` creates the TanStack Start server instance and registers CSRF middleware scoped only to server-function requests. `src/router.tsx` builds the router and wraps it with `QueryProvider`. `src/routes/__root.tsx` renders the actual `<html>` document (theme is hardcoded to `dark` via a static class, not runtime-toggled), does the root `beforeLoad` (session + setup status), and mounts `TanStackDevtools`. `src/server.ts` is the raw Cloudflare Worker `fetch` export sitting in front of the TanStack Start handler; it intercepts `.well-known/openid-configuration`, `.well-known/oauth-authorization-server`, and `/jwks` specifically to add CORS headers (`Access-Control-Allow-Origin: *`, `Access-Allow-Methods: GET`) those need but the app doesn't set by default, then falls through to `handler.fetch(...)` for everything else.

**Query client is a client/server-aware singleton** (`lib/queryClient.tsx`): on the client, `getContext()` reuses one module-level `QueryClient` across navigations; on the server it always constructs a fresh one per request (standard SSR-safe pattern, don't change this to a plain module-level singleton, it would leak state across requests). The `QueryProvider` unconditionally mounts `TanStackDevtools` (Router + Query panels). It is not gated behind a dev/prod check, so don't add one without checking whether that's intentional for this project.

**`queryClient.tsx` overrides `focusManager` to always report focused**; `networkMode` and `retryDelay` are both back to react-query's defaults. The one non-default piece left is queries' `retry`: a predicate that skips retrying on a `401`/`403` status and otherwise retries up to twice (mutations still default to `retry: 0`). The `focusManager.setEventListener` override still means `refetchOnWindowFocus` is inert app-wide; acceptable here since every mutation already invalidates its own affected queries explicitly.

**Errors surface as toasts globally**: the `QueryCache` in `queryClient.tsx` has an `onError` that calls `t.error(...)` (from `@infra/ui/components/ui/sonner`, backed by `goey-toast`) for every failed query except `AbortError`. Individual query hooks generally don't need their own error handling/toast logic for reads, it happens centrally.

**Every mutation hook builds on `useAppMutation` (`@infra/ui/hooks`, `shared/ui/src/hooks/use-app-mutation.ts`)** instead of calling `useMutation` directly. It reads the query client via `useQueryClient()` rather than each hook grabbing its own reference, takes an `invalidates` array of query keys and fires `invalidateQueries` for each one in `onSettled`, and applies the standard success/error toast pair from `successMessage`/`successDescription`/`errorMessage`. `optimisticUpdate`'s `cancelQueries` call in `onMutate` **is** awaited (narrows the window where an in-flight refetch could land after the optimistic write and clobber it). The optimistic rollback in `onError` only restores the pre-mutation snapshot if the cache still holds exactly what this mutation wrote, skipping it if a second mutation on the same key wrote something newer in the meantime. See any `domains/<domain>/use-<domain>.ts` file for the shape. The exceptions are sign-in/sign-out/complete-setup (`domains/auth/use-auth.ts`'s `useSignIn`, `useLogout`, `useCompleteSetup`), which swap out the session identity entirely and need `q.clear()` plus a navigation rather than a targeted invalidate, so they still call `useMutation` directly against the module-level `getContext()` client.

**Data flow: loader `ensureQueryData` + `useSuspenseQuery`, not `Route.useLoaderData()`, for anything a mutation can change.** The loader prefetches into the query cache so SSR/first paint has data; the component then subscribes via `useSuspenseQuery(sameQueryOptions())` so that a mutation's `invalidateQueries` actually triggers a re-render. `Route.useLoaderData()` is a one-time snapshot, fine for values a form seeds itself with once and forgets about, wrong for anything meant to stay live (a table of users, a list of OAuth applications).

**`domains/` (app root, not under `src/`) is the one place all backend-adjacent code lives, one folder per domain**: `domains/auth/` (session/sign-in/setup/consent), `domains/users/`, `domains/storage/` (the R2 browser), `domains/console/` (OAuth client/application management), `domains/stats/`. There is no `domains/index.ts` root barrel spanning every domain, only each domain's own `index.ts`. **There is no shared `schemas.ts`/`types.ts` at the `domains/` root**: every domain owns its own `types/index.ts` (every zod schema for that domain, moved out of a flat `schema.ts`) with types colocated in `func.ts` (`z.infer<typeof theSchema>`, or an explicit composite/intersection type when no single schema or upstream better-auth type covers the shape, for example `domains/users/func.ts`'s `ListedUser = UserWithRole & { twoFactorEnabled?: boolean }`, needed because `UserWithRole` doesn't reflect plugins actually registered on this instance). `auth.ts` (the app's thin `createAuth(...)` call, see below) and `components/` are deliberately outside `domains/`, this is about the server-function/hooks/schema/type layer, not the auth library setup or the UI.

**Inside a domain folder, `func.ts` holds every `createServerFn(...)` for that domain and nothing else** (no `Fn` suffix on the exported name: `createUser`, `findApp`). Everything that *wraps* those functions for the client lives outside `func.ts`, split by what kind of React Query hook it produces: a `get-<domain>.ts` file holds **only** `*Options()` factories (`get-users.ts`: `usersOptions`, `userDetailOptions`, no hooks); a `use-<domain>.ts` file holds **every** hook built on those options, both queries (`useSuspenseQuery`/`useQuery`) and mutations (`useMutation`/`useAppMutation`) — `use-users.ts`: `useUsers`, `useUserDetail`, `useCreateUser`, `useBanUser`, `useImpersonateUser`, all together. Every domain folder has an `index.ts` barrel doing `export * from "./func"`, `"./types"`, `"./get-<domain>"`, `"./use-<domain>"`, plus one `export *` per file under `views/`; import from `@/domains/<domain>`, not the individual file, unless you're inside that same folder, where relative imports between colocated files (typically `import { x } from "./func"`) are normal. Inside a handler that needs the request's headers for an `auth.api.*` call, use `getRequestHeaders()` from `@tanstack/react-start/server` (synchronous, no `await`), assigned to its own `const headers = getRequestHeaders()` line, not called inline in the call args. Middleware bodies, by contrast, already receive `request` as a parameter from the framework and should use `request.headers` directly. A handler gated by `AdminMiddleware`/`SessionMiddleware` never re-checks `if (!sessions)`, the middleware already guarantees a session (and the required role tier, if any) before the handler runs. A check that needs the *validated body* (not just the session) can't live in a `createMiddleware()` at all: TanStack Start always runs `.middleware([...])` before the server function's own `.validator()`, so a middleware only ever sees the raw unvalidated body. Those live as plain guard functions colocated in the domain instead (e.g. `domains/console/assert-owns-app.ts`'s `assertOwnsApp`, deliberately kept as its own dependency-free file rather than folded into `func.ts`, so its test can run without pulling in `@/auth` → `cloudflare:workers`).

**A `func.ts`-consuming file's internal order is imports, then anything local and not itself a server function** (types, plain consts, helper functions), **then the `createServerFn` exports last**. A file that accepts `FormData` as its input uses a plain function as its `.validator()`, not a zod schema: TanStack Start detects `data instanceof FormData` client-side and sends it as the raw fetch body instead of JSON-serializing it, and hands that same `FormData` instance straight to `.validator()` unparsed server-side, so the validator does its own `.get()` extraction.

**Every mutating `auth.api.*` call that needs to propagate cookies forwards its response headers**, not just Set-Cookie. `lib/forward-headers.ts`'s `forwardAuthHeaders(headers)` wraps `setResponseHeaders()` to propagate the entire header set better-auth returns. Call the `auth.api.*` method with `returnHeaders: true` and pass its `headers` straight to `forwardAuthHeaders`. The response shape changes when `returnHeaders: true` is added: an endpoint that normally returns a real payload gets wrapped as `{ response: T, headers }`, while an endpoint with no meaningful body stays flat as `{ headers }`. Not every wrapped call needs this: `domains/console/func.ts`'s `rotateApp`/`removeApp` skip it because they go through a raw `ctx.adapter.*` call and don't set cookies.

**Every middleware lives in `middleware/` (app root, not under `src/`), one file per middleware, with its own `index.ts` barrel**: `admin-middleware.ts` (`AdminMiddleware`, admin only), `session-middleware.ts` (`SessionMiddleware`, any authenticated user, no role/tier check at all). `SessionMiddleware` is what OAuth end-user flows (consent) build on; the one gate in the app a plain `user`-role account can pass. A middleware that gates access throws inside itself.

**Access model** (`shared/auth/src/core/permissions.ts`, the shared `@infra/auth` package, not local to this app): roles are the fixed two, `admin`/`user`, built statically by `buildRoles()` and passed to better-auth's `admin` plugin inside `shared/auth/src/index.ts`'s `createAuth(...)`. Dashboard access (`_workspace`) is admin only, hardcoded; the plain `user` role can never pass it, full stop, not a configurable instance setting — a `user`-role account has no page of its own in this app at all, `www` is where that population's self-service surface lives instead. Whoever holds `admin` has full administrative power inside the dashboard: add users, view everything, remove any account, promote/demote roles, ban/unban, reset passwords, revoke sessions, impersonate, manage every OAuth application — no further tier or carve-out on top of it (there used to be an `owner`/`admin` split; it was collapsed to a single `admin` role deliberately, since only one or a handful of deeply-trusted accounts will ever hold it). `isAdminTier(role)` is the single source of truth for the check; never write `role !== "admin"` by hand.

The first user to ever sign up (via `/setup`) becomes `admin` automatically; every subsequent `/sign-up/email` call (whether from `/create-account`'s OAuth-end-user flow or a raw API call) gets `role: "user"`, enforced in `databaseHooks.user.create.before`, also in `shared/auth/src/core/permissions.ts`, checking `ctx.context.adapter.count({ model: "user" })` rather than trusting anything client-supplied. This is what makes public self-signup for OAuth end-users safe: a `user`-role account genuinely cannot reach `_workspace` regardless of how it was created.

**`auth.ts` (app root) is a thin, mostly-static call into the shared `createAuth(...)` factory** (`shared/auth/src/index.ts`, the `@infra/auth` package) — it supplies only this app's own env bindings (`baseURL`, `database`, `cache`, `rateLimit`, `oauth: { loginPage, consentPage, signUpPage, scopes, resources }`) and its own custom plugin (`resources(...)`, see below), plus `isAdminTier` for that plugin's injected `isAdmin` callback. `appName`, fixed admin/user `roles`, `trustedOrigins`, and every core sign-in plugin (`emailAndPassword`, `twoFactor`, `passkey`, `jwt` with `disableSettingJwtHeader: true` and `disabledPaths: ["/token"]`, required per better-auth's own JWT-plugin docs for "OAuth Provider Mode," it prevents the plain JWT plugin's `/token` endpoint from letting any authenticated session mint a JWT that bypasses the OAuth consent/scope flow entirely) all live in `shared/auth/src/index.ts`/`config.ts` instead, not `awaited` from anywhere at request or boot time there either. `oauthProvider` is also registered in `shared/auth/src/config.ts` (see Console below). `admin`/`username`/`magicLink`/`apiKey`/`anonymous`/`phoneNumber`/`emailOTP` were either never built or were built then removed entirely as deliberate scope decisions; self-hosters who want any of these back can add the plugin themselves the same way `twoFactor`/`passkey` are already wired.

**Custom (non-better-auth-shipped) plugins live in `plugins/<name>/` at the monorepo root**, extracted so other apps can call them too via a client plugin, not just this app's in-process `auth.api.*`. One: `@infra/r2` (object storage), registered in this app's own `auth.ts`'s `plugins` array, imported from the workspace package rather than a relative path. The identity/application layer that used to be a third custom plugin (`applications`, SSH-deploy-key style ECDSA identity) was deleted entirely and replaced by `@better-auth/oauth-provider`, a real spec-compliant OAuth 2.1/OIDC provider, see Console below.

**`@infra/r2` (`plugins/r2/`, monorepo root): a real, generically reusable plugin, not this-app-specific.** Exported as `resources({ binding, isAdmin })` (renamed from `r2Provider`), where `binding` is an `R2Bucket` and `isAdmin: (role) => boolean` is infra's own `isAdminTier`, both passed in by the caller (`resources({ binding: env.R2, isAdmin: isAdminTier })` in `auth.ts`) rather than the plugin importing `env`/infra's role model itself; this is what makes it a real plugin instead of code tied to this one app. `@infra/r2/client`'s `r2Client()` gives `www` (or any consumer) `authClient.r2.*`: plain better-auth path inference for `list`/`delete`, hand-written `getActions` for `uploadAvatar`/`uploadFile` (build the `FormData` from a raw `File` internally). Endpoints, all mounted under `/r2/*` except the CDN one: `uploadAvatar` (`POST /r2/avatar`, self-or-admin-on-behalf-of via an optional `userId` field in the multipart body; a different `userId` than the caller's own requires `isAdmin`), `uploadFile` (`POST /r2/upload`, self-service), `listObjects` (`GET /r2/list?prefix=`, admin-only, calls `binding.list({ prefix, delimiter: "/" })` directly, R2's own S3-compatible mechanism, returns `delimitedPrefixes` (subfolders) separately from `objects` (files at exactly this level)), `deleteObjects` (`POST /r2/delete`, unified single/multiple/prefix delete; non-admins can only touch keys under their own `{userId}/` prefix, checked with `targetKeys.some((key) => !key.startsWith(ownPrefix))`), and `getCdnFile` (`GET /cdn/**:key`, fully public, no session, serves **any** key in the bucket by its exact path; there's no separate "download" endpoint, this is the one way to read object content back out, avatars and everything else alike). Response headers on the CDN endpoint: `Content-Type` from the object's stored metadata, `ETag` from `object.httpEtag`, `Cache-Control: public, max-age=31536000, stale-while-revalidate=60`, `X-Content-Type-Options: nosniff`. Allowlist, not denylist, for uploads: images (png/webp/jpg/svg) and docs (pdf/json), validated by sniffing the actual bytes (`sniff-file-type.ts`), never by trusting the extension or client-declared `Content-Type`. SVGs are sanitized on upload (`sanitize-svg.ts`, strips `<script>`/event-handler attributes). `MAX_FILE_BYTES`/`MAX_USER_QUOTA_BYTES` live in `constants.ts`; quota is computed on demand by listing a user's objects and summing sizes, never a separate counter, so it can't drift from what's actually in the bucket. `cdnUrl(baseURL, key, version)` in `index.ts` builds the public URL; `ctx.context.baseURL` already resolves to the full mounted base including `/api/auth`, not just the origin, a doubled-path bug this hit once and is worth remembering if a future endpoint builds a URL the same way.

**Console (`/console`): the OAuth 2.1 / OIDC provider admin surface, backed by `@better-auth/oauth-provider`, a real spec-compliant plugin, not the custom identity model this replaced.** `oauthProvider(...)` itself is registered in the shared `shared/auth/src/config.ts` (not this app), with `storeClientSecret: "hashed"`, `allowDynamicClientRegistration: false`, and `clientPrivileges: async ({ user }) => isAdmin(...)` hardcoded there; `loginPage: "/sign-in"`, `consentPage: "/consent"`, `signUp: { page: "/create-account" }`, and `scopes: ["openid", "profile", "email", "offline_access"]` are this app's own values, passed in via `auth.ts`'s `oauth: {...}` block and merged in by `shared/auth/src/index.ts`'s `createAuth(...)`. Regardless of which file owns which value: admin-created clients (via `adminCreateOAuthClient`, the Console UI's own create flow) have no session context to attach a `userId` to unless the caller *is* authenticated when creating (confirmed live: when an admin creates a client through their own session, `userId` **does** get set to that admin's id, not left null as might be assumed), so `clientPrivileges` is what lets *any* admin manage *any* client instance-wide rather than only the one they personally created — for listing, viewing, editing, and enabling/disabling. Rotating the secret and deleting a client are deliberately narrower: `rotateApp`/`removeApp` add their own extra check (`assertOwnsApp`, `domains/console/assert-owns-app.ts`) restricting those two specifically to the admin who created that client, a real product decision (not a plugin limitation) layered on top of the instance-wide model everything else uses. A client with no recorded `userId` (predates or bypassed the ownership model) falls back to manageable-by-any-admin for rotate/delete too, same as the no-check behavior before this existed.

Three things worth knowing about the plugin's real capabilities, all worked around in `domains/console/func.ts` — none of these are plugin bugs, they're either deliberate scoping this plugin version doesn't offer an admin-wide equivalent for, or a bug this codebase itself had and fixed:
1. **`getOAuthClient`/`rotateClientSecret`/`deleteOAuthClient` have no admin-scoped equivalent at all — this isn't a bug, the plugin's docs are explicit that all three are self-service, ownership-scoped endpoints** ("obtain client information owned by a specific user," "delete a user or organization's client"), the counterpart to `createOAuthClient`/`updateOAuthClient` the same way `adminCreateOAuthClient`/`adminUpdateOAuthClient` are the counterpart to those two. The plugin only ever built admin-prefixed variants for create and update; there is no `adminGetOAuthClient`, `adminRotateClientSecret`, or `adminDeleteOAuthClient` anywhere in this package (confirmed by enumerating every `/admin/oauth2/*` and `/oauth2/*` route the plugin registers, not assumed). Their handlers check `client.userId !== session.user.id` unconditionally — by design, since they're for a client's own registrant, not an instance-wide admin — so an admin who didn't personally create a given client gets `UNAUTHORIZED` calling any of the three, regardless of what `clientPrivileges` says (confirmed by reading `getClientEndpoint`/`rotateClientSecretEndpoint`/`deleteClientEndpoint` directly in `@better-auth/oauth-provider`'s `dist/authorize-*.mjs`). `getOAuthClients` (plural) isn't a usable substitute for listing either, ownership check or not: its handler is hardcoded to `where: [{field: "userId", value: session.user.id}]`, "list my own clients," the wrong shape for an admin-wide console listing on its own terms. `listApps`/`findApp` go straight to `ctx.adapter.findMany`/`findOne` instead (matching `setAppActive`'s existing pattern, see gap 3 below): `AdminMiddleware` already guarantees the caller is admin, and there's no admin-scoped endpoint to call in the first place, not one being bypassed. `rotateApp`/`removeApp` also go straight to the adapter for the same underlying reason, but additionally now enforce their *own* creator-only restriction (`assertOwnsApp`) on top — a deliberate product choice, not something the plugin gap forced. Rotation re-implements the plugin's own secret hashing (SHA-256, base64url, no padding) using the exact same public `@better-auth/utils/hash` + `@better-auth/utils/base64` functions the plugin imports internally, confirmed correct end-to-end by rotating a real client's secret and using it in a real `/oauth2/token` `client_credentials` exchange, not just unit-tested against the hash function in isolation.
2. **The plugin declares `redirectUris`/`postLogoutRedirectUris`/`grantTypes`/`scopes` as `type: "string[]"` and `metadata` as `type: "json"`**: better-auth's adapter deserializes those into real arrays/objects itself before a raw `ctx.adapter.*` call ever sees them. An earlier version of `domains/console/func.ts` ran its own `JSON.parse` on top of that (assuming the adapter handed back raw stored strings), which silently discarded every scope/grant-type/redirect-uri/framework value on every read: `JSON.parse` on an already-parsed array coerces it to a comma-joined string first, that's invalid JSON, the parse throws, and the catch block returned `[]`. `toAppDetail` in `domains/console/func.ts` now trusts the adapter's own deserialization directly (`row.scopes ?? []`, not `parseJsonArray(row.scopes)`). Worth remembering for any future plugin schema field declared `string[]`/`json`: a raw adapter read already gives you the real type, don't re-parse it.
3. **Neither `adminCreateOAuthClient` nor `adminUpdateOAuthClient` has a `disabled` field on its body schema, in either direction** — confirmed by reading both bodies directly in the installed package (`authorize-*.mjs`), not just the docs, which only show a handful of illustrative fields rather than the exhaustive list. There is no endpoint anywhere in this plugin that lets an admin toggle a client's `disabled` state. `setAppActive` bypasses the plugin with a direct `ctx.adapter.update({ disabled: !data.active })` because there is genuinely nothing else to call.

`createAppSchema.redirect_uris` and `updateAppSchema.redirect_uris`/`post_logout_redirect_uris` both validate against `SafeUrlSchema` (imported from `@better-auth/core/utils/redirect-uri`, the exact rule the plugin itself enforces: requires HTTPS except for loopback hosts, rejects fragments and dangerous schemes, reused rather than reimplemented, per the doc comment in that package's own source). `createAppSchema.redirect_uris` deliberately has **no** `.min(1)`, unlike `updateAppSchema`'s: the create form lets the field come through empty on purpose, and `createApp`'s handler falls back to a `PENDING_REDIRECT_URI` sentinel (`http://127.0.0.1/pending`, a loopback host so it passes `SafeUrlSchema`) when that happens; adding `.min(1)` there once by mistake blocked that exact fallback path with a validation error.

`/console` is a folder route (`route.tsx` admin-tier guard, `index.tsx` the list table via `domains/console/views/list-applications.tsx`, `$client_id/index.tsx` a unified create/edit form; the literal string `"create-oauth2"` as the `$client_id` param is the sentinel for "this is the create flow," `$client_id/route.tsx`'s loader skips the DB lookup for it). The detail page reads `useApp(clientId)` (`domains/console/use-app.ts`, wrapping `useSuspenseQuery(appOptions(clientId))`), not `Route.useLoaderData()`, since admin actions can mutate this data live while the page stays open. A one-time client secret (from create or rotate) is passed through a `?secret=` search param and cleared from the URL immediately after being read into local state, so it never lingers in browser history.

**A component render function that reads `window` directly crashes SSR, not just "works differently."** Guard any client-only read (`typeof window !== "undefined" ? window.location.origin : ""`) if there's any chance the component renders on the server first; this has bitten more than one place in this app's history.

**The dashboard's own sign-in (`Login`, `domains/auth/views/login.tsx`) is email+password only, always**, regardless of which other methods exist. Those methods (twoFactor as a second factor aside, passkey) exist for the OAuth end-user sign-in flow this project now does build (`/sign-in` is also `oauthProvider`'s `loginPage`), not as options on the admin dashboard's own form: admin access can never depend on a method, so it isn't given the choice.

**Widgets, the only reusable pieces meant to be imported from anywhere, now live in `@infra/ui`'s `widgets/`** (`shared/ui/src/widgets/`, imported as `@infra/ui/widgets/tables`, `@infra/ui/widgets/blocks`, `@infra/ui/widgets/dialog-widget`), not in infra:
- `widgets/tables/`: `DataTable` (search, per-column filters auto-detected from data shape, column visibility, sort, row selection + bulk actions, pagination, built on `@tanstack/react-table` v9's real API) and `DataTablePagination`. `aria-label` is a **required** prop (react-aria's underlying grid throws a dev warning without one). `footer?: (columnCount: number) => ReactNode` renders inside the table's own `<tfoot>` (via `components/ui/table.tsx`'s `TableFooter`, which wraps react-aria-components' own `TableFooter`, a genuinely separate footer region from the sortable/selectable body rows, not a synthetic row mixed into the real row model).
- `widgets/blocks/`: the `useAppForm`/`withForm` TanStack Form setup (field components including `radioCard`, with an optional `icon?: ReactNode`, added for Console's framework picker, `multiselect`, `switch`, and the submit button) used by every form in the app.
- `widgets/dialog-widget/`: `DialogWidget`, the one entry point for a drawer-style dialog.

Feature-specific things that use a widget but aren't reusable themselves live in `components/dashboard/<feature>/`, not in `widgets/`.

**UI components follow shadcn's `aria-lyra` style** (`@infra/ui`'s own `components.json`): built on `react-aria-components`, not Radix. **Never hand-author a file under `@infra/ui`'s `components/`**, always `bunx shadcn add <component>` from within `shared/ui/`. The generated API frequently differs from shadcn's default/Radix registry, e.g. `DropdownMenuTrigger` is the *root* wrapping both the trigger element and `DropdownMenu` (the content), not just the trigger button.

**Dates go through `date-fns`**, not `Date.prototype.toLocaleString`/`toLocaleDateString`. See any list/detail component for the `format(date, "PPP")` convention.

**Styling is Tailwind v4, CSS-first, and lives in `@infra/ui`, not infra.** There is no `tailwind.config.js`; theme tokens, the `container` utility, and custom utilities (`no-scrollbar`, `dualTone`) are all defined in `@infra/ui`'s `src/globals.css` (imported here as `@infra/ui/globals.css?url` in `__root.tsx`) via `@theme inline` and `@utility`. Colors are OKLCH and swap via a `.dark` class selector, even though both apps currently force dark. `@infra/ui/typeset.css` holds prose/typography rules. infra keeps its own `tailwindcss`/`@tailwindcss/vite` devDependency regardless; Tailwind still needs to scan infra's own route/domain-view files for the utility classes used directly in their JSX.

**Path alias**: `@/*` maps to `./*`, the app root itself (set in `tsconfig.json`'s `paths`), not `src/*` — `@/domains/...`, `@/auth` (→ `auth.ts`), `@/middleware`, `@/components/...` all resolve directly off the app root; only routing (`routeTree.gen.ts`, `router.tsx`, `routes/`, `server.ts`, `start.ts`) actually lives under `src/`. This is infra's own source only; anything from the shared UI kit is imported via `@infra/ui/...` instead (see the monorepo root `CLAUDE.md`), not through `@/`.

**Responsive breakpoints diverge from Tailwind's defaults**: `@infra/ui`'s `shared/ui/src/lib/use-media-query.ts` (moved out of infra-local `lib/` along with the rest of the reusable UI layer) defines its own `BREAKPOINTS` map (`md: 800`, plus `3xl: 1600` / `4xl: 2000` beyond Tailwind's stock scale). `useIsMobile` itself is hardcoded to `(max-width: 768px)` rather than using the `md` entry from that same map.

## Lint/format notes

- Linting and formatting both went from per-package ESLint/Prettier to one root-level Biome config (`biome.json`), run from the monorepo root, not from inside `infra/`. See the root `CLAUDE.md` for what it covers and which rules are deliberately off. `typescript-eslint`'s TS-version compatibility window (the reason `bun run lint` used to fail outright here) no longer applies since ESLint is gone; TypeScript is on the `^7` line.
- No semicolons, double quotes, 4-space indent, `printWidth: 100` still hold, now enforced by Biome's formatter instead of Prettier. Biome has no Tailwind class-sorting equivalent to `prettier-plugin-tailwindcss` wired in yet, so class order inside `className` strings is no longer auto-sorted.

## Known issues / cleanup backlog

Flagged but not yet done, read before assuming either is already handled:

- **The Cloudflare Vite plugin's local AI-agent observability capture** (`X_LOCAL_OBSERVABILITY` / `X_LOCAL_EXPLORER`, controlled via `.env.local`, not a `package.json` script flag; `bun run dev` is just `vite dev --port=3000`). When enabled and running inside an AI coding agent, the plugin captures every internal sub-operation, KV call, D1 call, and internal module fetch during SSR as a span in a local SQLite-backed store, queryable at `/cdn-cgi/local/explorer/api/local/observability/query` (also useful directly: `/cdn-cgi/local/explorer/api/d1/database/<id>/raw` runs arbitrary SQL against the real local D1 database, handy for verifying state without going through the app's own code paths). In sustained use this has generated 150,000+ spans and made requests hang indefinitely once enough accumulated. It's tied to request volume, not idle time. If local dev becomes unresponsive during a long session, this is the first thing to check: either lower the volume of requests being sent, or restart the dev server to clear the accumulated span store. This is unrelated to and doesn't touch `wrangler.jsonc`'s `observability` block, which governs the real deployed Worker.
