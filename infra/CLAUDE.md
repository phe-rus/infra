# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

This repo is both a self-hosted authentication backend (better-auth, on Cloudflare Workers + D1 + KV + R2) and its admin dashboard: one TanStack Start (React 19 + SSR) app, one Worker, serving both the dashboard UI and better-auth's HTTP API. It also runs a real OAuth 2.1 / OIDC provider (`@better-auth/oauth-provider`), so connected applications can use this instance as their identity provider, and a PawaPay-backed payments layer for mobile-money deposits/payouts/refunds. See `README.md` for what the project is and why it exists; this file is the technical map.

Package manager: **bun** (`bun.lock` is the lockfile, gitignored, it's autogenerated by `bun install`, never committed; `.vscode/settings.json` pins `npm.packageManager` to `bun`).

## Commands

```bash
bun install       # install dependencies
bun run dev       # start dev server on port 3000
bun run build     # production build (vite build)
bun run deploy    # build and deploy to your Cloudflare account (wrangler deploy)
bun run preview   # preview a production build
bun run test      # run the vitest suite once (vitest run)
bun run lint      # eslint
bun run format    # prettier --write across ts/tsx/js/jsx
bun run check     # prettier --check (no writes)
bun run typecheck # tsc --noEmit
bun run type-gen  # wrangler types, regenerates worker-configuration.d.ts from wrangler.jsonc + .env.local
```

`bun run dev` needs a `.env.local` file (gitignored) with real secrets, copy `.env.example` and fill it in. `worker-configuration.d.ts` (the `Env` type) and `src/routeTree.gen.ts` (file-based routing) are both gitignored and autogenerated: `worker-configuration.d.ts` by `bun run type-gen` whenever `wrangler.jsonc` or `.env.local` change, `routeTree.gen.ts` automatically by the `@tanstack/router-plugin` Vite plugin on dev/build. Never hand-edit either.

There are no test files in the repo yet and no `vitest.config.*`, vitest currently runs against Vite's default config. When adding tests, run a single file with `bunx vitest run path/to/file.test.tsx` or a single test name with `bunx vitest run -t "test name"`.

## Architecture

**Routing is file-based and code-generated.** Routes live under `src/routes/`; `src/routeTree.gen.ts` is auto-generated, never hand-edit it. Four pathless layout routes sit at the top level:
- `_auth` (`src/routes/_auth/route.tsx`): `sign-in`, `setup`, `forgot-password`, `reset-password`, redirects away if a session already exists. `setup` is two phases toggled by one `initialized` boolean, not a wizard: run pending migrations, then create the first (owner) user, name/email/password only. `create-account` (self-service signup for OAuth end-users) and `consent` (the OAuth authorize-flow consent screen) are **not** infra routes: `oauthProvider`'s `loginPage`/`consentPage`/`signUp.page` in `src/auth/index.ts` all point at `${env.WWW_URL}/...`, so `www` hosts those pages; infra only keeps the admin-facing `/setup`, `/sign-in`, and `/forgot-password`/`/reset-password`. See the monorepo root `CLAUDE.md` for the `infra`/`www` split.
- `_workspace` (`src/routes/_workspace/route.tsx`): everything behind the admin `Dashboard` shell. `beforeLoad` does two checks in order: is there a session (else redirect to `/sign-in`), then is this session's role allowed to access the instance at all (else redirect to `/unauthorized`), see **Access model** below.
- `_account` (`src/routes/_account/route.tsx`): the one non-admin authenticated shell, added for the self-service payments page. `beforeLoad` requires *any* session (redirects to `/sign-in` otherwise) but does **not** check `isAdminTier`; this is the only place in the app a plain `user`-role account gets a real page. Mirrors `_workspace/route.tsx`'s own session-check shape but deliberately drops the tier check.
- `_protected` (`src/routes/_protected/route.tsx`): just `unauthorized.tsx`, deliberately outside `_workspace` so it renders without the `Dashboard` shell.

Current `_workspace` pages: `index` (home/business stats), `users`, `storage`, `console` (folder route), `billing` (folder route), `logs` (a placeholder page: the route and its sidebar link both exist, but it doesn't render real log data yet). Current `_account` pages: `payments` (self-service deposit form + own payment history). There is no self-service API keys feature: it was built, then removed entirely, a deliberate scope decision; don't reintroduce it without that decision being revisited. Team & Roles (an "allowed roles" list, then custom roles) was removed the same way: access is fixed code now (see Access model), nothing left to manage on a page.

**A flat route file's `RouteComponent` *is* the page; there is no separate page-wrapper component.** State, handlers, mutation hooks, a `useMemo(() => [...], [])`-wrapped column array, all of it lives directly in `RouteComponent`; `users.tsx`, `storage.tsx` are this shape. **A multi-page section is a folder route instead**, mirroring `_workspace/route.tsx`'s own layout shape: `console/` and `billing/` each have a `route.tsx` (admin gate + a loader doing the `ensureQueryData` calls shared by every child, `component` is just `<Outlet />`, no chrome of its own since each child page owns its own header), an `index.tsx` (the list page), and a detail page (`console/$client_id/`, `billing/$paymentId.tsx`) that reads its param and renders a receipt/detail view. `src/features/<domain>/` holds only the individual pieces a page composes (`list-users.tsx`, `list-payments.tsx`, `refund-dialog.tsx`, ...), flat, no nested `components/` subfolder, no generic `-section`/`-drawer` suffixes, named after the action or resource it's built around, matching its `kit/<domain>/` counterpart file-for-file wherever one exists. **`features/<domain>/index.ts` (never `.tsx`) is a plain re-export barrel over those pieces**, nothing else: it holds no component of its own, no JSX; a domain that hasn't outgrown a single file yet doesn't get one. `src/features/` is not where `components/` (shadcn primitives) or `widgets/` (both now live in `@infra/ui`, see the monorepo root `CLAUDE.md`) or `components/dashboard/` (the shell, still infra-local) belong.

The one real exception is something genuinely reused by more than one call site. That's `@infra/ui`'s `widgets/` now (`DataTable`, the `useAppForm` blocks setup, `DialogWidget`, see the root `CLAUDE.md`), imported via `@infra/ui/widgets/tables`, `@infra/ui/widgets/blocks`, `@infra/ui/widgets/dialog-widget`, never inlined. The one thing still local to infra under `src/components/widgets/` is `framework-icon.tsx`: it's tied to infra's own `kit/console` `Framework` type, so it can't move to the app-agnostic shared package. `components/dashboard/` currently holds only the `Dashboard` shell itself. A feature-specific standalone dialog with only one caller is not a `components/dashboard/` thing (that folder is for the shell), it lives flat in `features/<domain>/` per the note above; when in doubt for a small page, inline it into the route first, and only reach for `features/` once it's genuinely too large to.

**Shell / entry points**: `src/start.ts` creates the TanStack Start server instance and registers CSRF middleware scoped only to server-function requests. `src/router.tsx` builds the router and wraps it with `QueryProvider`. `src/routes/__root.tsx` renders the actual `<html>` document (theme is hardcoded to `dark` via a static class, not runtime-toggled), does the root `beforeLoad` (session + setup status), and mounts `TanStackDevtools`. `src/server.ts` is the raw Cloudflare Worker `fetch` export sitting in front of the TanStack Start handler; it intercepts `.well-known/openid-configuration`, `.well-known/oauth-authorization-server`, and `/jwks` specifically to add CORS headers (`Access-Control-Allow-Origin: *`, `Access-Allow-Methods: GET`) those need but the app doesn't set by default, then falls through to `handler.fetch(...)` for everything else.

**Query client is a client/server-aware singleton** (`src/lib/queryClient.tsx`): on the client, `getContext()` reuses one module-level `QueryClient` across navigations; on the server it always constructs a fresh one per request (standard SSR-safe pattern, don't change this to a plain module-level singleton, it would leak state across requests). The `QueryProvider` unconditionally mounts `TanStackDevtools` (Router + Query panels). It is not gated behind a dev/prod check, so don't add one without checking whether that's intentional for this project.

**`queryClient.tsx` overrides `focusManager` to always report focused**; `networkMode` and `retryDelay` are both back to react-query's defaults. The one non-default piece left is queries' `retry`: a predicate that skips retrying on a `401`/`403` status and otherwise retries up to twice (mutations still default to `retry: 0`). The `focusManager.setEventListener` override still means `refetchOnWindowFocus` is inert app-wide; acceptable here since every mutation already invalidates its own affected queries explicitly.

**Errors surface as toasts globally**: the `QueryCache` in `queryClient.tsx` has an `onError` that calls `t.error(...)` (from `@infra/ui/components/ui/sonner`, backed by `goey-toast`) for every failed query except `AbortError`. Individual query hooks generally don't need their own error handling/toast logic for reads, it happens centrally.

**Every mutation hook builds on `useAppMutation` (`src/kit/shared/use-app-mutation.ts`)** instead of calling `useMutation` directly. It reads the query client via `useQueryClient()` rather than each hook grabbing its own reference, takes an `invalidates` array of query keys and fires `invalidateQueries` for each one in `onSettled`, and applies the standard success/error toast pair from `successMessage`/`successDescription`/`errorMessage`. `optimisticUpdate`'s `cancelQueries` call in `onMutate` **is** awaited (narrows the window where an in-flight refetch could land after the optimistic write and clobber it). The optimistic rollback in `onError` only restores the pre-mutation snapshot if the cache still holds exactly what this mutation wrote, skipping it if a second mutation on the same key wrote something newer in the meantime. See any `kit/<domain>/use-*.ts` file for the shape. The exceptions are sign-in/sign-out/complete-setup (`kit/auth/use-sign-in.ts`, `use-logout.ts`, `use-complete-setup.ts`), which swap out the session identity entirely and need `q.clear()` plus a navigation rather than a targeted invalidate, so they still call `useMutation` directly against the module-level `getContext()` client.

A query with a dynamic filter that can change while its own data stays visible (the wallet-balances "preferred currency" picker, `kit/payments/get-payment.ts`'s `walletBalancesOptions`) sets `placeholderData: keepPreviousData`, otherwise switching the filter would suspend the whole section back to its fallback instead of just quietly refetching in the background.

**Data flow: loader `ensureQueryData` + `useSuspenseQuery`, not `Route.useLoaderData()`, for anything a mutation can change.** The loader prefetches into the query cache so SSR/first paint has data; the component then subscribes via `useSuspenseQuery(sameQueryOptions())` so that a mutation's `invalidateQueries` actually triggers a re-render. `Route.useLoaderData()` is a one-time snapshot, fine for values a form seeds itself with once and forgets about, wrong for anything meant to stay live (a table of users, a payments list).

**`src/kit/` is the one place all backend-adjacent code lives, one folder per domain**: `kit/auth/` (session/sign-in/setup/consent), `kit/users/`, `kit/storage/` (the R2 browser), `kit/console/` (OAuth client/application management), `kit/payments/` (PawaPay deposits/payouts/refunds/config/balances), `kit/stats/`, `kit/middleware/` (`AdminMiddleware`/`OwnerMiddleware`/`SessionMiddleware`), `kit/shared/` (cross-cutting helpers with no one domain), plus `kit/index.ts`, a flat barrel re-exporting every domain. **There is no shared `kit/schemas.ts` or `kit/types.ts`**: every domain owns its own `schema.ts` (every zod schema for that domain) with types colocated in `fnc.ts` (`z.infer<typeof theSchema>`, or an explicit composite/intersection type when no single schema or upstream better-auth type covers the shape, for example `kit/users/fnc.ts`'s `ListedUser = UserWithRole & { twoFactorEnabled?: boolean }`, needed because `UserWithRole` doesn't reflect plugins actually registered on this instance). `src/auth/` (the better-auth config and its custom plugins) and `src/components/` are deliberately outside `kit/`, this is about the server-function/hooks/schema/type layer, not the auth library setup or the UI.

**Inside a domain folder, `fnc.ts` holds every `createServerFn(...)` for that domain and nothing else** (no `Fn` suffix on the exported name: `createUser`, `initiateDeposit`, `findApp`). Everything that *wraps* those functions for the client lives outside `fnc.ts`, split by what kind of React Query hook it produces: a `get-<name>.ts` file holds `*Options()` factories plus their `useQuery`/`useSuspenseQuery` hooks (`get-payment.ts`: `paymentsOptions`/`usePayments`, `myPaymentsOptions`/`useMyPayments`, `paymentConfigOptions`/`usePaymentConfig`, `walletBalancesOptions`/`useWalletBalances`, `paymentOptions`/`usePayment`, all in one file since they're all reads for the same domain); a `use-<name>.ts` file holds one or more `useMutation`/`useAppMutation` hooks. Every domain folder has an `index.ts` barrel doing `export * from "./fnc"`, `"./schema"`, plus one `export *` per `get-*`/`use-*` file; import from `@/kit/<domain>`, not the individual file, unless you're inside that same folder, where relative imports between colocated files (typically `import { x } from "./fnc"`) are normal. Inside a handler that needs the request's headers for an `auth.api.*` call, use `getRequestHeaders()` from `@tanstack/react-start/server` (synchronous, no `await`), assigned to its own `const headers = getRequestHeaders()` line, not called inline in the call args. Middleware bodies, by contrast, already receive `request` as a parameter from the framework and should use `request.headers` directly. A handler gated by `AdminMiddleware`/`OwnerMiddleware`/`SessionMiddleware` never re-checks `if (!sessions)`, the middleware already guarantees a session (and the required role tier, if any) before the handler runs. A check that needs the *validated body* (not just the session) can't live in a `createMiddleware()` at all: TanStack Start always runs `.middleware([...])` before the server function's own `.validator()`, so a middleware only ever sees the raw unvalidated body. Those live as plain guard functions in `kit/shared/` instead (`assert-can-assign-role.ts`'s `assertCanAssignRole`).

**A `fnc.ts`-consuming file's internal order is imports, then anything local and not itself a server function** (types, plain consts, helper functions), **then the `createServerFn` exports last**. A file that accepts `FormData` as its input uses a plain function as its `.validator()`, not a zod schema: TanStack Start detects `data instanceof FormData` client-side and sends it as the raw fetch body instead of JSON-serializing it, and hands that same `FormData` instance straight to `.validator()` unparsed server-side, so the validator does its own `.get()` extraction.

**Every mutating `auth.api.*` call that needs to propagate cookies forwards its response headers**, not just Set-Cookie. `src/lib/forward-headers.ts`'s `forwardAuthHeaders(headers)` wraps `setResponseHeaders()` to propagate the entire header set better-auth returns. Call the `auth.api.*` method with `returnHeaders: true` and pass its `headers` straight to `forwardAuthHeaders`. The response shape changes when `returnHeaders: true` is added: an endpoint that normally returns a real payload gets wrapped as `{ response: T, headers }`, while an endpoint with no meaningful body stays flat as `{ headers }`. Not every wrapped call needs this: `kit/console/fnc.ts`'s `rotateApp`/`removeApp` and `kit/payments/fnc.ts`'s reads all skip it because they go through a raw `ctx.adapter.*` call or don't set cookies.

**Every middleware lives in `src/kit/middleware/`, one file per middleware, with its own `index.ts` barrel**: `owner-middleware.ts` (`OwnerMiddleware`, owner only), `admin-middleware.ts` (`AdminMiddleware`, owner or admin), `session-middleware.ts` (`SessionMiddleware`, any authenticated user, no role/tier check at all). `SessionMiddleware` is what OAuth end-user flows (consent) and self-service payment actions (deposit, own payment history) build on; the one gate in the app a plain `user`-role account can pass. A middleware that gates access throws inside itself. `assertCanAssignRole` is not here despite being an authorization check too: it needs the validated body, so it lives in `kit/shared/` as a plain function instead.

**Access model** (`src/auth/utils/permissions.ts`): roles are the fixed three, `owner`/`admin`/`user`, built statically by `buildRoles()` and passed to better-auth's `admin` plugin in `src/auth/index.ts`. Dashboard access (`_workspace`) is owner/admin only, hardcoded; the plain `user` role can never pass it, full stop, not a configurable instance setting, but it *can* pass `_account` (session-only, see the routing note above), which is where the self-service payments page lives. Within the dashboard, owner and admin are further distinguished: admin has broad access (add users, view everything, remove any non-owner account, manage every OAuth application, initiate deposits/payouts on the Billing page) but only owner can promote/demote roles, remove another owner, ban/unban, reset passwords, or impersonate. `isAdminTier(role)`/`isOwner(role)` are the single source of truth for the tier check; never write `role !== "owner" && role !== "admin"` by hand.

The first user to ever sign up (via `/setup`) becomes `owner` automatically; every subsequent `/sign-up/email` call (whether from `/create-account`'s OAuth-end-user flow or a raw API call) gets `role: "user"`, enforced in `databaseHooks.user.create.before` in `src/auth/index.ts`, checking `ctx.context.adapter.count({ model: "user" })` rather than trusting anything client-supplied. This is what makes public self-signup for OAuth end-users safe: a `user`-role account genuinely cannot reach `_workspace` regardless of how it was created.

**`src/auth/index.ts` is now entirely static** except for the payment/OAuth-provider plugins' own KV/env wiring (see below). `appName`, `security`, `roles` (fixed owner/admin/user), and `trustedOrigins` are all plain constants or env vars, not `await`ed from anywhere at request or boot time. Sign-in methods (`emailAndPassword` always on, plus `twoFactor`, `passkey`) are registered unconditionally in the `plugins` array. Also registered: `jwt` (with `disableSettingJwtHeader: true`, and `disabledPaths: ["/token"]` set at the top level of the config, required per better-auth's own JWT-plugin docs for "OAuth Provider Mode," it prevents the plain JWT plugin's `/token` endpoint from letting any authenticated session mint a JWT that bypasses the OAuth consent/scope flow entirely) and `oauthProvider` (see Console below). `admin`/`username`/`magicLink`/`apiKey`/`anonymous`/`phoneNumber`/`emailOTP` were either never built or were built then removed entirely as deliberate scope decisions; self-hosters who want any of these back can add the plugin themselves the same way `twoFactor`/`passkey` are already wired.

**Custom (non-better-auth-shipped) plugins now live in `plugins/<name>/` at the monorepo root**, not under `infra/src/auth/plugins/`, extracted so `www` can call them too via a client plugin, not just this app's in-process `auth.api.*`. Two: `@infra/r2` (object storage) and `@infra/payment` (PawaPay integration), both registered in `auth/index.ts`'s `plugins` array the same way as the shipped ones, imported from the workspace package rather than a relative path. The identity/application layer that used to be a third custom plugin (`applications`, SSH-deploy-key style ECDSA identity) was deleted entirely and replaced by `@better-auth/oauth-provider`, a real spec-compliant OAuth 2.1/OIDC provider, see Console below.

**`@infra/r2` (`plugins/r2/`, monorepo root): a real, generically reusable plugin, not this-app-specific.** Exported as `r2Provider({ binding, isAdmin })`, where `binding` is an `R2Bucket` and `isAdmin: (role) => boolean` is infra's own `isAdminTier`, both passed in by the caller (`r2Provider({ binding: env.STORAGE, isAdmin: isAdminTier })` in `auth/index.ts`) rather than the plugin importing `env`/infra's role model itself; this is what makes it a real plugin instead of code tied to this one app. `@infra/r2/client`'s `r2Client()` gives `www` (or any consumer) `authClient.r2.*`: plain better-auth path inference for `list`/`delete`, hand-written `getActions` for `uploadAvatar`/`uploadFile` (build the `FormData` from a raw `File` internally). Endpoints, all mounted under `/r2/*` except the CDN one: `uploadAvatar` (`POST /r2/avatar`, self-or-admin-on-behalf-of via an optional `userId` field in the multipart body; a different `userId` than the caller's own requires `isAdmin`), `uploadFile` (`POST /r2/upload`, self-service), `listObjects` (`GET /r2/list?prefix=`, admin-only, calls `binding.list({ prefix, delimiter: "/" })` directly, R2's own S3-compatible mechanism, returns `delimitedPrefixes` (subfolders) separately from `objects` (files at exactly this level)), `deleteObjects` (`POST /r2/delete`, unified single/multiple/prefix delete; non-admins can only touch keys under their own `{userId}/` prefix, checked with `targetKeys.some((key) => !key.startsWith(ownPrefix))`), and `getCdnFile` (`GET /cdn/**:key`, fully public, no session, serves **any** key in the bucket by its exact path; there's no separate "download" endpoint, this is the one way to read object content back out, avatars and everything else alike). Response headers on the CDN endpoint: `Content-Type` from the object's stored metadata, `ETag` from `object.httpEtag`, `Cache-Control: public, max-age=31536000, stale-while-revalidate=60`, `X-Content-Type-Options: nosniff`. Allowlist, not denylist, for uploads: images (png/webp/jpg/svg) and docs (pdf/json), validated by sniffing the actual bytes (`sniff-file-type.ts`), never by trusting the extension or client-declared `Content-Type`. SVGs are sanitized on upload (`sanitize-svg.ts`, strips `<script>`/event-handler attributes). `MAX_FILE_BYTES`/`MAX_USER_QUOTA_BYTES` live in `constants.ts`; quota is computed on demand by listing a user's objects and summing sizes, never a separate counter, so it can't drift from what's actually in the bucket. `cdnUrl(baseURL, key, version)` in `index.ts` builds the public URL; `ctx.context.baseURL` already resolves to the full mounted base including `/api/auth`, not just the origin, a doubled-path bug this hit once and is worth remembering if a future endpoint builds a URL the same way.

**Console (`/console`): the OAuth 2.1 / OIDC provider admin surface, backed by `@better-auth/oauth-provider`, a real spec-compliant plugin, not the custom identity model this replaced.** `oauthProvider(...)` in `auth/index.ts`: `loginPage: "/sign-in"`, `consentPage: "/consent"`, `signUp: { page: "/create-account" }`, `storeClientSecret: "hashed"`, `scopes: ["openid", "profile", "email", "offline_access", "payments"]`, and `clientPrivileges: async ({ user }) => isAdminTier(...)`: admin-created clients (via `adminCreateOAuthClient`, the Console UI's own create flow) have no session context to attach a `userId` to unless the caller *is* authenticated when creating (confirmed live: when an admin creates a client through their own session, `userId` **does** get set to that admin's id, not left null as might be assumed), so `clientPrivileges` is what lets *any* admin/owner manage *any* client instance-wide rather than only the one they personally created.

Two real gotchas the plugin itself has, both worked around in `kit/console/fnc.ts`:
1. **`rotateClientSecret`/`deleteOAuthClient` (the plugin's own non-admin-prefixed endpoints) re-check ownership via `client.userId` *after* `clientPrivileges` already passed**, and unconditionally reject if `userId` doesn't exactly match the caller's own id (or is unset with no `clientReference` configured). This means an admin who didn't personally create a given client gets `UNAUTHORIZED` trying to rotate or remove it, even though `clientPrivileges` said they're allowed, confirmed by reading the plugin's bundled source (`deleteClientEndpoint`/`rotateClientSecretEndpoint` in `@better-auth/oauth-provider`'s `dist/index.mjs`), not assumed. `rotateApp`/`removeApp` bypass both endpoints entirely via a direct `ctx.adapter.delete`/`ctx.adapter.update` call instead (matching `setAppActive`'s existing pattern): `AdminMiddleware` already guarantees the caller is admin/owner, so there's no privilege check left to replicate, just the actual work. Rotation re-implements the plugin's own secret hashing (SHA-256, base64url, no padding) using the exact same public `@better-auth/utils/hash` + `@better-auth/utils/base64` functions the plugin imports internally, confirmed correct end-to-end by rotating a real client's secret and using it in a real `/oauth2/token` `client_credentials` exchange, not just unit-tested against the hash function in isolation.
2. **The plugin declares `redirectUris`/`postLogoutRedirectUris`/`grantTypes`/`scopes` as `type: "string[]"` and `metadata` as `type: "json"`**: better-auth's adapter deserializes those into real arrays/objects itself before a raw `ctx.adapter.*` call ever sees them. An earlier version of `kit/console/fnc.ts` ran its own `JSON.parse` on top of that (assuming the adapter handed back raw stored strings), which silently discarded every scope/grant-type/redirect-uri/framework value on every read: `JSON.parse` on an already-parsed array coerces it to a comma-joined string first, that's invalid JSON, the parse throws, and the catch block returned `[]`. `toAppDetail` in `kit/console/fnc.ts` now trusts the adapter's own deserialization directly (`row.scopes ?? []`, not `parseJsonArray(row.scopes)`). Worth remembering for any future plugin schema field declared `string[]`/`json`: a raw adapter read already gives you the real type, don't re-parse it.

`createAppSchema.redirect_uris` and `updateAppSchema.redirect_uris`/`post_logout_redirect_uris` both validate against `SafeUrlSchema` (imported from `@better-auth/core/utils/redirect-uri`, the exact rule the plugin itself enforces: requires HTTPS except for loopback hosts, rejects fragments and dangerous schemes, reused rather than reimplemented, per the doc comment in that package's own source). `createAppSchema.redirect_uris` deliberately has **no** `.min(1)`, unlike `updateAppSchema`'s: the create form lets the field come through empty on purpose, and `createApp`'s handler falls back to a `PENDING_REDIRECT_URI` sentinel (`http://127.0.0.1/pending`, a loopback host so it passes `SafeUrlSchema`) when that happens; adding `.min(1)` there once by mistake blocked that exact fallback path with a validation error.

`/console` is a folder route (`route.tsx` admin gate + shared loader, `index.tsx` the list table via `features/console/list-applications.tsx`, `$client_id/index.tsx` a unified create/edit form; the literal string `"create-oauth2"` as the `$client_id` param is the sentinel for "this is the create flow," `$client_id/route.tsx`'s loader skips the DB lookup for it). The detail page reads `appOptions(clientId)` via `useSuspenseQuery`, not `Route.useLoaderData()`, since admin actions can mutate this data live while the page stays open. A one-time client secret (from create or rotate) is passed through a `?secret=` search param and cleared from the URL immediately after being read into local state, so it never lingers in browser history.

**`@infra/payment` (`plugins/payment/`, monorepo root, folder renamed from `infra-payment`, the "infra-" prefix was redundant once it's a `plugins/` package): PawaPay mobile-money integration (deposits, payouts, refunds), sandbox-only so far.** `infraPayment({ apiToken, environment, cache, isAdmin, onPaymentCompleted? })`: `isAdmin: (role) => boolean` is infra's own `isAdminTier`; `onPaymentCompleted?: (email, receipt: PaymentReceiptInfo) => Promise<void>` is infra's own `sendPaymentReceiptEmail`, both injected rather than imported (same principle as `@infra/r2`, above); `onPaymentCompleted` is optional since not every self-hoster wants receipt emails. `@infra/payment/client`'s `paymentClient()` gives `authClient.pay.*` via plain inference (every endpoint is JSON in/out, no hand-written actions needed); `/pay/webhook` has no client method, PawaPay's servers call it directly. `cache` is a `KVNamespace` (the dedicated `PAYMENTS` binding in `wrangler.jsonc`, deliberately its own namespace rather than reusing `CACHE`, the one better-auth's own session/rate-limit machinery already uses, to keep blast radius and read/write volume separate). `client.ts`'s `PawaPayClient` wraps PawaPay's real v2 API (`https://api.sandbox.pawapay.io` / `https://api.pawapay.io`): `initiateDeposit`/`initiatePayout`/`initiateRefund` (all POST, caller-generated UUIDv4 ids, response `{status: ACCEPTED|REJECTED|DUPLICATE_IGNORED, failureReason?}`), `getActiveConfig`/`getWalletBalances`/`getPublicKeys`. One real bug this hit: PawaPay legitimately returns a `REJECTED` outcome with a non-2xx HTTP status (confirmed live: 400, with a real `{status:"REJECTED", failureReason}` body); `PawaPayClient`'s `request()` used to throw on any non-2xx, turning a normal business rejection into an unhandled 500. It now parses the body regardless of status and only throws if it doesn't look like a recognizable `{status: ...}` response.

Endpoints, mounted under `/pay/*`: `depositPayment` (`POST /pay/deposit`, any signed-in user, self-service; `clientId` in the body is which connected OAuth app requested it, if any, null for a dashboard-initiated deposit), `payoutPayment` (`POST /pay/payout`, admin/owner only, the platform cashing out), `refundPayment` (`POST /pay/refund`, admin/owner only, reverses a deposit; deliberately does **not** gate on this app's own locally-stored `status` column, since that can lag reality (the webhook that would flip `pending → completed` depends on PawaPay actually reaching this instance); PawaPay's own API is the real source of truth on whether a deposit is refundable, and rejects cleanly with a `failureReason` if it isn't), `paymentConfig` (`GET /pay/config`, any signed-in user, the deposit/payout/refund forms' country → provider picker, PawaPay's real active-configuration response trimmed down via `active-config.ts`'s `toPaymentCountryOptions` and cached in KV for 1 hour, populated lazily on whichever request hits a cold cache first, never pre-seeded), `walletBalances` (`GET /pay/balances`, admin/owner only, the platform's real PawaPay wallet balances; when `?currency=` is given, converts every balance into one combined total via `fx.ts`'s live USD-pivot rate table from `fawazahmed0/currency-api`, itself cached in KV for 12 hours), and `paymentWebhook` (`POST /pay/webhook`, fully public; every claim in the body is untrusted until its RFC-9421 signature checks out via `verify-signature.ts`).

**`purpose`/PawaPay's `customerMessage` field has a real constraint the schemas now enforce up front**: 4–22 characters, alphanumeric and spaces only (confirmed live: a hyphen and a 3-character string both got rejected by PawaPay's API before this was caught in `kit/payments/schema.ts`'s `purposeSchema`, at both the kit-schema layer and the plugin's own endpoint body schemas).

**RFC-9421 webhook verification (`verify-signature.ts`)**: algorithm `ecdsa-p256-sha256`. Steps: verify `Content-Digest` (sha-256/512 hash of the raw body) matches, reconstruct the RFC-9421 signature-base string from the components listed in the `Signature-Input` header (using the *actual* incoming header values, not hardcoded assumptions about which ones are covered), fetch PawaPay's public key by `keyid` from `GET /v2/public-key/http`, verify via Web Crypto (`ECDSA`/`SHA-256`, RFC 9421 ECDSA signatures are IEEE P1363 raw r‖s format, directly compatible with Web Crypto's native verify, no DER conversion needed). The endpoint sets `cloneRequest: true`; without it, better-call's router always calls `getBody()` internally before the handler runs regardless of a declared body schema, and by the time the handler tries to read `ctx.request` itself the stream is already locked (confirmed live: "This ReadableStream is currently locked to a reader"). With `cloneRequest: true`, better-call clones the request for its own internal parsing, leaving the original untouched for the handler to read the exact raw bytes PawaPay actually signed.

**Plugin-added models get no automatic `id`/`createdAt`/`updatedAt` columns** (only better-auth's own core models do); the `payment` model's schema (`infra-payment/schema.ts`) declares `createdAt`/`updatedAt` explicitly (`type: "date"`, `defaultValue: () => new Date()`, `onUpdate: () => new Date()` for the latter); `id` is still implicit for every model, plugin or core.

`kit/payments/` wraps all of this for the dashboard: `listPayments` (admin, every payment, joined against `user` for name/email via one follow-up `IN` query rather than one-per-row), `listMyPayments` (self-service, `SessionMiddleware`-gated, the first non-admin-gated kit/ read since self-service API keys were removed), `findPayment` (admin, one payment's full detail for the receipt page; a refund also carries the deposit it reversed and a deposit carries any refunds against it, cross-referenced via a `{depositId, originalPaymentId}` JSON blob in the `payment.metadata` column since it isn't indexed/queryable directly), plus `getPaymentConfig`, `getWalletBalances`, `initiateDeposit`, `initiatePayout`, `initiateRefund`. `/billing` (admin) shows every payment with a **net total per currency in the table's own `<tfoot>`** (via `DataTable`'s `footer` render-prop, see Widgets below; completed transactions only, deposits add, payouts/refunds subtract) and links each row's id to `/billing/$paymentId`, a printable receipt page (`window.print()`, print-specific spacing via Tailwind's `print:` variant) showing the full detail plus the deposit↔refund cross-links. `/payments` (`_account`, any signed-in user) is the self-service equivalent: a deposit form and the caller's own history, no receipt pages or totals.

**A component render function that reads `window` directly crashes SSR, not just "works differently."** Guard any client-only read (`typeof window !== "undefined" ? window.location.origin : ""`) if there's any chance the component renders on the server first; this has bitten more than one place in this app's history.

**The dashboard's own sign-in (`Login`, `src/features/auth/login.tsx`) is email+password only, always**, regardless of which other methods exist. Those methods (twoFactor as a second factor aside, passkey) exist for the OAuth end-user sign-in flow this project now does build (`/sign-in` is also `oauthProvider`'s `loginPage`), not as options on the admin dashboard's own form: owner/admin access can never depend on a method, so it isn't given the choice.

**Widgets, the only reusable pieces meant to be imported from anywhere, now live in `@infra/ui`'s `widgets/`** (`shared/ui/src/widgets/`, imported as `@infra/ui/widgets/tables`, `@infra/ui/widgets/blocks`, `@infra/ui/widgets/dialog-widget`), not in infra:
- `widgets/tables/`: `DataTable` (search, per-column filters auto-detected from data shape, column visibility, sort, row selection + bulk actions, pagination, built on `@tanstack/react-table` v9's real API) and `DataTablePagination`. `aria-label` is a **required** prop (react-aria's underlying grid throws a dev warning without one). `footer?: (columnCount: number) => ReactNode` renders inside the table's own `<tfoot>` (via `components/ui/table.tsx`'s `TableFooter`, which wraps react-aria-components' own `TableFooter`, a genuinely separate footer region from the sortable/selectable body rows, not a synthetic row mixed into the real row model), used by `features/payments/list-payments.tsx` for its net-total line.
- `widgets/blocks/`: the `useAppForm`/`withForm` TanStack Form setup (field components including `radioCard`, with an optional `icon?: ReactNode`, added for Console's framework picker, `multiselect`, `switch`, and the submit button) used by every form in the app.
- `widgets/dialog-widget/`: `DialogWidget`, the one entry point for a drawer-style dialog.

Feature-specific things that use a widget but aren't reusable themselves live in `components/dashboard/<feature>/`, not in `widgets/`.

**UI components follow shadcn's `aria-lyra` style** (`@infra/ui`'s own `components.json`): built on `react-aria-components`, not Radix. **Never hand-author a file under `@infra/ui`'s `components/`**, always `bunx shadcn add <component>` from within `shared/ui/`. The generated API frequently differs from shadcn's default/Radix registry, e.g. `DropdownMenuTrigger` is the *root* wrapping both the trigger element and `DropdownMenu` (the content), not just the trigger button.

**Dates go through `date-fns`**, not `Date.prototype.toLocaleString`/`toLocaleDateString`. See any list/detail component for the `format(date, "PPP")` convention.

**Styling is Tailwind v4, CSS-first, and lives in `@infra/ui`, not infra.** There is no `tailwind.config.js`; theme tokens, the `container` utility, and custom utilities (`no-scrollbar`, `dualTone`) are all defined in `@infra/ui`'s `src/globals.css` (imported here as `@infra/ui/globals.css?url` in `__root.tsx`) via `@theme inline` and `@utility`. Colors are OKLCH and swap via a `.dark` class selector, even though both apps currently force dark. `@infra/ui/typeset.css` holds prose/typography rules. infra keeps its own `tailwindcss`/`@tailwindcss/vite` devDependency regardless; Tailwind still needs to scan infra's own route/feature files for the utility classes used directly in their JSX.

**Path alias**: `@/*` maps to `src/*` (set in both `tsconfig.json` and consumed via `vite-tsconfig-paths`); this is infra's own source only. Anything from the shared UI kit is imported via `@infra/ui/...` instead (see the monorepo root `CLAUDE.md`), not through `@/`.

**Responsive breakpoints diverge from Tailwind's defaults**: `src/lib/use-media-query.ts` defines its own `BREAKPOINTS` map (`md: 800`, plus `3xl: 1600` / `4xl: 2000` beyond Tailwind's stock scale). `useIsMobile` itself is hardcoded to `(max-width: 768px)` rather than using the `md` entry from that same map.

## Lint/format notes

- Linting and formatting both went from per-package ESLint/Prettier to one root-level Biome config (`biome.json`), run from the monorepo root, not from inside `infra/`. See the root `CLAUDE.md` for what it covers and which rules are deliberately off. `typescript-eslint`'s TS-version compatibility window (the reason `bun run lint` used to fail outright here) no longer applies since ESLint is gone; TypeScript is on the `^7` line.

## Known issues / cleanup backlog

Flagged but not yet done, read before assuming either is already handled:

- **The Cloudflare Vite plugin's local AI-agent observability capture** (`X_LOCAL_OBSERVABILITY` / `X_LOCAL_EXPLORER`, controlled via `.env.local`, not a `package.json` script flag; `bun run dev` is just `vite dev --port=3000`). When enabled and running inside an AI coding agent, the plugin captures every internal sub-operation, KV call, D1 call, and internal module fetch during SSR as a span in a local SQLite-backed store, queryable at `/cdn-cgi/local/explorer/api/local/observability/query` (also useful directly: `/cdn-cgi/local/explorer/api/d1/database/<id>/raw` runs arbitrary SQL against the real local D1 database, handy for verifying state without going through the app's own code paths). In sustained use this has generated 150,000+ spans and made requests hang indefinitely once enough accumulated. It's tied to request volume, not idle time. If local dev becomes unresponsive during a long session, this is the first thing to check: either lower the volume of requests being sent, or restart the dev server to clear the accumulated span store. This is unrelated to and doesn't touch `wrangler.jsonc`'s `observability` block, which governs the real deployed Worker.
- **PawaPay's dashboard callback URLs point at a placeholder (a Postman mock endpoint), not this app's real `/pay/webhook`.** Nothing in local dev auto-transitions a payment out of `pending`. The signature verification and status-update logic are real and tested (including against a real signed request via a live rotate → token-exchange round trip and synthetic self-signed test cases covering tampered-body/wrong-key scenarios), but there's no live PawaPay-signed callback hitting this instance yet. Testing that end-to-end needs either a public tunnel (ngrok/Cloudflare Tunnel) pointed at local dev, or a real deployment PawaPay's dashboard can be reconfigured to call.
- **Receipts are email, not a downloadable PDF, by decision**: the `/billing/$paymentId` receipt page (structured HTML, printable via `window.print()`) stays as the admin-side printable view. `www`'s self-service side deliberately doesn't add PDF generation on top of it (no server-side rendering library fits the Workers runtime cleanly); instead `@infra/payment`'s `resendReceipt` endpoint re-sends the same `onPaymentCompleted` email on demand, one or many at a time from the transaction list.
